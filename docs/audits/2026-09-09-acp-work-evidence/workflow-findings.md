## PM / handoff churn: necessary versus avoidable

- Necessary: exact base/head range after branch rewrite, final-head check status, and runnable test commands. H1493 explains the prior amendment range omitted product changes. PM must not accept a green result from an old head, as H615 showed.
- Avoidable: PM asks for a40-character SHA and skipped statuses (H1449); Gemini provides them (H1451); PM immediately asks for the same allegedly missing fields again (H1453), prompting a repeated answer (H1454). Whether caused by queued delivery or PM reading, the room shows a redundant correction.
- Avoidable: asking several agents to restate the same decision. At23:02 Luna/Astra/PM/Architect all weigh in on one privilege/setup decision (H701,703–705); PM says the room answered three times and stops further answers (H706). Use one decision owner plus a factual correction channel.

Later force pushes/rebases also invalidate ready review ranges (H660,679,1493). A clean baton and append-only task commits remove much of this work.
- Not evidence of waste: no-tool PM/Architect turns can be substantive routing/design; silent turns still consume context but may be correctly suppressing chat. Do not rank PM solely on tool count or sum concurrent waits as elapsed delivery delay.

## Eight concrete recommendations

1. **Make completions wake the owner.** Tool/gate exit should send one final completion tagged to PM, with success/failure and output path. Keep a single durable current-owner/task/head/status record. A terminal answer that says “I can't page PM” must not count as handoff complete. Fix delivery before adding more reminders.
2. **Keep authorization separate from transport limits.** Overnight authorization should not depend on Ben resetting the hop counter. Count human-approved workflow transitions separately from runaway conversational loops, or provide an explicit trusted coordinator continuation. Measure blocked-recipient durations.
3. **Assign one branch writer and keep review ranges stable.** Handover requires clean tree,current head,incoming owner acknowledgment; prohibit mid-task rewrite. Architect owns plan edits; builder references one approved revision. Batch several small plan rulings into a correction when they are already known instead of multiple serial doc merges.
4. **One compact evidence form, mechanically checked.** PR/base/head, tests and result, GitHub terminal status, deviations, unproven paths, next owner. Query checks programmatically; do not ask an LLM to reproduce the same skipped-job list several times. Preserve final-head correctness while eliminating status prose.
5. **Put boundary acceptance checks into each task before coding.** For this feature: actual service identity/capabilities, serialized subscriber snapshots, persistence, notification consumer compatibility, one approval writer, actual cancel-session path, forced write-order inversion, and redaction negative tests. A small fixture at the true boundary beats more assertions on shared objects.
6. **Review the connected path early, then review deltas.** Keep cross-model review and targeted live proof. The first provider-client-runner vertical path should be proven before expanding tables and migration. After a correction, review named findings plus adjacent regressions; avoid rereading the whole unchanged slice.
7. **Use full gates at meaningful integration points, focused checks per correction.** Run formatter/linter/types before the36–38minute gate; avoid repeated full suites for reporting-only,docs-only,or test-fixture-only corrections unless policy genuinely requires them. Retain one final trusted full gate on the delivered head and required CI. Parent audit supplies gate receipts; room chatter alone cannot prove run count or critical-path time.
8. **Judge seats by accepted bounded work and rework, not model reputation.** Pilot new builders on a low-boundary task with explicit checks. For task8a-like stream/security work retain a reviewer tracing real consumers. Let independent UI work proceed on a separate branch once its contract is stable, without sharing one writable branch or pretending blocked backend assumptions are settled.
