# Scheduled tasks and proactive messaging research

Research date: 2026-10-07. This is evidence for discussion, not an approved scope or implementation spec. No meeting-module code was changed.

## Which products this means

**Muse** means Meta's personal agent; **Grokbot** means SpaceXAI's **Grok Bot**, launched August 11, 2026; **Dots** means OpenAI's recently launched ChatGPT dots. These are different from Muse Code, ordinary Grok chat automations, the older new.computer Dot, and the local Dots coding session. [Meta Muse reminders](https://www.meta.com/help/artificial-intelligence/1484325780075655/), [Grok Bot introduction](https://x.ai/news/introducing-grok-bot), [OpenAI getting started](https://learn.chatgpt.com/docs/dots/getting-started).

The useful distinction is between **requested scheduled work**, **requested monitoring of changes**, and **agent-initiated suggestions**. Vendors present these together, but they have different triggers and permission implications. OpenAI explicitly separates proactive read-only research from recurring tasks that can perform authorized actions. [Dots tasks and memory](https://learn.chatgpt.com/docs/dots/tasks-and-memory).

## What permissions actually mean

**Muse:** permissions distinguish reading from writing, with connector and web-access defaults. Approval scope can be one action, the current task, a site or a connector. Users can inspect task details before approving and revoke access. Meta documents important permission checks outside the model. Scheduling therefore does not imply unrestricted future writes. [Guidance and approvals](https://www.meta.com/help/artificial-intelligence/1385290430137537/), [security](https://www.meta.com/help/artificial-intelligence/1047255454427887/).

**Grok Bot:** approval shows the operation and inputs, with allow-once, saved allow and deny. Auto Review rules can require approval or allow matching actions; **Ask first** wins conflicts. Team rules can only be made stricter by individual rules. The docs call Auto Review model-based, so it is not equivalent to a deterministic permission boundary. [Approvals and security](https://docs.x.ai/grok-bot/approvals-security-and-privacy).

**Dots:** the proactive research agents cannot send messages, mutate connected apps, or control browsers/computers. Their private research goes back to the parent dot. Assigned recurring work can include writes the user authorized; that task's permissions and schedule are separate from ambient proactive research. [Tasks and memory](https://learn.chatgpt.com/docs/dots/tasks-and-memory).

**OpenClaw:** standing orders define scope/approval/escalation while automations enforce timing. Its docs distinguish authority from cadence explicitly. Scheduler context and tool restrictions remain relevant; a prompt naming a path or service does not itself authorize access. [Standing orders](https://docs.openclaw.ai/automation/standing-orders), [execution context](https://docs.openclaw.ai/automation/cron-jobs/payloads).

## Failure and delivery lessons

- **Separate execution from delivery.** OpenClaw records whether work ran, whole-run completion and delivery outcome separately. It can retain a result in the conversation even when an external route fails. Ambiguous delivery is recorded as unknown rather than automatically replayed. This is a useful reference for avoiding duplicate messages; it is not a blanket exactly-once guarantee. [Delivery](https://docs.openclaw.ai/automation/cron-jobs/delivery), [run management](https://docs.openclaw.ai/automation/cron-jobs/managing-jobs).
- **Make stale or missing inputs visible.** Grok Bot's routine guidance asks users to define source-failure policy and inspect current inputs and partial completion. Its troubleshooting names disabled routines, wrong time zones, removed owners, expired integrations and paused usage as failure causes. Exact internal retry timing is not documented there. [Routine design](https://docs.x.ai/grok-bot/skills-routines-and-automations), [troubleshooting](https://docs.x.ai/grok-bot/troubleshooting).
- **Have an explicit missed-run policy.** OpenClaw normally catches up missed recurring work after downtime, with an option to skip those occurrences. Transient one-shot errors retry; recurring execution failures back off. These are documented choices, not behavior we can assume for Muse/Dots/Grok Bot. [Management and retries](https://docs.openclaw.ai/automation/cron-jobs/managing-jobs).
- **A check need not send a message.** OpenClaw heartbeat can stay silent, limit active hours, and skip busy periods; selected monitoring can compare persisted observations to suppress repeats. Execution, result storage and interruption should be distinct decisions. [Heartbeat](https://docs.openclaw.ai/gateway/heartbeat), [watcher state](https://docs.openclaw.ai/automation/cron-jobs/schedules).

## Existing Moss foundations and scope

> 🧠 **From Hindsight memory (Component map)** — Moss already has pg-boss jobs, briefings, notifications/push, and proactive-monitoring subsystems. The following inventory was checked against current source rather than relying on that historical description.

At research baseline `60505036c`, these are concrete reuse candidates, not a proposal to build another scheduler:

- [Briefing schedule reconciliation](../../packages/briefings/src/schedule.ts) saves timezone-aware daily/weekly pg-boss schedules keyed by a definition ID; its payload contains actor and definition metadata rather than the instruction or private source material.
- [Briefing workers](../../packages/briefings/src/jobs.ts) already run scheduled work and expose a ready-notification path. This is a precedent for scheduling and delivery, not proof that arbitrary chat instructions can run unattended.
- [Proactive scanner](../../packages/proactive-monitoring/src/scanner.ts) collects source signals and ranks them into cards. [Anti-spam policy](../../packages/proactive-monitoring/src/anti-spam.ts) applies dismissed-item suppression, daily/hourly caps, and quiet-hours deferral. A monitoring card is not automatically a conversational Moss message.
- [Notification creation](../../packages/notifications/src/repository.ts) checks module notification preferences, defers normal notifications during quiet hours, upserts keyed events, and enqueues push or a deferred summary. Re-firing an event key updates the row and resets its read state: this is not an exactly-once delivery guarantee.

The existing open [issue 2388, Schedules and watchers the user creates in chat](https://github.com/motioneso/moss/issues/2388), already describes chat-created scheduled instructions, a user-visible management list, and later event watchers/heartbeat behavior. It is a starting point for the discussion, not an approved build spec. Its older competitor claims should be checked against current primary docs.

Before choosing an implementation, follow the actor-scoped background AI execution and conversation-persistence paths, current permission enforcement, and delivery failure recovery. This inventory does not establish those seams end to end. Retain the repo's metadata-only queue, provider-agnostic AI, private-by-default access, and module-isolation requirements.

## Proposed product direction

These are recommendations inferred from the evidence, not commitments:

1. **Start with explicit user requests.** Support examples like “Every morning, review my calendar and tasks and message me here” before granting broad unsolicited responsibility. The successful UX pattern is chat creation with a concrete confirmation, plus one place to inspect/edit/pause/cancel.
2. **Distinguish three jobs in the conversation.** A reminder can deliver fixed text; a scheduled check must read current sources; a watcher should notify only when its stated condition changes. Agent-initiated suggestions need a separate discussion about scope and interruption.
3. **Make a proactive message a normal conversation entry.** It should say why Moss is speaking, link its evidence where applicable and allow a reply. Push/email are delivery preferences layered on that durable result.
4. **Confirm what repeats, when, where and with what authority.** Include time zone and next run. A task that reads and reports differs from one that edits the calendar or contacts someone. Scheduled authority needs explicit scope and revocation.
5. **Design quietness and failures into the first useful slice.** Avoid repeated unchanged alerts; expose pause/cancel and last/next run; choose downtime behavior; show unavailable inputs and delivery failures without claiming successful completion.

The product decision to discuss first is whether this starts as **user-directed recurring briefings/checks** or includes **Moss choosing opportunities to message the user without a named request**. Both fit the feature idea, but they need different authority and attention rules. Conversation placement, integration with existing briefings, frequency/usage bounds, and interruption criteria also remain open.

## Evidence limits and research method

Primary product help/docs were read on 2026-10-07. Recent products and gradual rollouts make older tutorials unreliable: Grok Bot routine docs date September 14 and notification/approval docs September 28, 2026. Capabilities described here are documented behavior, not tested accounts or service guarantees.

Muse's reviewed pages do not specify quiet hours, suppression of unchanged checks, retry/backfill, maximum active tasks or delivery guarantees. Dots' reviewed pages do not specify internal heartbeat cadence or queue infrastructure. Grok Bot's reviewed docs do not give an exact general retry/backfill contract. Location reminders in Muse and future channel features in Dots should not be silently treated as baseline Moss requirements. Dots texting is coming soon and agent-initiated calls are planned after launch, rather than established current channels. [Dots channels](https://learn.chatgpt.com/docs/dots/channels).

Discovery followed Agent Reach's Exa route. Exa returned HTTP 429 after initial successful searches, so targeted searches used the installed web-search connector; webpage reading continued through Agent Reach's Jina route. OpenAI sources were verified by the main research session through official developer-docs tools. Secondary comparison articles were useful to identify products; product claims above cite first-party pages. No source documents an internal architecture for all three closed products, and this note does not infer one from “always-on” marketing.
