# Spec — issue #1993: CSP still blocking images on Today and Sports/News; stale hashed assets served as text/plain

## What is wrong

1. **Missing image host.** ESPN serves some event/scoreboard art (the "stitcher" path) from
   `s.espncdn.com`, a host distinct from `a.espncdn.com` and `s.secure.espncdn.com`, which are
   already allowed. The browser's Content Security Policy blocks it, so that art never loads on
   Today and Sports. Confirmed: `s.espncdn.com` is absent from the sports source's image host list
   (`packages/sports/src/source/espn-source.ts`), the copy of the policy baked into the nginx
   config (`infra/nginx/jarv1s-web.conf`), and the test that pins both copies
   (`tests/unit/static-web-csp.test.ts`). The news sources' image hosts were checked too and already
   match the nginx copy — no gap there.

2. **Inline script warning.** The browser console reported a blocked inline script with a specific
   fingerprint (hash). A full search of this codebase found no inline `<script>` tag anywhere — not
   in the app's HTML page, not in the offline page, not written by any of our own code. The
   generated page's script tag loads a real file (`/src/main.tsx`), not an inline block. The most
   likely explanation is a browser extension injecting its own script into the page, which this
   project cannot fix and should not paper over with a permissive policy. This item is closed by
   confirming — with the console open in a private/incognito window with no extensions — that the
   warning does not reproduce.

3. **Old hashed file returns the wrong response.** When a browser still holds an old page that
   references a stylesheet or script whose hashed filename no longer exists (because a newer build
   replaced it), two different code paths mishandle the miss:
   - In the API server's own static file handler (`apps/api/src/static-web.ts`), a request for a
     missing file whose name has a dot in it (like `something.css`) is supposed to answer with a
     plain 404. Instead it calls Fastify's built-in "not found" trigger from inside the app's own
     not-found handler, which hands the response to Fastify's generic fallback: still a 404, but
     with the wrong content type (plain text) instead of leaving the well-formed 404 our own code
     was about to send. Combined with the "don't sniff the content type" header the app always
     sends, the browser refuses to use it as a stylesheet and shows exactly the console warning
     from the bug report.
   - In the production web server config (`infra/nginx/jarv1s-web.conf`), any request that doesn't
     match a file on disk falls back to serving the app's main page (`index.html`) — the standard
     behavior for letting the app's own in-page navigation work. But that fallback also catches
     requests for missing hashed asset files, which should never fall back to the main page; they
     should get a real 404 so the browser (or a service worker) knows the old file is truly gone
     rather than silently getting page content back with a mismatched content type.

   The separate service worker file was reviewed for overlap with the earlier image-caching fix
   (issue #1872) — it does not cache the app's stylesheets or scripts by filename and does not
   contribute to this bug; no change needed there.

4. **Chat stream interruption seen once during the same load.** Reviewed and attributed to the app
   restart happening mid-page-load during that single observation, not a separate bug. No fix
   needed; not covered by this spec's exit criteria.

## The fix

- Add `s.espncdn.com` to the sports source's exported image host list
  (`packages/sports/src/source/espn-source.ts`, `ESPN_IMAGE_HOSTS`). This host list already flows
  automatically into the app's built-in policy (`apps/api/src/static-web.ts`) through the module
  registry, so no other production code changes for that side.
- Add the same host to the nginx copy of the policy (`infra/nginx/jarv1s-web.conf`).
- Update the pinning tests that hard-code the expected host lists so they require the new host:
  `tests/unit/static-web-csp.test.ts`, `tests/unit/sports-registry.test.ts`,
  `tests/unit/sports-manifest.test.ts`.
- In `apps/api/src/static-web.ts`, stop re-triggering Fastify's generic not-found fallback from
  inside the app's own not-found handler. Send a real, correctly-labeled 404 response directly for
  both the asset-miss case and the `/api`/`/health` passthrough case, so the content type is never
  wrong and the "don't sniff" header stays honest.
- In `infra/nginx/jarv1s-web.conf`, add a location block for the built asset folder (`/assets/`)
  that returns a plain 404 for a missing file there instead of falling back to `index.html`. The
  page-navigation fallback for everything else stays as-is.
- No change planned for the inline-script item beyond confirming the console warning does not
  reproduce with browser extensions disabled; if it still reproduces in that clean state, that is a
  new finding to report back before any fix is written.

## How this will be verified

- A new or updated unit test in `tests/unit/static-web-csp.test.ts` (or a sibling test file for
  `static-web.ts`) that requests a plainly nonexistent hashed file, e.g. `/assets/does-not-exist.css`,
  through the API's static handler and asserts: status 404, content type is the real file type for
  a 404 answer (not left as a stale value), and the body is not the app's main page.
- Existing pinning tests updated and green with `s.espncdn.com` included.
- `pnpm format:check`, `pnpm lint`, `pnpm typecheck` clean.
- The `verify-gate` skill's scoped unit test run green for the touched packages
  (`static-web`, `sports`).
- Live-path proof on the dev instance: open Today and Sports pages, confirm no console CSP image
  warnings for ESPN art; request a made-up hashed asset path directly against the dev instance and
  confirm a real 404, not a 200 or a wrong content type; open the same pages in a private window
  with extensions disabled and confirm no inline-script console warning.

## Acceptance (from the issue)

On Today, Sports, and News: no CSP `img-src` violations for ESPN or news art; no inline-script
violation; a stale hashed asset request yields a clean 404; a page refresh recovers without a hard
reload.
