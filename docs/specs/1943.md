# 1943 — Asking Moss for a module in chat: prove it really works

## Where this started

Issue #1943 was cut from #1888 one minute before pull request 1940 merged, from a status
report that was already out of date. It says the chat request "fails before reaching the
build service". That exact failure was fixed in 1940 and the fix is on main today.

So the honest question this branch has to answer is not "why does it still fail" but
"does it actually work, and can we prove it".

## What is wrong

The browser test that is supposed to guard this feature can pass while the feature is
broken.

`tests/live/workshop-1888-uat.spec.ts` signs in, opens the chat drawer, sends one message,
and then waits for the words "Build it" to appear anywhere on the page. The chat drawer
restores the earlier conversation when it opens, and an approved plan from a previous run
is still sitting in that history with its "Build it" button. So the words are already on
screen before the message is even answered.

Run against this branch it passed in 1.9 seconds. A real turn takes about 20 seconds,
because a model has to answer. Nothing new happened: the database shows no new build
record and no new entry in the tool audit log for that run. The test was reading an old
card.

That is a hole in the gate that is meant to keep this feature honest, and it is the same
gate that signed off pull request 1940.

## What this change does

1. Make the browser test prove the card came from this turn, not from history. It counts
   the plan cards on screen before sending, and then waits for one more to appear. A
   leftover card cannot satisfy that, and neither can a polite refusal.
2. Run that honest test against a live instance on this branch, and report what it finds.
3. If the honest run shows the chat request still failing, fix the failure. If it shows the
   feature working, say so plainly with the database evidence behind it.

Nothing about the feature's own behaviour changes unless step 3 turns up a real failure.

## How it is verified

- The browser test is run against a live instance built from this branch: real API, real
  Postgres with row-level security on, real chat engine, real model. Nothing faked.
- Passing means the test exit code is 0 **and** the database gained a new module build
  record and a new successful entry in the tool audit log, timed to that run. The database
  check is what makes the pass real, because it cannot be satisfied by anything already on
  the page.
- The test is also run once with the message removed, to confirm it now fails when no new
  card arrives. A gate that cannot fail is not a gate.
- The usual local checks: formatting, linting, both TypeScript passes, and the unit tests
  for the files touched.
