# Spec 1992 — show the owner when chat archiving is paused or failing

## What

Chat archiving writes a note for each day's conversation into the user's connected notes folder,
once a day, when the setting is turned on. Right now if that write cannot happen, nothing tells
the owner — the daily note is just quietly missing.

This change makes the daily archive job record a short, safe status whenever it can't do its job,
and clears that status the next time a write succeeds. Settings shows the status next to the
archiving controls so the owner knows something needs attention.

## Behavior

The daily archive job (`handleArchiveDayJob` in `packages/chat/src/jobs.ts`) already calls
`writeDailyChatArchive` and gets back a result describing what happened. Today that result is
thrown away. This change reads it and records one of three states under a new preference key,
`chat-archive.status`:

- **Write succeeded** (`written: true`) — clear the status (store `null`). Archiving is healthy
  again.
- **No notes folder connected** (`writeDailyChatArchive` reports `no-notes-source`) — record
  `{ state: "paused", reason: "No notes folder is connected." }`.
- **The write itself failed** — either `writeDailyChatArchive` reports `bad-folder`, or it throws
  (both today's file and its fallback name are already taken by a file archiving didn't write) —
  record `{ state: "failed", reason: "<short plain-English reason>" }`. The reason never contains
  chat text, note contents, or a file path — just what kind of problem it was, e.g. "The transcript
  folder setting isn't valid." or "Today's note already exists and wasn't written by chat
  archiving."

`no-sessions` (nothing to archive that day) and archiving being turned off are not failures and
never touch the status — the status only reflects "should have written and couldn't."

The status is plain data (a small JSON object or null), stored with the existing preferences
mechanism, the same way `chat-archive.enabled` and `chat-archive.folder` already are. It carries no
chat text and no server file paths.

## Surface

- `GET /api/me/chat-archive` returns the status alongside `enabled` and `folder`, as an optional
  `status` field: either `null` or `{ state: "paused" | "failed", reason: string }`.
- Settings shows the status as a short message directly under the "Save chats to Notes" controls,
  only when a status is present. No status shown means archiving is healthy (or off).

## Out of scope

- Chat replies and the rest of the chat feature are untouched — this only touches the once-a-day
  archive job and its status display.
- No change to what counts as a valid folder, or to how the write itself resolves the notes
  folder — this only observes the existing result and records it.

## Verification

- Unit tests on `handleArchiveDayJob`: a successful write clears a previously-set status; a
  missing notes folder sets a "paused" status; a folder validation failure and a file-name
  collision each set a "failed" status with a reason that contains no file path or chat content;
  archiving-off and no-sessions-that-day leave any existing status untouched.
- Unit test on the settings route: `GET /api/me/chat-archive` includes the stored status.
- Live proof on the dev instance: turn on archiving, disconnect the notes folder (or otherwise
  cause a failure), trigger the archive job, confirm Settings shows a paused/failed message next
  to the archiving controls, then reconnect and confirm a successful run clears it. Chat replies
  keep working throughout.
- Release note: user-facing (Settings now shows when daily chat archiving needs attention).
