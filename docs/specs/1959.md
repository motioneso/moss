# Spec: store all six medication schedule types and a real time zone (#1959)

## What exists today

- `packages/wellness/src/occurrence-engine.ts` already computes dose dates for all six
  schedule shapes (daily, selected days, every interval with a days/weeks/months choice,
  monthly by numbered date or by weekday position, on/off cycle, as needed), including the
  explicit "last day of the month" choice and real per-schedule time zone handling across
  daylight-saving changes. This file is not changed by this work.
- `app.medications` (migration `0083`) only has columns for the old three-choice picker:
  `frequency_type` (`once_daily`, `times_per_day`, `specific_weekdays`, `every_n_hours`,
  `as_needed`, `cyclical`), `times_per_day`, `interval_hours`, `weekdays`, `schedule_times`,
  `cycle_days_on/off`, `cycle_anchor_date`. No start date, no end date, no time zone.
- `packages/wellness/src/schedule.ts` (`toEngineInput`) maps those old columns onto the
  engine's shapes, always with a fixed `1970-01-01` stand-in start date and `timeZone: "UTC"`.
  This is how the four existing screens (schedule preview, Today, adherence, exports) get
  their dose lists.
- Save and load: `packages/wellness/src/repository.ts` (`createMedication`,
  `updateMedication`, `listMedications`, `getMedication`), request parsing and hand-rolled
  validation in `packages/wellness/src/routes.ts` (`parseCreateMedicationBody`), the shared
  contract in `packages/shared/src/wellness-api.ts` (`MedicationDto`,
  `CreateMedicationRequest`, `MEDICATION_FREQUENCY_TYPES`), and DTO mapping in
  `packages/wellness/src/serialize.ts` (`serializeMedication`).
- `every_n_hours` is a legacy-only shape (not one of the six) that stays exactly as it is;
  it is not part of this change.

## What this change does

### 1. New migration: `packages/wellness/sql/0194_wellness_medication_schedule_v2.sql`

Adds columns to `app.medications` (all nullable, so existing rows are untouched):

- `schedule_start_date date`
- `schedule_end_date date`
- `time_zone text` — IANA name
- `interval_unit text` — `days` | `weeks` | `months`
- `interval_count smallint`
- `month_kind text` — `date` | `weekdayPosition`
- `month_day smallint` — 1-31
- `month_day_is_last boolean not null default false`
- `month_weekday_position text` — `first` | `second` | `third` | `fourth` | `last`
- `month_weekday smallint` — 1 (Mon) - 7 (Sun)

Extends the `frequency_type` allowed list (drop + re-add the named CHECK constraint from
`0083`, which is allowed — only editing the applied file itself is forbidden) with two new
values: `every_interval`, `monthly`.

Adds new named CHECK constraints (defense in depth, same pattern as `0083`):

- `every_interval` rows need `interval_unit`, `interval_count >= 1`, `schedule_start_date`,
  `time_zone`, and at least one `schedule_times` entry.
- `every_interval` with `interval_unit = 'weeks'` also needs at least one `weekdays` entry.
- `monthly` rows need `month_kind`, `schedule_start_date`, `time_zone`, and at least one
  `schedule_times` entry.
- `monthly` with `month_kind = 'date'` needs exactly one of `month_day` (1-31) or
  `month_day_is_last = true`, and no weekday-position fields set.
- `monthly` with `month_kind = 'weekdayPosition'` needs both `month_weekday_position` and
  `month_weekday` set, and no date fields set (`month_day` null, `month_day_is_last = false`).
- `schedule_end_date`, when present, is never before `schedule_start_date`.
- The new columns are all null/false for every frequency type except `every_interval` and
  `monthly` — keeps old rows unambiguous.

Migration is additive-only and re-runnable: `CREATE TABLE IF NOT EXISTS` semantics don't
apply to `ALTER TABLE ADD COLUMN`, so each statement uses `ADD COLUMN IF NOT EXISTS` /
`DROP CONSTRAINT IF EXISTS` so it applies cleanly on a fresh database and one that already
has medications in it.

### 2. Shared contract (`packages/shared/src/wellness-api.ts`)

- `MEDICATION_FREQUENCY_TYPES` gains `every_interval` and `monthly`.
- `MedicationDto` and `CreateMedicationRequest` gain the new fields above, in camelCase,
  all optional/nullable: `scheduleStartDate`, `scheduleEndDate`, `timeZone`, `intervalUnit`,
  `intervalCount`, `monthKind`, `monthDay`, `monthDayIsLast`, `monthWeekdayPosition`,
  `monthWeekday`. `UpdateMedicationRequest` is unchanged (schedule editing stays out of
  scope, same as today — delete and recreate).

### 3. Server-side validation (`packages/wellness/src/routes.ts`,

`parseCreateMedicationBody`)

Extends the existing hand-rolled checks (same style as the current function) with the new
rules, only enforced when `frequencyType` is `every_interval` or `monthly` — old-style
requests are validated exactly as they are today, so the current picker's request shape
keeps working unchanged:

- `frequencyType` must be one of the (now eight) values.
- `every_interval`: `intervalUnit` must be `days`, `weeks`, or `months`; `intervalCount` a
  whole number >= 1; `scheduleTimes` non-empty; `weekdays` non-empty (ISO 1-7) when
  `intervalUnit` is `weeks`; `startDate` required (`YYYY-MM-DD`); `endDate`, if present,
  not before `startDate`.
- `monthly`: `monthKind` must be `date` or `weekdayPosition`; for `date`, exactly one of a
  1-31 `monthDay` or `monthDayIsLast: true`; for `weekdayPosition`, both `monthWeekdayPosition`
  (`first`/`second`/`third`/`fourth`/`last`) and `monthWeekday` (1-7) required; `scheduleTimes`
  non-empty; `startDate` required; `endDate`, if present, not before `startDate`.
- `as_needed` keeps rejecting every scheduling field, now including the new ones too.
- Time zone is never a request field (matches the existing `createCheckin` pattern — see
  `resolveRouteTimeZone` already used elsewhere in this file). The route resolves the
  caller's real time zone the same way and passes it to `repository.createMedication` for
  every new medication, old or new family alike, which stores it in the new `time_zone`
  column. This is how "the silent UTC treatment goes away for new saves" without the form
  changing: the picker doesn't need to send a time zone field for its save to get a real
  one recorded. Existing rows are untouched (`time_zone` stays null), which is what keeps
  their behavior identical.

### 4. Repository (`packages/wellness/src/repository.ts`)

- `CreateMedicationInput` gains the new fields plus a `timeZone` parameter (route-supplied,
  same pattern as `createCheckin`'s `timeZone` argument).
- `createMedication` writes all new columns (null where not applicable) plus `time_zone` for
  every new row.
- `listMedications` / `getMedication` already `selectAll()`, so the new columns come back for
  free once `packages/db/src/types.ts`'s `MedicationsTable` lists them.

### 5. DTO mapping (`packages/wellness/src/serialize.ts`)

`serializeMedication` maps the new columns to the new camelCase DTO fields (straight
pass-through, `null` when absent — same style as every other field in that function).

### 6. Wiring the engine for the two new families

(`packages/wellness/src/schedule.ts`, `toEngineInput`)

- `every_interval` maps to the engine's `everyInterval` family (`days`/`weeks`/`months`
  variant chosen by `interval_unit`), anchored at the medication's own
  `{ startDate: schedule_start_date, endDate: schedule_end_date, timeZone: time_zone ?? "UTC" }`
  — a real anchor, not the `1970-01-01`/`UTC` stand-in the other families use.
- `monthly` maps to the engine's `monthly` family (`date` or `weekdayPosition` variant
  chosen by `month_kind`), same real anchor.
- The five existing families (`once_daily`, `times_per_day`, `specific_weekdays`,
  `every_n_hours`, `cyclical`) are **not touched** — same stand-in anchor, same `"UTC"`, same
  output, so the four existing screens produce identical results for existing medications.
  This is what "existing rows keep working by treating their stored data exactly as they do
  today" means in code: the branch each family takes through `toEngineInput` doesn't change
  for the five old families, only two new branches are added.
- Because `computeSchedule`, the adherence code, and the export renderer all go through this
  same `toEngineInput` function, saving an `every_interval` or `monthly` medication makes it
  show up correctly on all four screens with no further wiring — proving the "shared code"
  claim from #1953 for the two new families too.

## Validation rules, gathered in one place (server-side, before saving)

- `frequencyType` is one of the eight (six spec types, plus the two `once_daily`/
  `times_per_day` daily variants, plus legacy `every_n_hours`).
- Start date required for `every_interval` and `monthly` (the two new types); end date
  optional, never before start date.
- `every_interval`: whole-number interval >= 1; unit one of days/weeks/months; weekdays
  required (>=1) only for the weeks unit.
- `monthly` by date: a date 1-31, or the explicit last-day-of-month choice — never both,
  never neither.
- `monthly` by weekday: a position (first/second/third/fourth/last) and a weekday.
- `cycle` (existing `cyclical`): whole-number on/off day counts, on >= 1, off >= 0
  (unchanged from today).
- `selectedDays` (existing `specific_weekdays`): at least one weekday (unchanged).
- Time zone: resolved server-side (never a request field), must be a real recognized IANA
  name — validated the same way `resolveRouteTimeZone` already validates it elsewhere.
- `as_needed`: no dose times, and now also no interval/monthly fields — it never produces a
  dose slot or a missed-dose count (unchanged, extended to the new fields).
- A dose on the 29th/30th/31st of a `monthly`-by-date schedule skips months that don't have
  that date; it is never moved to month end. That's already how the engine's `monthly`
  `date` family behaves (see `occurrence-engine.ts` `isEligibleMonthly`) — this slice only
  has to store `month_day` and `month_day_is_last` as the two distinct choices the engine
  already expects, not implement the skip behavior itself.

## Tests (all in `tests/`, matching the existing suites' conventions)

Extend `tests/integration/wellness-medications.test.ts` (and/or a new
`tests/integration/wellness-medication-schedule-v2.test.ts` if that keeps the existing file
a manageable size) to prove, through the real repository + route validation:

1. A medication of each of the six schedule types can be saved, reloaded, and comes back
   meaning the same thing — including a third-Tuesday monthly schedule, an explicit
   last-day-of-month schedule, an every-other-day interval, and an on/off cycle.
2. Each validation rule above rejects bad input with a clear 400 message (mirror the
   existing table-driven style already used for the old picker's validation tests, if one
   exists — otherwise one case per rule).
3. A saved `every_interval` or `monthly` schedule keeps its dose times at the same clock
   time across a daylight-saving change, using its stored time zone (reuse fixtures/timezone
   patterns from `tests/unit/wellness-schedule-engine-parity.test.ts` and the DST tests
   already written for the occurrence engine in #1950).
4. A medication saved under the old three-choice picker's exact request shape (no start
   date, no time zone field, no new columns) still loads unchanged, and
   `computeSchedule`/adherence/export-render still produce exactly the same results for it
   as before this change — a regression test, not just a new-feature test.
5. The migration applies cleanly on a fresh database and on one that already has
   medications in it (this is exercised by the normal migration-runner test path used by
   every other migration in this repo — no special test needed beyond running the suite
   against a seeded database).

## Out of scope (explicitly, per the issue)

- Any change to the medication form / UI. The old three-choice picker's request shape and
  behavior are unchanged.
- The six-type builder form — a later issue.
- Reminder delivery — a later issue.
- Editing an existing medication's schedule (`UpdateMedicationRequest` stays limited to
  non-schedule fields, same as today).
