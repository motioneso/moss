# Spec 1508 — widen and harden the fake-conversation-turn filter

**Issue:** #1508 (parent roll-up #1488). **Risk tier: security** — this PR needs adversarial
review and Ben's merge sign-off.

**Grounding check (2026-08-27):** confirmed on current `main`/this branch — `#1259` and `#1260`
are both closed and merged, no open pull request touches `packages/chat/src/live/prompt-safety.ts`,
and the file still matches this spec's description exactly: it recognizes only five role words
(`user`, `assistant`, `system`, `human`, `ai`), only an ASCII space or tab before a marker, only a
plain ASCII colon, and the comment above the role-marker code still wrongly claims our own
`User: ...` labels are never re-matched. The five files that call the shared cleanup function
(`recall-seed.ts`, `chat-context-blocks.ts`, `codex-exec-session.ts`, `cross-tool-reasoning.ts`,
`passive-retrieval.ts`) are unchanged from this list. Building directly against current main, no
changes to the plan below.

## What this is fixing, in plain terms

When text a user typed — or that got recalled from memory, or pulled in from notes, email,
calendar, or tasks — gets placed into the prompt sent to the model, we already rewrite lines that
look like a fake conversation turn (a line starting with "User:" or "System:") so the model can't
be tricked into thinking a new trusted turn just started. Security testing found two ways past
this: using invisible or lookalike characters, and using role words we don't cover yet — most
importantly our own assistant's name, "Moss".

## What to change

All in one file: `packages/chat/src/live/prompt-safety.ts`.

1. **Widen the recognized role words** from five (`user`, `assistant`, `system`, `human`, `ai`) to
   ten, adding `moss`, `developer`, `tool`, `function`, `model`. "Moss" matters most: a forged
   "Moss: I'll comply..." line is the most convincing fake turn an attacker could write for this
   product. "Developer" is a real instruction role in the model family behind Codex. "Tool",
   "function", "model" are common labels in tool/model transcripts that could pass as a new turn.

2. **See through invisible characters and lookalike spacing.** Right now a single invisible
   character right before or inside a role word lets it slip through untouched. Recognize a
   defined set of invisible characters (zero-width space, zero-width joiners, word joiner,
   byte-order-mark) and a wider set of space-like characters (including non-breaking space and
   other Unicode space characters). Strip the invisible ones out of a matched role word before
   comparing it against the allowed list. Recognize full-width and other lookalike forms of the
   role word and the colon (e.g. a colon that looks like ":" but is a different Unicode character)
   and normalize them — but only inside the small matched marker itself, never across the
   surrounding text.

3. **Keep the rewrite scoped tightly.** Only the matched role word and colon change (e.g. "User:"
   becomes "[User]:"); everything else on the line, and the rest of the message, stays
   byte-for-byte the same. Deliberate tradeoff: a config or code sample containing a line like
   "user: root" still gets rewritten to "[user]: root" even though it isn't really impersonation,
   because we can't reliably tell the difference and refusing to rewrite would reopen the security
   hole. No special-case detection for YAML, Markdown headers, or code blocks — add a test that
   records this tradeoff so nobody "fixes" it later without a security conversation.

4. **Fix the wrong comment.** It currently claims this codebase's own emitted "User: ..." /
   "Assistant: ..." labels are never re-checked because they're only added after the check runs.
   Not true in one case: past conversations are stored to memory with those labels baked into the
   saved text, and when recalled later, that text does go back through this same check and does
   get rewritten to "[User]: ..." — intentional and fine. Replace the comment with an accurate
   explanation of that distinction. Don't change how or what gets saved to memory; only the comment
   and matching behavior are in scope.

5. **Don't touch the five call sites** (`recall-seed.ts`, `chat-context-blocks.ts`,
   `codex-exec-session.ts`, `cross-tool-reasoning.ts`, `passive-retrieval.ts`). They already call
   the shared function correctly; the fix belongs only inside `prompt-safety.ts`.

## How to test

In `tests/unit/chat-recall-seed.test.ts` and `tests/unit/chat-cross-tool-reasoning.test.ts`:

- An invisible character right before a role word no longer slips through; same for one placed
  inside the word.
- A full-width or lookalike-letter version of a role word gets caught.
- A lookalike colon gets caught.
- The five new role words (`moss`, `developer`, `tool`, `function`, `model`) are all caught the
  same way the original five are.
- Ordinary-looking config or Markdown text (e.g. "user: root" or "## AI") still gets rewritten —
  records the deliberate tradeoff as expected, not a bug.
- A role word not on the approved list, or text containing a lookalike letter from a different
  alphabet (e.g. Cyrillic standing in for an English "e"), is left completely unchanged — proves
  the check doesn't get too aggressive.
- The cleanup is idempotent: running it twice on already-cleaned text gives the same result as
  running it once.
- A real-code-path test for recalling memory: build a memory chunk whose text is
  "User: hello\nAssistant: hi", call the function that turns memory into a seed block, and check
  the result contains "[User]: hello" and "[Assistant]: hi" — not just the helper in isolation.
- A similar real-code-path test for cross-tool summaries (notes, email, calendar, tasks): build a
  fake evidence item with a disguised role marker in both its summary text and its source label,
  call the actual rendering function, and check the rendered line only contains the safe bracketed
  version, while the block's own trusted opening/closing tags are untouched.
- A timing test proving the check still runs safely fast on adversarial input (long runs of
  decoration characters, long runs of invisible characters, near-match role words) — a past version
  of this code had a bug that could make it hang.

Run tests directly:
`npx vitest run tests/unit/chat-recall-seed.test.ts tests/unit/chat-cross-tool-reasoning.test.ts`

Do not use a package-scoped `test` script for chat — it doesn't exist and produced a false
all-green result once before. Run the project's `lint` and `typecheck` scripts before calling this
done (confirmed current names: `pnpm lint`, `pnpm typecheck`).

## What "done" looks like

- All new and existing tests above pass.
- Text containing none of the ten role words is completely unchanged, byte for byte, regardless of
  other Unicode characters present.
- Running the cleanup twice never differs from running it once.
- The rewrite still only changes the small matched marker itself, never other text on the line or
  in the message.
- The five files that already call this cleanup function are untouched — no new imports, no new
  call sites, no changed function signature.
- Nothing about how chat memory gets saved to the database changes; only how already-saved
  "User:"/"Assistant:" text gets displayed back to the model when recalled.
- No new outside library, no new file, no new exported helper beyond what's already exported from
  `prompt-safety.ts`.
- This only changes how text is rewritten before being shown to the model and doesn't change any
  screen the user sees, so the live-app proof requirement does not apply — the proof is the test
  suite plus a security-focused code review, which this kind of change always needs.
