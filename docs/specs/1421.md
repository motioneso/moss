# Spec: route job-fit scoring to the cheap model tier (issue #1421)

## What is changing

Job-fit scoring (the feature that scores one job posting against a person's resume) currently
asks the AI router for the most expensive tier of model on every call. That tier is not needed
for this job: it is a small, structured, one-shot answer, and another feature in the app (email
triage) already gets good results asking for the cheap tier for a similarly-sized job.

The fix is a one-line change in the job-search module's scoring code
(`external-modules/job-search/src/worker/stages/score.ts`): the request to the AI router will ask
for the cheap tier instead of the expensive one. No provider or model name is named anywhere —
the code only ever says which tier it wants, and the router (elsewhere in the app) decides which
actual model that maps to for this install. This keeps the "never hardcode a model" rule intact.

A comment near the top of that file currently describes model call timing "on the reasoning
tier" (the expensive one) to explain a wait-time safety margin. That comment will be corrected to
say what tier scoring now actually uses, so it does not describe a setup that no longer exists.

## What is NOT changing

- The scoring logic itself: the prompt, the schema, the fit/want scores, and how they are stored.
- Any other feature that asks the router for a tier (email triage, finance categorizing, the food
  estimator, and so on) — this change only touches job-fit scoring.
- The user-facing product: nobody sees a different screen or a different kind of answer. The
  scores should look the same, just produced more cheaply.

## How this will be verified

1. **Automated test**: a unit test on the scoring code asserts the AI request now asks for the
   cheap tier, not the expensive one. (Today no test pins this at all — the assertion is new.)
2. **Existing test suite**: the job-search unit and integration tests for scoring keep passing
   unchanged, since the prompt, schema, and scoring math are untouched.
3. **Spot-check for drift** (per the issue's acceptance criteria): before merging, re-run scoring
   for roughly 20 postings that already have a score on file, using the cheap tier, and compare
   the new fit/want scores against the old ones. The bar is "no material drift" — scores landing
   in noticeably different bands would be a sign the cheap tier is not good enough for this job.
   This is a manual check recorded on the pull request, not an automated test (there is no
   dev-database-touching test allowed outside the verify-gate process, and this check needs real
   scored postings to compare against).

## Why this is safe

The router already lets any feature ask for a tier without naming a model, so this change only
flips which tier one caller asks for — it does not touch how the router itself decides what model
serves that tier, and it does not touch any other caller.
