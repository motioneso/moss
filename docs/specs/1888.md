# Spec — #1888: ask Moss for a module in chat, and get a plan back

## What the change is

Today the Workshop module declares no assistant tools at all, so Moss cannot see the module-build
capability. The build engine (`startModuleBuild`) exists and works, but nothing calls it outside
its own unit test. This change makes the capability reachable from chat.

After this change: open the chat drawer, say "build me something that shows today's videos from
these two channels", Moss asks the questions it needs to, and once it can describe the thing
concretely it comes back with a plan card — what it reaches out to, what it keeps, when it runs,
roughly what it costs — with "Build it" and "Not yet" buttons. "Build it" starts the build.

Admins only, matching the Workshop's existing `workshop.view` permission.

## How it hangs together

**1. The tool.** Add one entry to the Workshop manifest's `assistantTools`:

- name `workshop.buildModule`, `permissionId: "workshop.view"`.
- `risk: "write"`, `executionPolicy: "auto"`, `selfOperationGrant: "granted_at_install"`, with a
  new action family (`module_builds`, defaultTier `ask_each_time`, allowedTiers
  `ask_each_time` / `trusted_auto` / `always_confirm`).
- `requiresServices: ["moduleBuildStart"]`.
- Input: `description` (string, required) and `conversationExcerpt` (string, optional).

Why `granted_at_install` and not a confirm-style grant: the human gate for this action is the
plan card, and Ben ruled the plan card *is* the approval moment. A generic Approve/Deny card
raised before the plan is even written would be a second, emptier gate in front of the real one.
`confirm_always` is also structurally unavailable — `PLANNED_CONFIRM_ALWAYS_TOOLS` in
`packages/ai/src/gateway/self-operation.ts` is a closed five-name allowlist.

Two consequences of that choice that must be honored:

- `risk: "write"` is required for the plan to reach the browser at all. The gateway only emits an
  `action_result` record onto the chat stream for non-read tools
  (`packages/ai/src/gateway/gateway.ts`, the `if (found.tool.risk !== "read")` guard). A read tool
  would run silently and the card would never render.
- Workshop is a `required` module, so it never traverses an enable request and
  `grantSelfOperationForModule` never fires for it. `selfHealGrantedAtInstallTier` covers exactly
  this case (see its comment referencing #1311) and is already wired at
  `packages/chat/src/gateway-services.ts:262`. No new install-time plumbing needed.

**2. The tool description does the requirements-gathering.** Per Ben's 2026-08-23 ruling, Moss
holds a real conversation first. The description instructs Moss not to call the tool until it can
state concretely what the module does, what it reaches, what it keeps and when it runs — and to
ask about the empty case and about what a click does. That is prompt text in the manifest, not
tool logic.

**3. The service.** `moduleBuildStart` is built by the composition host in
`packages/chat/src/gateway-services.ts` (`buildChatToolServices`), the same way `notesSync` and
`calendarWrite` are. It binds `startModuleBuild`'s six deps to the real repository, the real
plan writer and the real queue. Workshop declares only the narrow interface; it constructs
nothing. This keeps `@moss/workshop` free of a dependency on `@moss/ai`, `@moss/db` and
`@moss/jobs`.

The service also enforces admins-only: it reads the actor's instance-admin flag and refuses a
non-admin call. The chat drawer's tool list is not admin-filtered today
(`createActiveModulesResolver` filters on enable/disable rows only, never on admin), so the check
has to live in the service. This is the security-relevant line of this change.

**4. The card.** The tool returns the plan plus `buildId` and `awaitingApproval` in its
`ToolResult.data`. The gateway already forwards `result.data` onto the chat stream, and
`TranscriptRecord.result` already carries it to the browser
(`apps/web/src/chat/use-chat-stream.ts`). So `RecordRow` in
`apps/web/src/chat/message-row.tsx` gains one branch: when an `action_result` record names this
tool and its result parses as a plan, render `PlanApprovalCard` instead of the one-line
"Changed / Not changed" row. When `awaitingApproval` is false (the "stop asking me" setting is
on, so the build already started), render the card with `superseded` set — it is a record of what
was agreed, not a question.

Parsing is defensive: anything that does not match the five-field plan shape falls through to the
existing one-line rendering rather than throwing inside the transcript.

**5. The buttons.** "Build it" posts to a new Workshop route,
`POST /api/workshop/builds/:buildId/approve`, which calls `approveModuleBuildPlan` with the same
deps. `approveModuleBuildPlan` is already ownership-scoped — a build that does not exist and a
build owned by someone else both raise the same error, so the route cannot be used to probe for
other people's builds. The route additionally requires instance admin. "Not yet" is client-side
only: the card marks itself superseded and the conversation continues.

## Guardrails this must not break

- `tests/unit/self-operation-module-build.test.ts` and
  `tests/integration/mcp-gateway-self-operation.test.ts` stay green. In particular
  `start-build.ts` must keep containing no reference to installing or shipping a module — do not
  add one while wiring.
- The seven server-owned exclusion categories in `packages/ai/src/gateway/self-operation.ts` are
  not touched. `workshop.buildModule` does not fall under any of them and does not need to.
- `assertBuiltInSelfOperationManifests` runs at API boot (`apps/api/src/server.ts:672`). The new
  tool and family must satisfy it: unique tool name across all built-in modules, family resolves
  within Workshop, family default is `ask_each_time`.
- No secret, credential or private content goes into the tool result, the queue payload or the
  plan.

## How it will be verified

Unit tests, each written before its code:

1. The Workshop manifest passes `assertBuiltInSelfOperationManifests` alongside every other
   built-in manifest (extends the existing startup test).
2. The `moduleBuildStart` service refuses a non-admin actor and does not create a build row.
3. The service, for an admin, calls `startModuleBuild` and returns the plan, the build id and the
   awaiting-approval flag.
4. `RecordRow` renders `PlanApprovalCard` for an `action_result` naming this tool with a
   well-formed plan; renders the ordinary one-line row when the result is malformed or names
   another tool; renders the card as superseded when the build already started.
5. The approve route rejects a non-admin, and rejects a build owned by someone else with the same
   error it gives for a build that does not exist.
6. The existing self-operation boundary tests still pass unchanged.

Live proof on the dev instance, recorded on the PR (this is a user-facing path, so the live-path
gate applies): in the real chat drawer, describe a module, answer Moss's questions, see the plan
card render, press "Build it", and observe the build row move to `building`.

## Out of scope

- Loosening the seven exclusion categories. If that turns out to be needed, raise it rather than
  doing it here.
- Any Workshop page work — the workshop page still renders against empty lists (#1752/#1753).
- Installing or shipping a built module. Those stay separate human actions.
