# Spec: groundwork so every schedule type can carry a start date, a reminder toggle, and be edited (#1968)

Piece 1 of 4, re-sliced from #1965. Database and server only — no form work. Pieces 2, 3 and 4
depend on this landing first.

## What exists today (verified on this branch, at 5a4871f1b)

1. **A start date is only storable for two of the six schedule types.** The constraint
   `medications_v2_fields_scoped_to_v2_types`, added in
   `packages/wellness/sql/0194_wellness_medication_schedule_v2.sql`, forces `schedule_start_date`
   and `schedule_end_date` to be NULL unless `frequency_type` is `every_interval` or `monthly`.
   The route mirrors this: `parseCreateMedicationBody` in `packages/wellness/src/routes.ts` only
   requires/validates `startDate` inside the `every_interval` and `monthly` branches, and
   explicitly rejects `startDate`/`endDate` for `as_needed`.
2. **There is no reminder on/off field.** `app.medications` has no such column, `MedicationsTable`
   in `packages/db/src/types.ts` has no such property, and `medicationDtoSchema` in
   `packages/shared/src/wellness-api.ts` has no such field. The only trace of reminders anywhere
   is a designed-but-unused queue name (`WELLNESS_MEDICATION_REMINDER_QUEUE`) with no worker.
3. **A saved schedule cannot be edited.** `updateMedicationRequestSchema` accepts only `name`,
   `dosage`, `form`, `active` and `notes`, and `WellnessRepository.updateMedication` carries the
   comment "schedule_times is NOT updatable in this slice". Changing a schedule today means
   deleting the medication and creating a new one.

## What this change does

### 1. New migration: `packages/wellness/sql/0196_wellness_medication_start_date_reminders.sql`

Additive and re-runnable, like 0194. Never edits an applied file.

- Replace `medications_v2_fields_scoped_to_v2_types` with
  `medications_v2_shape_fields_scoped_to_v2_types`, which scopes only the shape-describing
  columns (`interval_unit`, `interval_count`, `month_kind`, `month_day`, `month_day_is_last`,
  `month_weekday_position`, `month_weekday`) to `every_interval` and `monthly`.
  `schedule_start_date` and `schedule_end_date` drop out of that scope, so every schedule type can
  carry them. The old constraint is dropped by name with `IF EXISTS`.
- `medications_schedule_end_not_before_start` (already unscoped) keeps guarding the ordering.
- Add `reminders_enabled boolean NOT NULL DEFAULT false`. Default false, deliberately: no reminder
  delivery exists yet, so no existing medication should be silently marked as expecting one. The
  builder form (piece 3) sends an explicit value for new medications and is free to default its
  own control to on.
- Add `medications_as_needed_no_reminders`: an `as_needed` medication must have
  `reminders_enabled = false`. A PRN medication has no scheduled time, so there is nothing a
  reminder could fire on. This matches how 0083 already keeps `as_needed` free of every other
  scheduling field.

### 2. Database types (`packages/db/src/types.ts`)

Add `reminders_enabled: ColumnType<boolean, boolean | undefined, boolean>` to `MedicationsTable`.

### 3. Shared contract (`packages/shared/src/wellness-api.ts`)

- `medicationDtoSchema`: add required `remindersEnabled: { type: "boolean" }`.
- `createMedicationRequestSchema`: add `remindersEnabled` (boolean or null).
- `updateMedicationRequestSchema`: add `frequencyType`, `remindersEnabled`, and the full set of
  schedule fields the create request already accepts (`timesPerDay`, `intervalHours`, `weekdays`,
  `scheduleTimes`, `cycleDaysOn`, `cycleDaysOff`, `cycleAnchorDate`, `intervalUnit`,
  `intervalCount`, `startDate`, `endDate`, `monthKind`, `monthDay`, `monthDayIsLast`,
  `monthWeekdayPosition`, `monthWeekday`), with the same value ranges. `additionalProperties`
  stays `false`, so this is a widening: today's five-field update requests are unaffected.
- Add `MedicationDto.remindersEnabled` to the TypeScript type alongside the JSON schema.

### 4. Route validation (`packages/wellness/src/routes.ts`)

- Extract the schedule half of `parseCreateMedicationBody` into one shared function
  (`parseMedicationScheduleBody`) used by both create and update, so an edit is validated by
  exactly the same rules as a create. This is the reason edits were blocked before; sharing the
  code removes the reason.
- `startDate` / `endDate` are accepted for **every** schedule type, not just the two new ones.
  They stay **required** for `every_interval` and `monthly` (those two count their repeat from the
  start date) and stay optional for the other four.
- Remove `startDate` and `endDate` from the list of fields rejected for `as_needed`. Everything
  else on that list still stays rejected.
- Validate both dates as a real `YYYY-MM-DD` calendar date for every type, returning a 400 rather
  than letting a malformed value reach Postgres and surface as a 500.
- Apply the "end date must not be before start date" check for every type, not only inside the two
  new-type branches.
- `remindersEnabled` must be a boolean if present, and must not be true for `as_needed` (400).
- **Editing a schedule is all-or-nothing.** If an update request carries `frequencyType`, it must
  carry the complete schedule for that type and is validated exactly like a create. If it carries
  any schedule field *without* `frequencyType`, it is rejected with a 400 naming `frequencyType`.
  This rules out the half-changed state where a leftover column from the previous schedule type
  trips a database check and surfaces as a 500.
- The PATCH handler resolves the caller's time zone (the same `resolveRouteTimeZone` call the POST
  handler already makes) and passes it to the repository, so an edited schedule records a real
  time zone the same way a created one does.

### 5. Repository (`packages/wellness/src/repository.ts`)

- `UpdateMedicationInput` gains an optional `schedule` sub-object (the same shape the create input
  uses) and an optional `remindersEnabled`.
- `updateMedication(scopedDb, id, input, timeZone)`: when `input.schedule` is present, write
  **every** schedule column explicitly, including setting the ones that do not apply to the new
  type back to NULL (and `month_day_is_last` back to false), and refresh `time_zone`. When it is
  absent, behaviour is exactly as today. Row scoping is unchanged: the update runs inside the
  actor's data context, so row-level security still restricts it to the owner's own rows.
- Delete the stale "schedule_times is NOT updatable in this slice" comment.

### 6. Serializer (`packages/wellness/src/serialize.ts`)

Map `reminders_enabled` to `remindersEnabled`.

### 7. Honouring the stored start and end dates (`packages/wellness/src/schedule.ts`)

A start date nothing reads is not a start date, and without this an adherence count would report
missed doses for days before the medication began. `computeSchedule` gains a per-medication
window check: if the requested day is before `schedule_start_date`, or after `schedule_end_date`,
that medication produces no slots for that day.

This is done as a day-level window clamp rather than by feeding the start date into the schedule
engine's anchor, deliberately: for a cycle schedule the anchor is `cycle_anchor_date` and it sets
which days are "on" days, so moving it would shift the whole on/off pattern. Clamping the day
leaves every family's existing repeat maths untouched. Medications with no stored dates (which is
every medication today, apart from the two new types) behave exactly as before.

## Validation rules, in one place

| Rule | Applies to | Response when broken |
| --- | --- | --- |
| `startDate` required | `every_interval`, `monthly` | 400 |
| `startDate` / `endDate` accepted | all six types | — |
| `startDate` / `endDate` must be a real `YYYY-MM-DD` date | all | 400 |
| `endDate` must not be before `startDate` | all | 400 |
| `remindersEnabled` must be a boolean | all | 400 |
| `remindersEnabled` must not be true | `as_needed` | 400 |
| Any schedule field present without `frequencyType`, on update | all | 400 |
| Every existing per-type rule (times, weekdays, cycle, monthly shape) | unchanged | 400 |

## Tests

New file `tests/integration/wellness-medication-editing.test.ts`, following the conventions of the
existing `tests/integration/wellness-medication-schedule-v2.test.ts`:

- A start date saves and reloads for each of the six schedule types, including `as_needed`.
- `remindersEnabled` saves, reloads, and defaults to false when the field is omitted.
- `remindersEnabled: true` on an `as_needed` medication is rejected with a 400.
- An `every_interval` schedule can be edited into a `monthly` one through PATCH, reloads as the
  new schedule, and the columns belonging to the old type come back empty.
- A `monthly` schedule can be edited into an `as_needed` one and back.
- An edit with a schedule field but no `frequencyType` is rejected with a 400.
- An edit with a `frequencyType` but a missing required field for that type is rejected with a 400.
- An edit that only changes `name` still works, unchanged.
- One user cannot edit another user's medication (404, not a 200), proving row-level security
  still covers the widened update path.
- A malformed `startDate` is rejected with a 400, not a 500.

Added to `tests/unit/` (or the nearest existing schedule unit suite):

- A daily medication with a start date in the future produces no slots before that date.
- A daily medication with an end date in the past produces no slots after that date.
- A cycle medication with a start date later than its cycle anchor keeps the same on/off pattern —
  the clamp hides early days, it does not shift the phase.

## Out of scope

- The six-choice builder form, the preview sentence, and the edit screen — pieces 2, 3 and 4.
- Reminder delivery. The toggle is stored and read back; no worker sends anything.
- Re-anchoring dose logs recorded against a previous schedule. Editing a schedule leaves old logs
  in place; they simply no longer line up with a slot.
- Adding the reminder toggle to the wellness data export.

## How this is verified

- The tests above, plus the full local gate, plus CI.
- Live proof on the dev instance: apply the migration, then through the running server create a
  daily medication with a start date and the reminder toggle on, read it back, edit it into a
  monthly schedule, read that back, and confirm a start date in the future produces no dose slot
  for today.
