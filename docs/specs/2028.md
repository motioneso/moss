## Short version

The one-line change this issue describes (drop the note that keeps Google out of the
default-chat-model list) is correct but is roughly five percent of the work. Every other piece of
the Google chat path was written for a **different Google tool** - the Antigravity command-line
tool, whose command is `agy` - and none of it runs against the tool that #2026 actually pinned and
#2027 actually signed you into, which is Google's Gemini CLI, command `gemini`.

Proof, not inference. I downloaded the exact pinned package (`@google/gemini-cli` at 0.57.0, the
version in the catalog) into a scratch folder outside the repo and ran it:

```
$ node bundle/gemini.js --print --conversation abc -p hi
Unknown arguments: print, conversation
```

The chat engine's launch line is `agy --dangerously-skip-permissions --conversation <id> --print
--log-file <path> "<prompt>"`. Of those, the command name is wrong and four of the five flags do
not exist. So today a founder who installs Gemini, signs in, and sends a message gets nothing back.

Everything below is grounded in that run plus the code on `main` at `23f1bc193`.

## What is already done, and needs no work

- Installing it works. `packages/cli-runner/src/catalog.ts` pins version 0.57.0 with a committed
  lockfile and records the command name as `gemini`.
- Signing in works. `packages/cli-runner/src/login-adapters.ts` has the adapter, and the readiness
  check in `packages/chat/src/live/provider-probe.ts` already runs the real `gemini --prompt`.
- The "is it on the machine" check already accepts the `gemini` name
  (`packages/ai/src/cli-availability.ts`).
- Settings already offers Google in the admin provider list
  (`apps/web/src/settings/settings-ai-admin-pane.tsx:69`), so no new UI is needed. Once a default
  chat model exists for it, it appears as a pickable chat model the same way Claude and Codex do.
- New provider rows default to the one-shot mode (`packages/ai/src/repository.ts:391`), and the
  engine picker sends one-shot Google sessions to `AgyPrintChatEngine`
  (`packages/chat/src/live/engine-selection.ts:89`). So the one-shot engine is the path that has to
  work; the multiplexer path is a side road.

## What is broken, with the real command's behaviour beside it

These are the real flags of the pinned tool, read from `gemini --help` on the pinned version:

| The code uses                    | The pinned tool actually offers                                                       |
| -------------------------------- | ------------------------------------------------------------------------------------- |
| command `agy`                    | command `gemini`                                                                      |
| `--print`                        | `-p, --prompt <text>`                                                                 |
| `--conversation <uuid>`          | `--session-id <uuid>` to start one, `--resume <uuid or index>` to continue            |
| `--log-file <path>`              | nothing; use `-o, --output-format` (`text`, `json`, `stream-json`) on standard output |
| `--dangerously-skip-permissions` | `-y, --yolo` or `--approval-mode default\|auto_edit\|yolo\|plan`                      |
| `--mode accept-edits`            | `--approval-mode auto_edit`                                                           |
| `--sandbox` (as used)            | `-s, --sandbox` exists and is a plain on/off switch                                   |

Broken call sites:

1. `packages/chat/src/live/agy-print-chat-engine.ts:62` - the one-shot launch line. Wrong command,
   four non-existent flags.
2. `packages/chat/src/live/cli-launch-commands.ts:167` - the multiplexer launch line. Same problem.
3. `packages/module-registry/src/chat-multiplexer.ts:288` - the onboarding "is this provider ready"
   check runs `agy auth status`. The pinned tool has no `auth` command at all (its only
   subcommands are `mcp`, `extensions`, `skills`, `hooks`, `gemma`), so this check can only ever
   report an error. #2027 already solved the same problem correctly in `provider-probe.ts`; this
   second copy was missed.
4. `packages/ai/src/adapters/tmux-bridge.ts:130` - the transcript folder is
   `~/.gemini/antigravity-cli/brain`, which is the Antigravity tool's storage. The pinned tool
   stores conversations somewhere else entirely (below).
5. `packages/ai/src/cli-availability.ts:23` - the primary command name for Google is still `agy`.
   Harmless today because `gemini` is accepted as an alternative, but it is the last place that
   still calls the primary name wrong, and leaving it invites the next reader to copy it.

## Where the pinned tool really stores a conversation

Read out of the pinned package's own storage code:

- Global folder `~/.gemini`.
- A registry file `~/.gemini/projects.json` maps each working folder to a short id.
- Conversations for that folder live in `~/.gemini/tmp/<short id>/chats/` as `.json` files,
  alongside `logs/` and `tool-outputs/`.
- Prompt history lives in `~/.gemini/history/<short id>/`.

Two consequences.

First, the transcript path the engine reads today
(`<root>/<uuid>/.system_generated/logs/transcript_full.jsonl`) will never exist. Nor will the shape
the reader expects: the file-per-line format documented at
`packages/ai/src/adapters/transcript-reader.ts:49` does not match what 0.57.0 writes.

Second, the private-data cleanup is currently pointed at the wrong folder, so **a real conversation
would be left behind on disk after the session ends**. That is the part of this issue with a
privacy consequence, and it is not optional.

## The plan

### Decision 1 - read the answer from standard output, not from the tool's own conversation file

Recommended: run the one-shot turn as
`gemini -p "<prompt>" --output-format stream-json` with standard output and standard error
redirected to a file the engine owns inside the session's own working folder, and parse that file.

Why this rather than tailing `~/.gemini/tmp/<short id>/chats/*.json`: the short id comes out of a
registry file, not a formula, so the engine cannot work out the path without reading and parsing
someone else's registry and racing its writes. A file we redirect into is deterministic, is already
inside the folder the session cleans up, and matches how the Claude one-shot engine is fed. The
event names on that stream are `init`, `message`, `tool_use`, `tool_result`, `error`, `result` -
one JSON object per line.

The builder must confirm the exact field names on a real run (I could read the names of the event
types out of the package but not their payload shape without a live sign-in). Do that first, in one
throwaway run against the live dev instance, before writing the parser.

### Decision 2 - continuing a conversation

Mirror what the Claude one-shot engine already does at
`packages/chat/src/live/claude-print-chat-engine.ts:254`: generate a UUID at launch, pass
`--session-id <uuid>` on the first turn and `--resume <uuid>` on every later turn. The pinned tool
has both flags with exactly those meanings. Confirm on the live run that a second turn really does
remember the first - if it does not, say so on the pull request rather than shipping a chat that
silently forgets.

### Decision 3 - the automatic-approval conflict, which needs resolving before anything else works

`packages/chat/src/live/cli-launch-commands.ts:232` writes `security.disableYoloMode: true` into
the per-session settings file. That setting is real in the pinned tool and it refuses the
auto-approve mode. But a headless one-shot turn has nobody to answer an approval prompt, so any
tool call will stall or fail.

The builder picks one and writes down why in the pull request:

- `--approval-mode auto_edit` plus leaving that setting on - approves edits, still prompts for
  shell commands, so shell tools are effectively unavailable in chat; or
- drop `security.disableYoloMode` from the written settings and pass `--approval-mode yolo` -
  matches what the Claude and Codex one-shot paths already do, and the session runs in its own
  throwaway folder.

The second is more consistent with the rest of the codebase. It is a security-shaped choice, so
state it plainly on the pull request rather than burying it in a commit.

### Files to change

`packages/chat/src/live/agy-print-chat-engine.ts` - the bulk of the work. New launch line, new
output parsing, new session-id handling, new cleanup. Rename the file and the class to say Gemini
rather than Agy; the current name refers to a tool this code will no longer talk to. Update the
imports in `engine-selection.ts` and the test file.

`packages/chat/src/live/private-transcript-cleanup.ts` - replace the Antigravity conversation-id
capture and folder purge with a purge that removes, for the session's short id: the folder
`~/.gemini/tmp/<short id>`, the folder `~/.gemini/history/<short id>`, and that folder's entry in
`~/.gemini/projects.json`. Look the short id up in that registry, keyed on the session's working
folder. Follow the existing rule in this file that a purge which cannot confirm it removed
everything throws rather than reporting success.

`packages/ai/src/adapters/tmux-bridge.ts` - point the transcript root at `~/.gemini/tmp` and expose
whatever the new cleanup needs. Rename away from `agyPrintTranscriptRoot`.

`packages/ai/src/adapters/transcript-reader.ts` - replace the Antigravity record mapping (line 361
onward) and the format note at line 49 with the real stream shape from Decision 1.

`packages/chat/src/live/cli-launch-commands.ts` - fix the multiplexer launch line (`gemini`, real
flags) and settle the approval question from Decision 3. If the multiplexer path is not going to be
exercised live, say so in a comment; do not leave a line that names a command nothing installs.

`packages/module-registry/src/chat-multiplexer.ts:288` - replace `agy auth status` with the same
approach `provider-probe.ts` already uses.

`packages/ai/src/cli-availability.ts:23` - make `gemini` the primary command name.

`packages/ai/src/auto-register.ts:77` - the change the issue actually asks for: replace the note
with a `google` entry alongside Claude and Codex, using the same "let the tool pick its own model"

`packages/ai/src/model-discovery.ts:48` - add a short list of Gemini model names so a founder who
wants to pin one has something to pick, and update the note at line 45. Confirm the names against
the live tool rather than from memory.

### Tests

Existing tests to update: `tests/unit/agy-print-chat-engine.test.ts` (rename with the file),
`tests/unit/chat-multiplexer-provider-check.test.ts`, and any auto-register test that asserts

New tests worth having:

  it first.
- A guard test that no file under `packages/` builds a command line starting with `agy`. Cheap,
  and it stops this coming back.
- Parsing a recorded sample of the tool's real streamed output into one reply plus its activity
  lines. Record the sample from the live run; do not invent it.
- The cleanup removes all three locations and refuses to report success when it cannot.

Gate: `pnpm verify:foundation` through the `verify-gate` skill. Never run it unscoped.
