SPEC

Piece 2 of the Moss self-diagnostics spec (#1586). Build the machinery: one platform diagnostics
service, a seam that lets a module publish its own safe diagnostic view, the news provider as the
first user of that seam, and a bounded reader for deployed application source. No assistant tools
and no end-to-end conversation test - that is piece 3 (#2032).

Piece 1 (#2030) is merged as PR #2045, so the news refresh history this depends on is on main.

## What exists today

Everything below is on main at 15c79ddb7.

**Read tools cannot reach write-capable services.** The assistant gateway keeps two separate
service bags. Write tools get a per-tool subset of `toolServices`; read tools get
`readToolServices` and nothing else. The split is in
packages/ai/src/gateway/gateway.ts, method `servicesFor` (around line 561), and the comment there
explains that this is the structural reason a read tool can never bypass the approve step. The two
bags are assembled in packages/chat/src/gateway-services.ts, function
`buildChatGatewayDependencies` (`toolServices` at line 172, `readToolServices` at line
193). This is the boundary your last negative test asserts against; do not weaken it.

**The app map** is a read service built at the composition root, in
packages/module-registry/src/index.ts around line 2570, from an artifact loaded at
`APP_MAP_ARTIFACT_PATH` (line 418). The service itself is packages/settings/src/app-map.ts. It
already does the two things you need to copy: it resolves the actor's active modules, and it hides
admin-scope items from non-admin users by reading `is_instance_admin` through
`SettingsRepository.getUserById`. It also exposes `getBuildInfo()`, which is the deployed version
and build id. packages/settings/src/app-map-tool.ts is the matching read tool - useful as a shape
reference, but do not add a tool in this piece.

**Safe host diagnostics** already exist and are already sanitized. packages/settings/src/
host-diagnostics.ts has `buildHostDiagnostics` (explicit allowlisted field-by-field construction)
and `assertDiagnosticsSafe` (refuses to emit any string containing a connection URL or the name of
a known secret environment variable). The runtime facts come from a provider built in
apps/api/src/server.ts around line 474. The admin-only HTTP route that assembles the whole thing -
database ping, multiplexer setting, latest-release row - is packages/settings/src/
host-diagnostics-routes.ts. That assembly is currently inline in the route handler, which matters;
see task 3.

**Actor-scoped structured errors** are `AiRepository.listRecentErrors`
(packages/ai/src/repository.ts around line 2065) over `app.moss_error_log`. The table is owner-only
with FORCE row-level security (packages/ai/sql/0145_jarvis_error_log.sql). The projection that is
already considered safe to show a model is in packages/ai/src/error-tools.ts - occurred at,
feature, operation, error category, retryable, user message, internal summary, request id.

**The action audit** is `AiRepository.listActionAuditLog` (same file, around line 2004) over
`app.moss_action_audit_log`, also owner-only with FORCE row-level security
(packages/ai/sql/0127_jarvis_action_audit_log.sql).

**Module provider seams already exist** and you should copy one rather than invent a shape. The
manifest already carries `focusSignal`, `proactiveMonitor`, `personContextProvider` and
`dataLifecycle` (packages/module-sdk/src/index.ts, `MossModuleManifest` around line 624). The
generic collector is `focusSignalProvidersFor` in packages/module-registry/src/index.ts around
line 2381, and the generic aggregator is `aggregateFocusSignals` in
packages/module-sdk/src/index.ts around line 344. Read that aggregator carefully before writing
yours: it runs every provider in its own database context on purpose (a shared transaction would
serialize the queries onto one connection and let one provider's failed transaction poison every
other provider), it races each provider against a deadline, it treats a throw or a malformed
return as "no signal", and it reports the drop with the module id and the error's name only -
never the message, never the payload.

**Path containment** has a precedent in packages/vault/src/vault-path.ts: resolve, then require
the result to be the root or start with the root plus a separator. Note what it does not do - it
never calls `realpath`, so a symlink inside the root pointing outside it would pass. Your reader
must not have that hole.

**The deployed runtime really does contain the source.** The Dockerfile's runtime stage is `FROM
build`, and its comments state that the full workspace source, `packages/*/sql` and
`infra/postgres` are present at their repo-relative paths under `/app` because the migration
runner needs them. So a source reader needs no new artifact and no new dependency. It also means
`node_modules`, `dist`, `.git` and the built web assets are sitting right next to the source, so
the exclusion list is doing real work.

**News freshness** is `NewsPersonalizationRepository.readRefreshDiagnostics`
(packages/news/src/personalization-repository.ts, line 578), returning `NewsRefreshDiagnostics`
(same file, line 49): the live state and failure kind, the last requested / attempted / succeeded
/ failed timestamps and last failure kind, the requested and compiled generation, the snapshot
compiled and expiry times, the snapshot age in seconds, and an item count. It deliberately never
selects the article payload. That is exactly what the news provider should project.

## Where the code goes, and why

The dependency graph constrains this. `@moss/ai` already depends on `@moss/settings`, so settings
cannot import ai. `@moss/module-registry` depends on everything and is the composition root. So:

1. The seam types and the generic aggregator go in **`@moss/module-sdk`** - no new dependency for
   anyone, and it sits beside the three provider seams it copies.
2. The bounded source reader goes in **`@moss/settings`**, next to host diagnostics. It needs only
   `node:fs` and `node:path`, so it adds no package dependency.
3. The platform diagnostics service goes in **`@moss/ai`**, which can already import settings and
   already owns the error log and audit reads.
4. The news provider goes in **`@moss/news`**, attached to its own manifest.
5. Composition happens in **`@moss/module-registry`**, beside the app map service.

Do not create a new workspace package. It would need entries in package.json, tsconfig.json and
vitest.config.ts, and buys nothing here.

## Tasks

Each task should commit green on its own.

### Task 1 - the seam, in module-sdk

New file `packages/module-sdk/src/diagnostics.ts`. Export it explicitly by name from
packages/module-sdk/src/index.ts, the way `workflow.ts` and `external-module.ts` are exported
there - a named list, not `export *`, because widening the SDK's public surface should be visible
in review. A separate file also keeps index.ts under the 1000-line file size gate.

The provider a module implements:

    export interface ModuleDiagnosticProvider {
      readonly domain: string;      // "news"
      readonly providerId: string;  // "news.refresh"
      observe(
        scopedDb: unknown,
        ctx: { readonly actorUserId: string; readonly requestId: string }
      ): Promise<ModuleDiagnosticObservation | null>;
    }

`scopedDb` is typed `unknown` here for the same reason it is on every other seam: module-sdk has no
database dependency, and the owning module narrows it with `assertDataContextDb`.

What a provider returns:

    export interface ModuleDiagnosticObservation {
      readonly domain: string;
      readonly providerId: string;
      readonly observedAt: string;   // ISO 8601
      readonly status: "ok" | "degraded" | "failed" | "unknown";
      readonly summary: string;      // one plain sentence, hard-capped at 300 characters
      readonly remediationActionId?: string;
      readonly facts?: Readonly<Record<string, string | number | boolean | null>>;
    }

**`facts` is one field beyond the five the issue lists, and it is deliberate.** Without it a
provider can only produce a sentence, and piece 3 has to go back and read news state directly to
cite a timestamp - which is the module-isolation problem this seam exists to prevent. Keep it
tight: scalars only, at most 12 keys, string values capped at 120 characters, and the aggregator
drops any observation that breaks those caps. No nested objects, no arrays, no free text from
outside the platform.

Also in this file, the aggregator:

    export async function aggregateModuleDiagnostics(
      providers: readonly { moduleId: string; provider: ModuleDiagnosticProvider }[],
      runInContext: <T>(work: (scopedDb: unknown) => Promise<T>) => Promise<T>,
      ctx: { actorUserId: string; requestId: string },
      options?: { onProviderError?: (moduleId: string, errorName: string) => void }
    ): Promise<ModuleDiagnosticObservation[]>

Mirror `aggregateFocusSignals` exactly: a fresh context per provider, a deadline per provider, a
throw or a malformed return becomes no observation, and the drop is reported with the module id and
the error's name only. Use a 2000ms deadline rather than focus's 250ms - focus is on a page render
path, this is on a conversation path where a slow honest answer beats a fast empty one.

Then add `readonly diagnosticsProvider?: ModuleDiagnosticProvider;` to `MossModuleManifest`, and -
this is easy to miss - add `"diagnosticsProvider"` to `FORBIDDEN_FIELDS` in
packages/module-registry/src/external/validate.ts (around line 61), next to `focusSignal` and
`proactiveMonitor`. A downloadable module runs in a separate worker and cannot hand a function
across that boundary, so a manifest that declares one must be rejected.

### Task 2 - the bounded source reader, in settings

New file `packages/settings/src/source-inspector.ts`, exported from
packages/settings/src/index.ts. Two operations, both read-only, both using `node:fs` - never a
shell, never a child process:

    search({ query, pathPrefix?, limit? })  ->  matches with a relative path and a line excerpt
    read({ path, startLine?, lineCount? })  ->  one excerpt with a relative path and line range

Resolve the workspace root the way the app map already does - walk up from the module's own
directory looking for `pnpm-workspace.yaml`, exactly as `findWorkspaceRoot` does in
packages/module-registry/src/index.ts line 407. Everything outside that root is unreachable, which
is what keeps `/data` (the vaults and the CLI tool directories) and the host filesystem out
without a special rule.

Inside the root, allow only these top-level roots: `packages`, `apps`, `scripts`,
`infra/postgres`, `tests`, `docs`. Reject any path whose resolved location contains one of these
segments: `node_modules`, `dist`, `build`, `coverage`, `.git`, `.turbo`, `.cache`,
`.superpowers`, `external-modules`, `data`, `vaults`, `.claude`. Reject these file names and
extensions: anything named `.env` or starting with `.env.`, `pnpm-lock.yaml`, and the extensions
`.pem .key .p12 .pfx .crt .map .png .jpg .jpeg .webp .ico .woff .woff2 .zip .tar .gz`.

Containment must survive symlinks. Resolve, then call `realpathSync` on the result, then check
containment again against the real path of the root. Reject an absolute input path outright, and
reject anything that resolves outside the root - `../../etc/passwd`, `packages/../../etc`, a
leading `/`.

Limits, all enforced, all in one exported constant object so a test can read them:

- at most 10 matches per search
- at most 2000 files scanned per search, then stop and report that the scan was truncated
- at most 40 lines and 4096 bytes per excerpt
- at most 32768 bytes across a whole response
- at most 512 KB read from any single file

Provenance on every result is a path relative to the workspace root - for example
`packages/news/src/jobs.ts` - plus the start and end line. Never return an absolute path; an
absolute path leaks the deployment layout.

Then the secret guard, and here is the trap. The obvious implementation is to reuse the
`FORBIDDEN_SECRET_KEYS` list from packages/settings/src/host-diagnostics.ts and refuse any excerpt
containing one of those strings. **That would make the reader unable to read large parts of its
own codebase**, because host-diagnostics.ts literally contains the text `DATABASE_URL` as a source
literal, and so do several config files. Mentioning the name of a secret is not a leak; carrying
its value is. So match on shape, not on vocabulary:

- reject an excerpt containing a URL with credentials embedded in it (reuse the `CREDS_IN_URL`
  regular expression already in host-diagnostics.ts)
- reject an excerpt containing an assignment where the left side looks like a secret
  (`key`, `secret`, `token`, `password`, `passwd`, `credential`, `api_key`, case-insensitive) and
  the right side is a quoted or bare literal of 16 or more characters that is not obviously a
  placeholder such as `changeme`, `example`, `<...>` or `process.env...`
- reject an excerpt containing a private key header (`-----BEGIN`)

Reject the whole excerpt with a short reason string rather than silently dropping lines, so a
caller never gets a doctored excerpt that reads as complete.

### Task 3 - reuse the host diagnostics assembly instead of copying it

The route handler in packages/settings/src/host-diagnostics-routes.ts currently assembles the
diagnostics DTO inline: admin check, database ping, multiplexer setting, latest-release row, then
`buildHostDiagnostics`. The platform diagnostics service needs the same DTO, and the issue is
explicit that there must not be a second implementation.

Extract the assembly (everything after the admin check) into an exported function in
packages/settings/src/host-diagnostics.ts or a small sibling file - `collectHostDiagnostics` - and
have the existing route call it. The route keeps its own admin check and its own 503 for a missing
provider; only the assembly moves. This is a pure move: the route's response must not change, and
the existing tests/integration/host-diagnostics-admin.test.ts must pass untouched.

### Task 4 - the platform diagnostics service, in ai

New file `packages/ai/src/platform-diagnostics.ts`, exported from packages/ai/src/index.ts.

    export interface PlatformDiagnosticsQuery {
      readonly domain?: string;   // "news" - limit module observations to one domain
      readonly include?: readonly ("version" | "runtime" | "modules" | "errors" | "actions")[];
      readonly query?: string;    // free text, passed to the error search only
      readonly limit?: number;    // capped at 10
    }

    export interface PlatformDiagnosticsReport {
      readonly observedAt: string;
      readonly build: { readonly version: string; readonly buildId: string };
      readonly runtime: HostRuntimeObservation | null;
      readonly modules: readonly ModuleDiagnosticObservation[];
      readonly errors: readonly StructuredErrorObservation[];
      readonly actions: readonly ActionAuditObservation[];
      readonly redactions: readonly string[];
    }

Build it with a factory that takes injected ports only - the app map read service, the host
diagnostics collector from task 3, an `AiRepository`, the module diagnostic providers plus a
context runner, and a way to resolve whether the actor is an instance admin. It must not import
another module's internals and must not construct its own database handle.

The rules it enforces:

- **Version is for everyone.** `build` comes from the app map's `getBuildInfo()`, which every
  user can already see through the existing app map tool. No change in exposure.
- **Instance-wide host facts are admin-only.** Resolve admin the same way the app map does -
  `SettingsRepository.getUserById` and `is_instance_admin`. For an admin, `runtime` carries the
  host diagnostics DTO. For everyone else `runtime` is null and `redactions` contains `"runtime"`,
  so piece 3 can have Moss say "that is admin-only" instead of "I don't know". Admin here means
  configuration visibility only - it never changes which rows the actor's own queries return.
- **Errors and audit are the actor's own, by row-level security.** Query through the actor's own
  scoped database handle and add no owner filter of your own, the same way every other repository
  method here relies on the policy. Project errors using exactly the field list already in
  packages/ai/src/error-tools.ts and add nothing to it - that projection is already reviewed.
  For audit rows, project occurred at, tool module id, tool name, action kind, approval mode,
  outcome, error class and request id, and **leave `input_summary` out**. It is a summary of a
  tool's input and can carry user content; the spec limits operational text to trusted metadata.
- **Run the existing guard before returning.** Call `assertDiagnosticsSafe` on the host section.
  Do not write a second sanitizer.
- **Never let one provider break the report.** Use `aggregateModuleDiagnostics`, log a drop with
  the module id and the error name only.

The service is read-only by construction: it holds read ports, exposes one `observe` method, and
has no way to enqueue a job or write a row. Keep it that way - the issue is explicit that this must
not become a generic action executor.

### Task 5 - the news provider

New file `packages/news/src/diagnostics-provider.ts`. Domain `"news"`, provider id
`"news.refresh"`. It calls `NewsPersonalizationRepository.readRefreshDiagnostics` and maps:

- no refresh row and no snapshot -> `unknown`, "News has never been refreshed for this account."
- current state `failed`, or a last failure newer than the last success -> `failed`, with the
  failure kind (`fetch`, `ai` or `internal`) named in plain words
- no snapshot, or a snapshot older than 24 hours, or a requested generation ahead of the compiled
  one while the state is idle -> `degraded`
- otherwise -> `ok`

`facts` carries the timestamps, the failure kind, the snapshot age in seconds, the item count and
the live state. Nothing else - no headline, no source name, no article text of any kind. That is
the whole point of `readRefreshDiagnostics` never selecting the payload.

Set `remediationActionId` to `"news.refreshNews"`. Nothing in this piece can execute it; it is a
label that piece 3 turns into a real, individually permissioned write action.

Attach it as `diagnosticsProvider` on `newsModuleManifest` in packages/news/src/manifest.ts.

## How to test it

Four files. The first is pure and needs no database; the middle two need one.

**`tests/integration/source-inspector.test.ts`** - pure, no database. It lives under
tests/integration for the same reason tests/integration/host-diagnostics-unit.test.ts does: the
foundation gate runs that directory. Cover: an allowed read returns a relative path and the right
lines; an allowed search finds a known string in packages; every excluded segment is rejected
(`node_modules`, `dist`, `.git`, `external-modules`); path traversal is rejected in all three
forms (`../`, an absolute path, and a path that only escapes after resolution); a symlink inside an
allowed root pointing outside the workspace is rejected (create it in a temp directory in the
test); the result count, excerpt byte and total byte limits all bind; a file containing a URL with
embedded credentials is rejected; a file containing a private key header is rejected; and - the
regression that proves the guard matches shape and not vocabulary - reading
packages/settings/src/host-diagnostics.ts succeeds even though it contains the text `DATABASE_URL`.

**`tests/integration/platform-diagnostics.test.ts`** - database-backed. Copy the setup from
tests/integration/error-log.test.ts: `resetFoundationDatabase`, a `DataContextRunner`, and the two
seeded users from `./test-database.js`. Cover: an admin gets the runtime section; a non-admin gets
null for it and `"runtime"` in `redactions`; user A seeded with error rows, audit rows and news
state cannot see any of user B's, in any of the three sections; a provider that throws is dropped,
the report still returns, and the error hook received the module id and the error name and nothing
else; and a whole-report scan finds no connection URL and no credentials-in-URL anywhere in the
serialized output.

**`tests/integration/news-diagnostics-provider.test.ts`** - database-backed. Cover: no refresh row
gives `unknown`; a recorded failure followed by a success gives `ok` while the last-failure history
survives (that is the invariant piece 1 established); a snapshot older than a day gives `degraded`;
the item count is reported; and the serialized observation contains none of the article titles that
were seeded into the snapshot payload.

**Extend `tests/unit/chat-gateway-dependencies.test.ts`** with the negative wiring test: build the
dependencies with a platform diagnostics service supplied, then assert it is present in
`readToolServices` and absent from `toolServices`. That is the machine-checked form of "a read-only
inspection cannot obtain a write-capable service".

## Things that will bite you

- **The 1000-line file size gate** (`pnpm check:file-size`). packages/module-sdk/src/index.ts is
  already 855 lines, so the seam genuinely has to be its own file. Put new code in new files and
  export it by name from each package's index.
- **The package dependency gate** (`pnpm check:package-deps`). Any import of a workspace sibling
  must be declared in that package's package.json, including a type-only import. The placement in
  this plan needs no new declaration - if you find yourself adding one, the code is in the wrong
  package.
- **This piece adds no migration.** Piece 1 added the columns. If you find yourself writing SQL,
  stop and re-read the issue.
- **This piece adds no assistant tool and no route.** A new route would also need a manifest entry
  or the server refuses to start; you should not be adding one.
- **Never run the full local gate unsupervised.** Use the repository's `verify-gate` skill - an
  unscoped run points at the live development database.
