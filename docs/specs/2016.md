## Implementation plan for [906-A] Story feedback persistence, target verification, and lifecycle API

Written after reading the approved spec (`docs/superpowers/specs/2026-08-18-906-story-relevance-feedback.md`)
and the existing feedback code. Plain English throughout; exact paths and commands are given only
where the builder has to act on them. Whoever builds this must pass the plain-English rule on to
any agent they spawn.

### What this slice owns

The storage, the contracts, and the API for story-level "More like this" / "Less like this"
feedback. Nothing that picks or displays stories.

**In scope:** new database migration; widened feedback vocabularies; a required, bounded reason for
"Less like this"; a stable story identifier helper; owner-scoped verification that the story really
came from the actor's own News or Sports result; create with idempotent retry; opposite-direction
supersession; edit a reason; remove; reads filtered to one module; export coverage; deletion
coverage; owner-only privacy and the two-owner tests that prove it.

**Out of scope, on purpose:** compiling or evaluating relevance rules (that is 906-B), News and
Sports candidate selection and refresh (906-C and 906-D), all front-end work, and any queue job.
This slice must not enqueue anything. It only leaves the seam described in step 7 for C and D to
attach to.

### Where things stand today

- The feedback module is `packages/usefulness-feedback` - one migration, a repository, one routes
  file, and a small target-verifier registry. Its two tables are owner-only under forced row-level
  security with no admin bypass, and that must stay true.
- Contracts live in `packages/shared/src/usefulness-feedback-api.ts`; row types live in
  `packages/db/src/types.ts` (search for `UsefulnessFeedbackSignalsTable`).
- Verifiers are registered in `packages/module-registry/src/index.ts` around line 1627.
- `packages/briefings/src/feedback-verifier.ts` is the pattern to copy: for a target the module
  registered earlier, the verifier confirms the row exists for this owner and returns only the
  bounded context stored on it. Client-supplied claims are never trusted.
- The export already includes both feedback tables, in
  `packages/settings/src/data-export-queries.ts` (the two functions near line 635).

### Step 1 - one new migration

Create `packages/usefulness-feedback/sql/0192_story_relevance_feedback.sql`. Never edit the applied
`0120_usefulness_feedback_signals.sql`; the runner hash-checks it. Check for a newer number before
you write the file - other lanes are adding migrations too, and 0192 is only the next free number
as of today.

On `app.usefulness_feedback_signals`:

- Widen the allowed target kinds to add `news_story` and `sports_story`.
- Widen the allowed surfaces to add `news` and `sports` (`today` already exists).
- Widen the allowed actions to add `less_like_this`. Leave `not_useful` alone; the spec keeps them
  separate on purpose - `not_useful` describes one item that was shown, "Less like this" creates an
  ongoing preference.
- Widen the allowed statuses to add `superseded`, so that a preference replaced by the opposite
  direction is distinguishable from one the user removed.
- Add `reason_text text`, capped at 500 characters.
- Add `rule_json jsonb NOT NULL DEFAULT '{}'` (must be an object) and `rule_version integer` -
  both stay empty in this slice; 906-B fills them.
- Add `revision integer NOT NULL DEFAULT 1` and `updated_at timestamptz NOT NULL DEFAULT now()`.
- Add a check that a reason is present and non-blank exactly when the action is `less_like_this`,
  and absent otherwise. "More like this" takes no reason.
- Add a partial unique index so that, for the two story target kinds, a user can have at most one
  active row per story across both directions. The existing dedupe index also includes the action,
  so it will not stop a user holding both directions at once.

On `app.usefulness_feedback_targets`: widen the same target-kind and surface lists.

Widening a `CHECK` means dropping and re-adding the constraint in the new file. Do not touch the
old file.

### Step 2 - contracts

In `packages/shared/src/usefulness-feedback-api.ts`, add `less_like_this` to the action union and
enum, the two story kinds to the target union and enum, `news` and `sports` to the surface union
and enum, and `superseded` to the status union and enum. Add an optional `reason` to the create
request (max 500) and `reason`, `revision`, `ruleVersion`, `updatedAt` to the returned object.
Add a request shape and schema for the new edit endpoint, and a query shape for the module filter.

Keep `packages/shared` free of Node-only imports - the browser bundle imports this package, and
there is a comment in `packages/shared/src/ai-types.ts` recording a past breakage from exactly
that. The hashing helper in step 3 therefore does **not** go here.

In `packages/db/src/types.ts`, add the new columns to `UsefulnessFeedbackSignalsTable` and widen
the four small union types it uses.

### Step 3 - stable story identity

Add `packages/usefulness-feedback/src/story-target.ts` exporting a function that turns a module id
plus a story's canonical link into an opaque identifier, and a matching function that produces the
bounded context a story target row may carry (module, headline, source label, published time,
topic/team/competition identifiers, editorial-evidence flags).

Copy the shape of `packages/briefings/src/feedback-targets.ts`: lower-case, trim, join with a
separator, SHA-256, keep a short prefix. Raw links and article text are never used as identifiers
and never stored as one.

Two traps here:

- The metadata cleaner in `packages/usefulness-feedback/src/metadata.ts` silently drops any key
  whose name looks like `body`, `excerpt`, `externalId`, `prompt`, `raw`, `secret`, `sourceId(s)`,
  `summary`, or `token`. Name story context keys so they survive - `teamRef`, `competitionRef`,
  `topicRef` are fine; `externalId` would vanish without warning.
- Add `reason` to that same blocked-key list. The reason has its own column; it must never also
  land inside the generic metadata object.

### Step 4 - target verification

Add a verifier in the feedback module (not in News or Sports) that accepts the two story kinds and
looks the target up through the existing `findTarget`, exactly as the briefings verifier does for
briefing items. If the actor has no registered target row for that story, module, and surface, the
answer is "not found" and no feedback is created. Story targets can never be remembered, so the
"can remember" flag stays false.

Extend `isAllowedFeedbackPair` in `packages/usefulness-feedback/src/target-verifiers.ts`:
`news_story` allows surfaces `news` and `today`; `sports_story` allows `sports` and `today`. Both
allow only `more_like_this` and `less_like_this`.

Register the new verifier for both story kinds in `packages/module-registry/src/index.ts` next to
the existing four.

Also add a bounded cleaner for story target metadata and apply it when a story target is
registered. Do not apply it to the existing briefing path - there is a test that depends on
briefing target metadata merging through untouched.

### Step 5 - repository

In `packages/usefulness-feedback/src/repository.ts`:

- Store and return the new columns on create.
- Add a lookup for the active row for a given owner, story kind, and story reference, regardless of
  direction. Supersession needs this; the existing lookup is per-direction and will not find the
  opposite one.
- Add a "supersede" update that sets an active row to `superseded` with a resolved time.
- Add an "update reason" method that writes the new text, bumps `revision`, sets `updated_at`, and
  keeps the same id.
- Add a module filter and a status filter to `list`, and keep the existing 100-row limit.

### Step 6 - the API

In `packages/usefulness-feedback/src/routes.ts`:

- **Create.** The body check today insists on exactly four keys in a fixed order, so simply adding
  an optional reason will make every story request fail. Rewrite it to accept the four required
  keys plus an optional `reason`, and still reject anything else. There is an existing test that
  unknown keys are rejected - it must stay green.
  Validation for `less_like_this`: trim the ends, reject empty or whitespace-only with 400, reject
  more than 500 characters with 400, and otherwise store what the user typed verbatim. Do not
  collapse internal spacing - the spec requires the user to see back exactly what they wrote. (The
  "remember this" path does collapse whitespace; do not copy that here.)
  Sending `reason` with `more_like_this` is a 400.
  Order of work inside the request: verify the target first, then look for an existing active row
  for that story. Same direction already active means return it unchanged with 200 and do no other
  work. Opposite direction active means mark it superseded and insert the new one.
- **Edit.** Add `PATCH /api/me/usefulness-feedback/:id`, accepting only a reason. It is valid only
  on an active `less_like_this` row owned by the actor; anything else is a 404 (not found) or 400
  (wrong action). It keeps the id and bumps the revision.
- **Remove.** Reuse the existing undo endpoint. It already marks the row undone without deleting
  it, which is what the spec asks for. Do not add a delete endpoint.
- **Read.** Add optional `module` (news or sports) and `status` query parameters to the existing
  list endpoint, mapping module to the matching story target kind. News settings must never see
  Sports preferences and the other way round.
- Add an optional callback in the route dependencies, something like "story preference changed",
  called after a successful create, edit, or remove. Leave it unwired in this slice. 906-C and
  906-D attach the module refresh to it. That keeps this slice free of queue work while giving the
  later slices a seam that does not require re-opening this file.

Declare the new `PATCH` route in `packages/usefulness-feedback/src/manifest.ts` under the existing
`usefulness-feedback.manage` permission. A route that is not declared in the manifest makes the
server refuse to start.

Watch the file size: `routes.ts` is around 306 lines and the standard is not to push a file past 1000. If the create handler grows awkward, move body parsing and validation into a small
`request-parsing.ts` beside it rather than letting the route file sprawl.

### Step 7 - export and deletion

- Add the new columns to both queries in `packages/settings/src/data-export-queries.ts`. The
  reason belongs in the user's own export - that is explicitly required.
- Deletion already works: both tables cascade from `app.users`. But neither table appears in the
  count sweep in `scripts/delete-user-data.ts`, so a deletion report today silently under-reports.
  Add both, with the standard owner predicate.
- Do **not** migrate this module to the newer `dataLifecycle` declaration. `usefulness-feedback` is
  on the pending list in `packages/module-registry/src/index.ts`, and moving it is separate,
  already-planned work (#801 Phase B). Doing it here would drag the export section out of the
  settings package for no benefit to this slice.

### Step 8 - privacy

- The reason goes nowhere except its own column, the owner's own responses, and the owner's own
  export. Not into logs, not into metrics, not into any job payload, not into metadata.
- Keep forced row-level security and owner-only policies as they are. No admin bypass, and admin
  context must get nothing.
- Treat the reason as preference text, never as instructions. Nothing in this slice sends it to a
  model; 906-B owns that boundary.

### How to test it

Extend `tests/integration/usefulness-feedback.test.ts` - it already covers owner-only security,
verification, idempotent create, listing, and undo, so the new cases sit naturally beside the old
ones. New cases:

1. "Less like this" on a registered News story is created with the reason stored and returned.
2. An empty, whitespace-only, or over-length reason is rejected, and nothing is written.
3. "More like this" with a reason is rejected.
4. Sending the same feedback twice returns the same row and does not create a second one.
5. Saving the opposite direction marks the first row superseded and leaves exactly one active row
   for that story.
6. A story reference that the actor never had registered is rejected as not found, even if a second
   user does have it registered.
7. Editing a reason keeps the id, changes the text, and bumps the revision; editing a removed or
   "More like this" row fails.
8. Removing marks the row undone; the story becomes eligible again from the API's point of view.
9. A News-filtered read returns only News rows, and the Sports filter only Sports rows.
10. Two owners cannot see, edit, remove, or verify each other's feedback; an admin-scoped read gets
    nothing.
11. A reason containing instruction-like text is stored and returned unchanged as plain text and
    appears in no log line or metadata field.
12. The export contains the reason for its owner and only for its owner.

Add a small unit test for the story identity helper: the same link yields the same identifier
across calls, different links differ, the identifier contains no readable part of the link, and
the two modules produce different identifiers for the same link.

Also update the migration list in `tests/integration/foundation-schema-catalog.test.ts` - it
asserts the full ordered list of migration files, so a new file fails it until it is added.

Commands (use the `verify-gate` skill for anything that touches the database; an unscoped run hits
the live development database, and a piped run reports red as green):

```
npx tsc --noEmit
npx eslint <files you touched> --max-warnings=0
pnpm db:migrate
pnpm test:integration
```

The unit suite fails locally at the module worker tests for unrelated, known reasons; that is not
your branch and is green in continuous integration.

Commit through the `shared-checkout` skill - several agents share this working tree, so never stage
everything and never run a bare commit here.

### Done looks like

- The migration applies cleanly on a fresh database and on an existing one.
- A user can save, retry, flip, edit, and remove story feedback through the API, and reads can be
  narrowed to one module.
- A second user is refused at every one of those operations, and an admin gets no bypass.
- The reason survives round-trip exactly as typed, is capped at 500 characters, is required for
  "Less like this" and refused for "More like this", and appears in the owner's export and nowhere
  else.
- Deletion still removes everything and now reports both tables.
- Type checking, linting, the file-size check, and the integration suite pass.
- Nothing in News, Sports, or the web app changed; no queue job was added.

section should be `Category: N/A`. The template still has to be filled in.

## Build notes recorded on the branch (2026-08-27)

Two points where the branch differs from the plan text above, both checked against the real code
before any of it was written:

1. **Migration number.** The plan named `0192`. That number was taken by Sports while this issue
   waited, and `0200` was then taken by News (`0200_news_source_credentials.sql`, #2035) while
   this branch was in review. `scripts/migrate.ts` calls `assertUniqueMigrationVersions` across
   every module's SQL folder and throws on a repeated number, so a collision stops every
   migration. This slice therefore adds
   `packages/usefulness-feedback/sql/0201_story_relevance_feedback.sql`.

2. **Order of work inside the create request.** The plan said to verify the story target before
   looking for an existing saved preference. This branch does the lookup first and then verifies,
   for one reason: the lookup is already limited to rows the person asking owns, so returning an
   existing row early cannot tell anyone anything about someone else's data, and it keeps a
   repeated tap from re-running the verifier. There is an existing test that depends on that
   (a second identical request must not call the verifier again). Nothing is ever written without
   verification: both the "flip the direction" path and the "save a new one" path verify first.
