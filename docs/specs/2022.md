SPEC

## What is wrong today

The pre-check that blocks piped gate commands, `.claude/hooks/check-gate-pipe.sh`, tells the
blocked agent to fix the problem by writing:

    pnpm verify:foundation > /tmp/vf.log 2>&1; echo "EXIT=$?"

That is exactly the recipe the project has since ruled unsafe and replaced. The header comment in
`scripts/run-gate.sh` explains why: a full gate run takes 15 to 25 minutes, longer than a single
Bash call is allowed to run, so an agent following that foreground recipe cannot actually finish
it and ends up hand-rolling a background run and a wait loop instead — which is how the project
lost 19 hours to a dead gate once (see the comment block at the top of `scripts/run-gate.sh` for
the full story). The `verify-gate` skill (`.claude/skills/verify-gate/SKILL.md`) already says the
one accepted way to run `verify:foundation`, `test:integration`, `test:uat-seed`, or `db:migrate`
is `scripts/run-gate.sh` (`start`, then `wait`, then `status`) — never a hand-rolled redirect.

So right now, if an agent gets blocked while trying to pipe one of those specific gate commands,
the block message hands them the wrong fix and points them away from the documented safe
procedure.

## What to change

File: `.claude/hooks/check-gate-pipe.sh`

The block message (currently a single fixed block of text printed for every blocked command,
lines 43-55) needs to give different advice depending on what was blocked:

1. If the blocked command invokes the full gate or one of the database-touching gate scripts —
   `verify:foundation`, `test:integration`, `test:uat-seed`, or `db:migrate` — tell the agent to
   use `scripts/run-gate.sh` instead: run `start` (optionally with `--gate <pnpm-script>` for a
   narrower gate), then `wait`, then `status`, and read the exit code, not the piped text. Point
   at the `verify-gate` skill by name so the agent can read the full procedure.

2. For every other command the hook blocks (lint, typecheck, build, format check, and any other
   non-database gate script) keep the existing advice: redirect to a file and check the exit code
   afterward, e.g. `pnpm lint > /tmp/lint.log 2>&1; echo "EXIT=$?"`, or add `set -o pipefail` /
   check `${PIPESTATUS[0]}` if a pipe is genuinely needed. This is still a correct and safe
   pattern for those — the problem is only that it is wrong for the long, database-touching gate.

Keep everything else in the script exactly as it is: the `PreToolUse(Bash)` contract, the jq
availability check, the `pipefail`/`PIPESTATUS` opt-outs, the `||`-neutralizing step, and the
regex that decides whether a command counts as a piped gate invocation. This issue is about the
wording of the message the agent sees after being blocked, not about which commands get blocked.

A simple way to implement the split: after the existing regex confirms the command is a blocked
piped gate command, check whether `$cmd` also matches the database-touching gate names
(`verify:foundation`, `test:integration`, `test:uat-seed`, `db:migrate`) and print one message or
the other before the `exit 2`.

## How to test it

There is no existing test file for this hook. Add one, following the style already used for
another Claude Code hook in this repo (`tests/unit/claude-permission-hook.test.ts` spawns the
hook script as a child process, writes the JSON payload to its standard input, and reads back its
exit code and standard error).

For `check-gate-pipe.sh` specifically, spawn `bash .claude/hooks/check-gate-pipe.sh`, feed it a
JSON payload shaped like `{"tool_name": "Bash", "tool_input": {"command": "<the command under
test>"}}`, and assert on the exit code and the text printed to standard error. Cover at least:

- `pnpm verify:foundation | tail -20` is blocked (exit code 2) and the message printed mentions
  `scripts/run-gate.sh`.
- `pnpm test:integration | cat` and `pnpm db:migrate | tee /tmp/x` are blocked the same way, with
  the same `scripts/run-gate.sh` guidance.
- `pnpm lint | tail -20` is still blocked (exit code 2), but the message printed is the redirect
  and exit-code advice, not `scripts/run-gate.sh`.
- A command with `set -o pipefail` in front of a gate pipe, and one that checks
  `${PIPESTATUS[0]}`, are both still allowed through (exit code 0) — the existing opt-outs must
  keep working.
- A non-gate piped command (something with no lint/test/build/verify/etc token before the pipe)
  is still allowed through.

## What done looks like

- The block message an agent sees for `verify:foundation`, `test:integration`, `test:uat-seed`,
  or `db:migrate` names `scripts/run-gate.sh` as the fix, instead of the foreground redirect
  recipe that the project has already ruled out for those commands.
- Every other blocked gate command still gets the existing redirect-and-check-exit-code advice.
- The existing safety behavior is unchanged: any command that pipes a gate invocation without an
  opt-out is still blocked with exit code 2; `pipefail` and `PIPESTATUS` opt-outs still allow the
  command through; non-gate piped commands are still unaffected.
- The new test file passes and covers the cases listed above.

## Additional fix found during build

`pnpm db:migrate | tee /tmp/x` was not being blocked at all before this change, because the
overall piped-gate detector only recognized commands containing the words verify, test, lint,
typecheck, format, build, check, or audit — and "db:migrate" contains none of them. Added
"migrate" to that word list so a piped `db:migrate` is caught and routed to the
`scripts/run-gate.sh` message, matching the spec's required test case.
