SPEC

## What this issue is

Issue #1557 built a warm, reusable assistant session for Claude: one child process
that stays open and takes turn after turn without restarting
(`packages/chat/src/live/claude-persistent-runtime.ts`). This issue asks for the
same thing for Codex (OpenAI's CLI, called `openai-compatible` in this codebase).

Codex's own command-line tool does not offer a process you can keep open and feed
turn after turn the way Claude's does. Every `codex exec` call is a fresh process
that runs once and exits. The fix already used in this codebase for one-shot Codex
calls (`packages/chat/src/live/codex-exec-session.ts`) is to run `codex exec` for
the first turn, then `codex exec resume --last --json` for every turn after that,
so Codex continues the same conversation across separate process launches. This
plan builds a version of that pattern that satisfies the same shape everything else
in the warm-session system expects (start a session, send a turn, get events back
as they happen, cancel, check health, shut down, recover from a crash) — see
`packages/chat/src/live/provider-runtime.ts` for that shape (the file calls it
`ProviderChatRuntime`). Also confirmed in
`docs/superpowers/specs/2026-06-26-codex-non-interactive-execution-mode.md`:
"the engine is responsible for preserving the illusion of persistence" for Codex.

One honest tradeoff to flag up front, not to solve: because there is no process
staying alive between turns, the "warm pool" that limits how many concurrent
sessions exist won't actually be saving idle memory for Codex the way it does for
Claude (nothing is sitting there using memory between turns). That's fine — plug
it in the same way anyway, so admission limits and eviction still apply uniformly.
Don't try to special-case it.

## Files to add

**`packages/chat/src/live/codex-persistent-runtime.ts`** — new file, the Codex
version of `claude-persistent-runtime.ts`. Implements `ProviderChatRuntime` from
`provider-runtime.ts`:

- `kind = "persistent"`, `provider = "openai-compatible"`.
- `launch(opts)`: do the fail-closed MCP readiness check exactly like Claude's
  version does (`opts.mcpReadiness()` before allowing any turn), using the same
  `createMcpReadinessProbe` function already in `claude-persistent-runtime.ts` (it
  is provider-neutral — it just calls the MCP server directly over HTTP, it does
  not care which assistant CLI is running). Either import it from there or move it
  into `provider-runtime.ts` so both adapters use one copy — moving it is cleaner
  since it's genuinely shared, but importing across the two files is also fine for
  a bounded first cut. Record state as "ready" once the check passes; there is no
  child process to spawn yet, since Codex only starts a process per turn.
- `submitTurn(turnId, engineText)`: write the prompt to a file in the session's
  scratch folder (mirror `codex-exec-session.ts`'s `buildPrompt` for how the text,
  the persona, and any replay batch get combined, and its `buildCommand` for the
  exact command-line flags: `--skip-git-repo-check`, `--disable apps`,
  `--sandbox read-only`, `-c 'approval_policy="never"'`, the two
  `features.shell_tool=false` / `features.apply_patch_tool=false` overrides, and
  the MCP server config lines when a gateway token is present). The one change
  from the one-shot version: the FIRST turn on a runtime instance runs
  `codex exec --json`; every turn after that runs `codex exec resume --last --json`
  instead of replaying prior turns as literal `User:`/`Assistant:` text in the
  prompt (the one-shot version does that because it starts a fresh process with no
  memory each time; the persistent version doesn't need to, since it's the same
  logical Codex conversation continuing).
- Spawn that command directly (piped stdout, not a wait-for-full-output helper) so
  events can be read out as they arrive, the same way `claude-persistent-runtime.ts`
  spawns its child with piped stdio and feeds stdout chunks to a decoder as they
  come in.
- `streamEvents()`: decode each JSON line from that process's stdout as it
  streams, and turn it into the same `RuntimeTurnEvent` shape Claude's decoder
  produces (`record` / `turn-complete` / `turn-failed`, from `provider-runtime.ts`).
  The Codex line shapes to expect are already documented and already handled once
  in this codebase, in
  `packages/ai/src/adapters/transcript-reader.ts` (`mapCodexRecord` /
  `mapCodexExecItem`): a `thread.started`, then `turn.started`, then one
  `item.completed` per step (`reasoning` -> thinking, `command_execution` or
  `mcp_tool_call` -> tool, `agent_message` -> the final reply text), then
  `turn.completed`. Do not reuse `PersistentStreamDecoder` as-is — it only knows
  Claude's line shapes (`type: "assistant"`, `type: "result"`). Write a small
  Codex-specific decoder (a new class, e.g. `CodexStreamDecoder`, or a mapping
  function next to it) that turns those lines into the same `RuntimeTurnEvent`
  values, and reuse the same two safety limits from `persistent-stream-decoder.ts`
  (`MAX_FRAME_BYTES`, `MAX_TOTAL_BUFFERED_BYTES`) so a runaway Codex process can't
  fill memory either. A turn is complete when `turn.completed` arrives; treat a
  process exit with no completed turn as a `turn-failed` neutral failure, same as
  Claude's decoder does on an unexpected EOF.
- `cancel(turnId)`: kill the current per-turn child process, same signal pattern
  Claude's runtime uses (SIGTERM, then SIGKILL after a short grace period if it
  hasn't exited) — copy `killChildProcess` from `claude-persistent-runtime.ts`.
- `health()`: `alive` reflects whether a turn's process is currently running (there
  is nothing to be "alive" between turns, since no process exists then — treat that
  as a normal idle state, not a fault). Track `state` (`ready` / `in-turn` / `idle`)
  and `turnsCompleted` / `lastResultAt` the same way Claude's runtime does.
- `reap(reason)`: kill any in-flight per-turn process; there is no persistent
  process to additionally clean up.
- `recover(turnId)`: Claude's version can safely retry only if the stdin write
  never happened (the text never reached the child). Codex's equivalent safe-to-retry
  signal is "no tool ran yet for this turn" — if the decoder hasn't seen any
  `command_execution` or `mcp_tool_call` item for the turn that died, it's safe to
  re-run the same command once (same session resume, same prompt) because nothing
  in the world was changed yet. If a tool already ran, don't retry — return a
  neutral failure exactly like Claude's version does
  (`NEUTRAL_CRASH_FAILURE`-style message, reused or mirrored).

**Wiring it in** — two small edits:

- `packages/chat/src/live/persistent-runtime-engine.ts` currently hardcodes
  `ClaudePersistentRuntime` and `provider: ProviderKind = "anthropic"`. Generalize
  it to accept which runtime class and which provider to use (a constructor option,
  defaulting to the current Claude behavior so nothing else breaks), OR add a
  second small wrapper class for Codex that mirrors it — whichever keeps the diff
  smaller once you're looking at the file; the class is short. Either way, the
  Codex path ends up producing an object satisfying `CliChatEngine`.
- `packages/chat/src/live/engine-selection.ts`: the check
  `if (opts.persistentRuntimeEnabled && provider === "anthropic")` currently only
  turns on the persistent path for Claude. Extend it to also match
  `provider === "openai-compatible"` and construct the Codex engine/runtime in that
  branch. Leave the Claude branch and the bounded-fallback branch (used when the
  flag is off, or admission is denied) exactly as they are.

## Testing

- Add `tests/unit/codex-persistent-runtime.test.ts`, modeled on the existing
  `tests/unit/claude-persistent-runtime.test.ts`: inject a fake process spawner
  (same pattern as `ClaudePersistentRuntimeOpts.spawnChild`) so the test can feed
  canned Codex JSON lines and assert the right `RuntimeTurnEvent`s come out, that a
  second `submitTurn` call uses `resume --last`, that a crash before any tool ran
  triggers a resubmit, and that a crash after a tool ran does not.
- Extend `tests/unit/persistent-runtime-engine.test.ts` (or add a Codex-specific
  copy) to cover the generalized wrapper with a fake Codex runtime.
- Add a case to `packages/chat/src/live/engine-selection.test.ts` proving
  `provider === "openai-compatible"` with the flag on selects the persistent
  engine, matching the existing Claude case.
- Run this project's normal unit test command for the changed packages; this is a
  unit-testable change (fake process, no real Codex binary needed) so it does not
  need the live dev-instance proof this project requires for user-facing UI
  changes — nothing about the chat UI changes here, only which process runs behind
  a Codex chat session when the rollout flag is on.
