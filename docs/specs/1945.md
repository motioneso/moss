# Spec: #1945 — Workshop shows real build data (part 1 of #1889)

This is the first slice of #1889 ("the Workshop page shows real builds, and its buttons work").
It covers only getting real data onto the page. Everything else from #1889 — landing on the
Workshop page after approving a build, polling and notifications, and making the Stop / Ask for
a change / Turn on for everyone buttons actually do something — is a separate piece, not this one.

## What's wrong today

The Workshop page always shows three empty groups. The code that fills the page hands it two
empty lists no matter what is really happening — there is no way for the browser to ask the
server "what is Moss building for me right now, and what have I already got running."

## What this change does

- Add a new way for the browser to ask the server for the builds a person owns (their own builds
  only — nobody else's, including other admins).
- Reuse the existing "my modules" data (already used elsewhere in the app) to show the modules
  that are already running, and whether each one is visible only to the person who built it or
  turned on for everyone.
- Move the shapes describing "a build" and "a live module" out of a temporary stand-in file inside
  the Workshop page and into the shared package the rest of the app already uses for this kind of
  thing. Delete the placeholder shapes — they invent fields that don't exist in the real data
  (things like a progress percentage or a daily spending limit that isn't tracked anywhere).
- Update the Workshop page and its cards to show only real fields: what the build is doing, which
  web pages it looked at, whether a live module is private to its builder or on for everyone. Do
  not invent placeholder text for fields that don't exist.

## What this does not do

- Clicking "Build it" still does not take you to the Workshop page afterward.
- The page does not refresh itself while a build is running, and finishing a build does not send
  a notification.
- The Stop, Ask for a change, and Turn on for everyone buttons stay visual only — they don't call
  anything on the server yet.

## Guardrails

- A build or a draft module is visible only to the person who owns it. Nobody, including an
  admin, sees someone else's builds just by being an admin.
- Don't invent data fields. Every field shown on the page must come from data the server actually
  has today.
- Before touching how the page looks, it must still pass the repo's existing design-system check.

## How this will be verified

- Automated tests, written before the code: the new "my builds" endpoint returns only the caller's
  own builds; the page's cards render correctly with a build that has no plan yet, without
  showing made-up placeholder text.
- The formatting, linting, and type-checking commands succeed.
- Live proof on the real running dev copy of the app, recorded on the pull request: start a build
  from chat, see it appear on the Workshop page with its real status and the list of pages it
  looked at, and see an already-running module show correctly as private or public.
