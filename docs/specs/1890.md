# Spec — #1890, Workshop 8: throw a draft away

## What this changes

A draft module is one Moss built for you. Only you can see it, and until now there was no way to
get rid of one from the screen. The "Throw it away" button on the draft banner is greyed out with
the tooltip "Deleting a draft isn't wired up yet". This makes the button work.

Pressing it asks you to confirm, then deletes three things: the module's row in the database, the
installed module folder on disk, and any leftover build folder the build produced. After that the
module is gone from the sidebar and its page no longer exists, without restarting the app.

## What it does not change

- The banner's other dead button, "See the code", stays exactly as it is. Ben decided on
  2026-08-23 not to build a code viewer yet, and hiding the button is a separate visual choice.
- The banner's wording about what a draft reaches and keeps stays hard-coded. Ben saw this on
  2026-08-23 and chose to leave it.
- Any data tables the module created for itself are left alone. Destroying a module's own data is
  the existing "remove and purge" machinery, which runs at boot and is keyed off the very database
  row this feature deletes. Wiring the two together is a bigger change than this ticket, and
  #1890 lists only the row, the module folder and the build folder. Called out on the pull request
  so it is not lost.
- The Workshop page's "Live" list is not connected to real data yet — it renders an empty list for
  everyone today. So "the module disappears from the Live group" cannot be observed either way
  until that list is wired up. The observable proof is the sidebar, the module's own page, the
  database and the disk.

## How it works

### Server

A new endpoint, `DELETE /api/admin/modules/:id/draft`, sitting beside the existing ship endpoint
`POST /api/admin/modules/:id/ship` and built the same way.

Order of checks, deliberately: confirm the caller is an instance admin FIRST, before any other
branch, so someone who is not an admin can never learn whether a given module exists. Then refuse
with 409 if external modules are switched off on this instance. Then delete.

The delete itself is one database statement that only matches a row that is all three of: this
module id, still in draft status, and owned by the caller. If it matches nothing the endpoint
answers 404 — deliberately the same answer for "no such module", "that is a shipped module" and
"that draft belongs to someone else", so the endpoint cannot be used to probe for other people's
drafts. This mirrors the ship endpoint's existing behaviour and its stated reasoning.

Files are deleted after the database work succeeds, never before. If a file delete fails the row
is already gone, which is the safe direction: a leftover folder is harmless and the next scan
ignores it, whereas a deleted folder with a live row would leave a broken module in the sidebar.

Two folders are removed: the installed module folder, using the existing file-removal helper that
already guards against a crafted module id escaping the folder; and the build's source folder, via
the existing build-folder resolver, which throws on any id that is not a plain safe name. Build
folders are found from the caller's own build records, which are already restricted to their owner
by the database.

After the deletes, the running app rescans its modules folder and tells the worker process to do
the same, which is what makes the module vanish from the sidebar without a restart. This reuses
the same rescan path the existing admin rescan endpoint uses.

Every delete writes an audit entry carrying the module id and nothing else — no file contents, no
module data.

The new endpoint is declared in the route manifest, without which the server refuses to start.

### Browser

The draft banner already accepts an optional "throw away" handler and shows the button greyed out
with a tooltip when it is absent. Supplying the handler is all that is needed to make the button
live and drop the tooltip; that logic already exists and is not changed.

Pressing the button opens a confirm dialog before anything is deleted, built on the app's existing
dialog and button pieces. The confirm dialog lives next to the banner rather than reusing the
settings screen's shared confirm helper, because that helper is only mounted inside the settings
screen and the draft banner is not on it. The dialog is a plain warning: this deletes the module
and everything about it, it cannot be undone, and there is no earlier version to go back to.

While the delete is in flight the button is disabled so it cannot be pressed twice.

On success the app refetches the module list, which removes the module's route and its sidebar
entry, and then sends the user to the Workshop page — the module's own page has just ceased to
exist, so staying on it is not an option.

## Guardrails this must hold

- One instance admin cannot delete another's draft. Enforced by the owner check in the delete
  statement, and covered by a test that has a second admin try.
- A shipped module cannot be deleted through this path. Enforced by the draft-status check in the
  delete statement, and covered by a test.
- A non-admin gets the same refusal whether or not the module exists.
- The audit entry carries identifiers only, never content.

## How this is verified

Automated:

- A database-backed test that a draft's owner can delete it, and afterwards the row is gone.
- A database-backed test that a second instance admin gets 404 and the row survives.
- A database-backed test that a shipped (enabled) module gets 404 and the row survives.
- A database-backed test that a non-admin gets 403.
- A test that the deletes are attempted against the installed module folder and the build folder,
  and only after the database delete succeeded.
- A rendering test that the banner's throw-away button is enabled and carries no tooltip when the
  handler is supplied, and that the confirm dialog renders its warning and its two buttons.

All database-touching tests are run through the `verify-gate` skill, never directly.

Live proof on the dev instance, recorded on the pull request: build a draft, throw it away, and
confirm it is gone from the sidebar, from the database, and from the disk.
