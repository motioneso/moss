## What this proves

A real, docker-based test instance is booted, a module that is NOT in the registry is dropped onto the instance's disk, and the test proves the running app actually shows the "External modules" group, its trust warning, and the admin credential field for that module — the same behavior fixed in #1084 and #918. No mocked API calls; this is the same kind of test as `tests/uat/specs/module-install.uat.spec.ts`.

## New file

`tests/uat/specs/1106-external-module-trust-credentials.uat.spec.ts`

## What the test does, step by step

1. Provision a UAT stack the normal way (`provisionForUat`, minimal admin-only seed level — same as `tests/uat/specs/1270-provider-signin.uat.spec.ts` uses).
2. Build a small module folder on the test runner's disk (a temp directory), containing one file, `jarvis.module.json`, describing a module that:
   - has an id that is not in the registry and not pre-installed (so it counts as "undeclared" the same way `filterUndeclaredExternalModules` in `apps/web/src/settings/settings-instance-modules-pane.tsx` decides it),
   - declares one instance-scope credential (so the admin credential field this test also checks has something to show). `tests/integration/module-credentials.test.ts` (around line 45) has the exact JSON shape to copy — same `auth` array format, with `scope: "instance"`.
3. Copy that folder into the running instance's container, at the module directory the app reads on boot (`/data/modules/<the-module-id>`, see `scripts/start-jarv1s.ts`, which creates that directory). Copy it in with a plain `docker compose cp` command run from the test, built with the already-exported `buildUatComposeArgs(projectName, ["cp", localFolder, "jarv1s:/data/modules/<id>"])` from `tests/uat/provisioner.ts`. No changes to `provisioner.ts` are needed — `buildUatComposeArgs` is already exported for exactly this kind of one-off docker call.
4. Call the already-existing `restartUatStack(projectName, baseURL)` helper (also in `tests/uat/provisioner.ts`, already used by `module-install.uat.spec.ts`). This restarts the app container, which reruns its boot-time module scan and picks up the folder placed in step 3 — there is no in-app "rescan" button today, so a restart is the real way this becomes visible, matching how an operator would actually do it.
5. Log in as the admin (copy the login steps from `module-install.uat.spec.ts`), open Settings and permissions -> Admin / Setup -> Instance modules (same navigation steps as that file).
6. Assert, on the real page:
   - An "External modules" group is visible.
   - The warning text is visible: "External modules are not reviewed by Moss. Only enable modules you authored or fully trust — an enabled module runs with the same access as built-in features." (this exact text lives in `settings-instance-modules-pane.tsx`).
   - A row for the test module is visible, showing its name, publisher, and version, and its enable switch is present and unchecked (off by default).
   - The instance-scope credential field for the module is visible, labelled with the credential's display name (e.g. an input with that accessible name), matching what `apps/web/src/settings/module-credentials-section.tsx` renders for an admin-scope slot.
7. Optional stretch (only if time allows without complicating the test): turn the switch on, then off, and confirm the row's state follows — this proves the module is genuinely live, not just listed. Not required for the issue to count as done.

## What "done" looks like

- The new spec file exists, follows the existing UAT spec conventions (real login, real navigation, no `page.goto` shortcuts past the first load, matching `module-install.uat.spec.ts`).
- Running it against a real stack (the normal UAT run command used for the other specs in `tests/uat/specs/`) shows the trust warning group, the module row, and its credential field, all sourced from real server responses — not stubbed.
- No changes are needed to product code; this is a test-only addition. If the test fails because the External modules group does not actually appear, that is a real product bug to report separately, not something to work around in the test.

## Notes for whoever builds this

- Reuse `restartUatStack` and `buildUatComposeArgs` from `tests/uat/provisioner.ts` — don't write a new docker-restart helper.
- Copy the credential-manifest JSON shape from `tests/integration/module-credentials.test.ts`, not from scratch — it is already proven to be accepted by the server.
- Copy the login and navigation steps from `tests/uat/specs/module-install.uat.spec.ts` rather than re-deriving selectors.
