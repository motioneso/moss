# Adversarial review: draft specs #1553 and #1554

Grounding: both drafts, the Phase-0 spike, `CLAUDE.md`, `docs/DEVELOPMENT_STANDARDS.md`, GitHub issues #1553/#1554/#1248 and their relevant comments, and source at `128a5bed677862ff13da21c98e75d5a9572d1a57`. No live system or DB-touching test was used.

## #1553 — Chat context continuity and default notes retrieval

**Verdict: REVISE**

1. **Severity: blocker — The nonzero replay default also enables summary generation, contradicting the spec's explicit non-goal.**
   - Evidence: the draft says summaries are consumed but never generated or refreshed (`2026-08-10-1553-context-continuity-and-notes-retrieval.md:24-25,68,86-87`). In current source, `getReplayK()` drives both replay and the write path: `packages/chat/src/live/persistence.ts:240-260` writes `conversation_summary` whenever `k > 0`, while `:183-185` synthesizes `buildRollingSummary(...)` during reads when no stored summary exists. Changing the unset default from 0 to 20 activates both behaviors.
   - Fix direction: decouple replay-window configuration from summary creation and specify a read-only summary policy, including absent, stale, overlap, and coverage-watermark behavior.

2. **Severity: blocker — The promised replay of recorded tool calls/results has no persisted source and would expand the secrets boundary without a design.**
   - Evidence: the draft says tool calls/results are replayed "as recorded" in the existing `listPriorTurns` shape (`...1553-context-continuity-and-notes-retrieval.md:88-90`), but that shape is only `{ role, content }` (`packages/chat/src/live/persistence.ts:157-185`). Completed-turn persistence stores user/assistant text plus metadata, not structured tool calls/results (`packages/chat/src/live/persistence.ts:218-230`). Persisting or re-prompting raw tool results would also need to satisfy `CLAUDE.md:25-27` (credentials and tokens never enter AI prompts).
   - Fix direction: replay only the already-persisted user/assistant text, or write a separate sanitized structured-history contract with schema, redaction, retention, and compatibility rules before claiming tool replay.

3. **Severity: blocker — Default automatic notes injection can put credentials from personal notes into an AI prompt.**
   - Evidence: the hard invariant says credentials/auth tokens never reach AI prompts (`CLAUDE.md:25-27`). The draft injects raw note snippets by default and treats prompt-injection fencing as the entire trust boundary (`...1553-context-continuity-and-notes-retrieval.md:106-116`). The current notes search returns chunk text verbatim (`packages/notes/src/tools.ts:50-59`); its output contract has no secret exclusion or redaction.
   - Fix direction: require a fail-closed sensitive-content filter before passive injection, drop any suspect snippet, and add a test proving credential-shaped note content never reaches engine input.

4. **Severity: major — The notes-recall module seam cannot currently satisfy the required metadata and is not specified.**
   - Evidence: the draft requires note path and modified time on each injected snippet (`...1553-context-continuity-and-notes-retrieval.md:106-115`), but public `notes.search` returns only `sourcePath`, line bounds, and text (`packages/notes/src/tools.ts:34-62`). The draft merely says `PassiveContextRetriever` "gains a notes-recall path" and does not name a declared public API; importing notes internals or querying its tables would violate module isolation (`CLAUDE.md:36-37`).
   - Fix direction: define one public notes-recall port (or reuse the registered read-tool boundary) whose result includes owner-scoped relative provenance, modified time, score, and sanitized text.

5. **Severity: major — The replay selection algorithm is ambiguous at its core boundary.**
   - Evidence: the draft alternates between "last 20 turns" and dropping "whole turns" (`...1553-context-continuity-and-notes-retrieval.md:21-24,82-85`), while current code calls every individual user or assistant message a turn (`packages/chat/src/live/persistence.ts:170-185`). It also does not state the outcome for an oversized newest unit, an incomplete user-only exchange, or whether the 8k estimate includes replay framing. The cited estimator is deterministic but approximate (`packages/chat/src/live/recall-seed.ts:28-31`).
   - Fix direction: define the replay unit, exact serialized bytes fed to the estimator, tie/order rules, and the oversized/incomplete cases with one normative example.

6. **Severity: major — Incognito and user opt-out checks are promised but have no pre-retrieval source-of-truth seam.**
   - Evidence: the draft requires notes retrieval to be skipped entirely for incognito and mentions a config opt-out (`...1553-context-continuity-and-notes-retrieval.md:116,138-140`). Today `buildEngineText` invokes passive retrieval for every turn (`packages/chat/src/live/engine-text.ts:39-74`), `getThreadContext` does not return privacy state (`packages/chat/src/live/persistence.ts:354-371`), and `PassiveContextRetriever` has no incognito input while it does gate on existing `recallEnabled`/`factsEnabled` settings (`packages/chat/src/live/passive-retrieval.ts:101-125`). The spec never says how those user settings apply to notes.
   - Fix direction: require a server-truth privacy/recall decision before any notes query, define the existing settings' semantics, and test that the notes port is not called when disabled or incognito.

7. **Severity: major — The acceptance criteria do not falsify most of the normative contract.**
   - Evidence: criteria 1 and 3 rely on a model reply "demonstrating" context or answering from a note (`...1553-context-continuity-and-notes-retrieval.md:123-130`), which is nondeterministic. No criterion covers the 1,000-token summary cap, explicit replay `0`, stale/overlapping summary behavior, 500 ms timeout, 5-snippet/2,000-token bounds, retrieval failure, secret exclusion, modified-time provenance, owner scoping, or disabled recall.
   - Fix direction: add deterministic fake-engine/notes-port assertions for exact engine input and failure/privacy cases, keeping the real-model scenario only as live-path evidence.

8. **Severity: minor — Four source citations do not hold at the cited commit.**
   - Evidence: `launchSession` is `packages/chat/src/live/chat-session-manager.ts:212-295`, and `listPriorTurns` is called at `:246`, not the draft's `:210-283`/`:244`; `vaultReadOnlyToolPatterns` is `packages/chat/src/live/vault-allowlist.ts:18-25`, not `:17-24`; and no `DEFAULT_MOSS_PERSONA` exists at `packages/chat/src/live/runtime.ts:65-76`—the code has `MOSS_PERSONA_BASE` at `:65-66` and composition at `:85-89`.
   - Fix direction: update the ranges and name the actual persona composition seam.

### Investigated and judged INVALID

1. **Severity: INVALID — Dynamic notes injection does not conflict with prompt-cache discipline.**
   - Evidence: the standing persona rule is static, while the snippets are composed into each turn. That matches `docs/DEVELOPMENT_STANDARDS.md:127-135`, which requires dynamic context in turns rather than persona files.
   - Fix direction: none.

2. **Severity: INVALID — Reserved-delimiter prompt fencing is not absent.**
   - Evidence: `renderRetrievedContextBlock` labels recalled text as context and says to ignore embedded commands (`packages/chat/src/live/passive-retrieval.ts:180-203`), and `neutralizeSeedFraming` blocks reserved-tag and role-marker breakout (`packages/chat/src/live/prompt-safety.ts:17-32`). This does not cure finding 3's secret-content problem.
   - Fix direction: none; require the new notes path to use this existing fence.

3. **Severity: INVALID — The existing `notes.search` path is not an RLS bypass.**
   - Evidence: `notesSearchExecute` requires `DataContextDb` before retrieval (`packages/notes/src/tools.ts:34-51`). The risk is an unspecified new cross-module seam, not a demonstrated flaw in current owner scoping.
   - Fix direction: none; preserve this scoped boundary.

## #1554 — Persistent provider chat runtime

**Verdict: REVISE**

1. **Severity: blocker — Crash recovery has two competing sources of conversation truth and no provider-session identity rule.**
   - Evidence: the draft drops `--no-session-persistence`, adds `--session-id`, and calls the DB transcript authoritative (`2026-08-10-1554-persistent-provider-chat-runtime.md:104-121`), then requires relaunch with #1553 replay (`:130-134`). The spike says dropping the flag makes the provider session resumable (`2026-08-10-1554-phase0-spike.md:88-94`) but explicitly excluded bounded DB replay (`:3-5`). The spec never chooses among resuming the old provider transcript, replaying DB history into a fresh provider session, or doing both; doing both duplicates and bypasses the bounded context contract.
   - Fix direction: choose one source—prefer a fresh provider session ID per child plus bounded DB replay—and specify old transcript cleanup/adoption rules.

2. **Severity: blocker — "Relaunch once per turn" can duplicate an accepted turn or an already-executed write.**
   - Evidence: the draft automatically relaunches once after unexpected child exit (`...1554-persistent-provider-chat-runtime.md:130-134`) but does not define whether the current user frame is resubmitted. Current code deliberately distinguishes delivery-unknown from verifiably-unavailable and refuses to resubmit the former (`packages/chat/src/live/chat-session-manager.ts:433-447`). A write may execute after approval before a terminal result exists (`packages/ai/src/gateway/gateway.ts:580-626`), so replay plus resubmit is not safely idempotent.
   - Fix direction: retry only when pre-acceptance failure is provable; otherwise fail the turn neutrally, or first define end-to-end idempotency for every side effect.

3. **Severity: blocker — Initial/recovery MCP handshake failure still permits the exact tool-less successful turn that produced the incident.**
   - Evidence: the draft launches with `--strict-mcp-config` and derives health from result fields (`...1554-persistent-provider-chat-runtime.md:91-92,107-113`). The spike proved an unreachable configured server yields exit 0, `success`, `is_error:false`, no tools, and model-generated lifecycle prose (`2026-08-10-1554-phase0-spike.md:143-170,203-209`); `--strict-mcp-config` does not fail closed. Persistence removes per-turn handshakes but not launch/relaunch handshakes.
   - Fix direction: make child admission fail closed on a server-side required-tool handshake/readiness signal before any user frame, returning a neutral Moss error if readiness is absent.

4. **Severity: blocker — Cancel can leave a pending approval able to execute after the child is terminated.**
   - Evidence: v1 cancel is terminate plus relaunch (`...1554-persistent-provider-chat-runtime.md:69-70,90`), while approval remains a blocked gateway waiter (`:135-138`). In current code, confirmation waits independently of the child (`packages/ai/src/gateway/confirmation-registry.ts:15-30`), and a later confirmation runs the handler (`packages/ai/src/gateway/gateway.ts:548-609`). The spec does not bind cancel/process death to that waiter or pending action row.
   - Fix direction: cancel and terminally resolve every pending action for the session before killing/relaunching, and prove a late Approve cannot run the tool.

5. **Severity: blocker — Idle reap and LRU eviction lack an atomic "idle" definition and an all-children-busy policy.**
   - Evidence: the draft evicts the LRU idle child at cap and reaps after no activity (`...1554-persistent-provider-chat-runtime.md:125-138`), but it does not say that an in-flight turn or pending approval is non-idle, how launch races a state change, or what happens when all four children are busy. Current turn serialization and maintenance are separate mechanisms (`packages/chat/src/live/chat-session-manager.ts:330-359,784-802`); the configurable idle window can also be shorter than the existing 150-second confirmation wait (`packages/chat/src/live/claude-permission-hook.ts:17-19`).
   - Fix direction: define one lifecycle lock/state model where in-flight/approval states are never eviction candidates, recheck state atomically before kill, validate settings, and specify queue/reject/fallback when no idle child exists.

6. **Severity: blocker — Incognito cleanup is missing even though the adapter explicitly enables provider transcript persistence.**
   - Evidence: #1553 requires an incognito relaunch to remember nothing (`...1553-context-continuity-and-notes-retrieval.md:94-95`). #1554 drops `--no-session-persistence` (`...1554-persistent-provider-chat-runtime.md:115-121`) without defining incognito provider-session IDs, resume/adoption, or purge on crash/reap/cancel. Current launch refuses private chat unless the engine implements transcript purge (`packages/chat/src/live/chat-session-manager.ts:248-253`).
   - Fix direction: keep provider persistence off for incognito or guarantee fresh IDs plus purge on every termination path, and add disk-level/relaunch verification.

7. **Severity: major — The rollback flag cannot meet "without restart" for already-warm children as written.**
   - Evidence: engine selection consults the flag only when choosing an implementation (`...1554-persistent-provider-chat-runtime.md:96-100,154-162`), while acceptance criterion 5 says flipping it off returns the surface to one-shot without restart (`:175`). No policy says whether warm children are killed, drained, or allowed to remain, especially during an in-flight turn or approval.
   - Fix direction: define flag-off as a lifecycle transition—block new persistent launches, drain current turns, then reap/revoke warm children—and test both idle and in-flight flips.

8. **Severity: major — "Instance-wide" pool ownership is undefined across the two engine composition roots.**
   - Evidence: the draft puts the neutral contract in the session manager and caps warm children instance-wide (`...1554-persistent-provider-chat-runtime.md:81-100,123-129`). Source documents two engine-building roots—the in-process runtime and the cli-runner used by container deploys—and says divergence previously caused a full outage (`packages/chat/src/live/engine-selection.ts:1-15`). The spec does not identify which process owns the authoritative child registry/LRU or how adoption/reconnect preserves the count.
   - Fix direction: assign pool/LRU ownership to the process that owns child PIDs and route both composition roots through the single existing engine-selection seam.

9. **Severity: major — Extending `launchStructured` without a bounded stream decoder creates unbounded memory growth.**
   - Evidence: the draft says to extend that transport and parse events continuously (`...1554-persistent-provider-chat-runtime.md:102-121`). The current implementation appends every stdout chunk forever to `structuredOutput` (`packages/chat/src/live/claude-print-chat-engine.ts:84-109`) and repeatedly slices it (`:126-141`). The #1554 Buzz comparison comment explicitly required bounded JSONL parsing, but the spec omits frame/buffer limits, malformed-line behavior, and EOF-without-terminal handling.
   - Fix direction: require a consuming incremental line decoder with maximum frame/buffer sizes and explicit malformed/EOF failure behavior.

10. **Severity: major — Acceptance dropped the required gateway-interruption scenario.**
    - Evidence: issue #1554's Acceptance direction says, "Forced gateway interruption recovers once without rendering lifecycle instructions as assistant prose." The draft instead tests forced provider interruption and relaunch (`...1554-persistent-provider-chat-runtime.md:171-172`). The spike's gateway/MCP interruption recovered on the same child and exposed stale init status (`2026-08-10-1554-phase0-spike.md:172-188`), which is a distinct behavior.
    - Fix direction: retain the child-death test and add a gateway-down/restart test proving same-process recovery, continuing tool exposure, and no host lifecycle prose.

11. **Severity: minor — The approval timeout citation is wrong.**
    - Evidence: the draft cites `gateway.ts:430` as the fail-closed timeout guard (`...1554-persistent-provider-chat-runtime.md:135-138`), but that line is the JSDoc for `resolveActionRequest`; the waits are at `packages/ai/src/gateway/gateway.ts:332-335` and `:548-551`, and the actual timer is `packages/ai/src/gateway/confirmation-registry.ts:15-30`. The `claude-print-chat-engine.ts:84-110` citation is correct.
    - Fix direction: cite the waiter/timer and state the configured timeout value/ordering invariant.

### Investigated and judged INVALID

1. **Severity: INVALID — Vendor naming in the adapter section is not a provider-agnostic blocker.**
   - Evidence: the binding #1554 comment permits vendor names in adapter code, provider settings, operator diagnostics, and provider-specific tests. The draft states the same boundary (`...1554-persistent-provider-chat-runtime.md:75-79`) and keeps product/acceptance language neutral.
   - Fix direction: none.

2. **Severity: INVALID — The acceptance criteria do not rely on per-turn `system/init` counts or stale `init.mcp_servers`.**
   - Evidence: criteria explicitly require process identity/server-side handshake counts and forbid those two signals (`...1554-persistent-provider-chat-runtime.md:166-177`), matching the spike (`2026-08-10-1554-phase0-spike.md:124-139,185-200`).
   - Fix direction: none.

3. **Severity: INVALID — The ineffective `--allowedTools` restriction is not ignored.**
   - Evidence: the draft correctly calls `PreToolUse` the sole effective deny-by-default guard (`...1554-persistent-provider-chat-runtime.md:50-52,180-183`), matching the spike (`2026-08-10-1554-phase0-spike.md:192-204`).
   - Fix direction: none.

4. **Severity: INVALID — Static persona launch plus per-turn notes injection is a coherent seam.**
   - Evidence: #1553 puts only a standing rule in the persona and injects snippets during each turn (`...1553-context-continuity-and-notes-retrieval.md:99-116`), while #1554 keeps persona at launch and sends one user frame per turn (`...1554-persistent-provider-chat-runtime.md:104-121`). This is compatible with the prompt-cache rule that dynamic content follows launch.
   - Fix direction: none.

## Fable dispositions (2026-08-10, post-review)

Every valid finding is **ACCEPTED**; both specs revised in place the same day. The four+3 INVALID
findings stand as ledger entries — do not re-derive them. Per finding, how it landed:

### #1553

1. ACCEPTED — replay knob decoupled from summary generation; summary is read-only under this spec
   (present ⇒ prepended capped at 1,000 tokens; absent ⇒ nothing written, nothing synthesized).
   Decoupling has its own acceptance test (no write to `conversation_summary`).
2. ACCEPTED — replay is persisted user/assistant **text only**; tool calls/results are explicitly
   out of replay (no persisted source exists; adding one would need its own sanitized-history
   spec). Stated in the order-and-shape rule.
3. ACCEPTED — fail-closed sensitive-content filter before injection; suspect snippet dropped and
   logged, never truncated-and-kept; regression test that credential-shaped note content never
   reaches engine input. Pattern set is a plan decision; fail-closed disposition is spec-fixed.
4. ACCEPTED — declared public notes-recall port beside the `notes.search` tool boundary; result
   contract = owner-scoped relative path, modified time, score, sanitized text.
5. ACCEPTED — replay unit defined as one persisted message; bounds 40 messages / 8k tokens;
   oldest-whole-message truncation; oversized-newest truncated head-first tail-kept; unpaired
   user-only message replays as-is; chronological order; normative example added.
6. ACCEPTED — server-truth gating seam: `getThreadContext` extended to carry privacy state; notes
   path obeys existing `recallEnabled` identically to graph recall; disabled/incognito ⇒ port
   never called, asserted at the port.
7. ACCEPTED — acceptance criteria rebuilt around deterministic fake-engine and fake-notes-port
   input assertions; live-model scenarios kept only as live-path evidence.
8. ACCEPTED — all four citations corrected (`launchSession :212-295`/`:246`,
   `vault-allowlist.ts:18-25`, `MOSS_PERSONA_BASE` runtime.ts:65-66 composed `:85-89`).

### #1554

1. ACCEPTED — provider-session identity rule added: DB transcript is sole truth; provider
   transcript never resumed/adopted; fresh provider session per launch + bounded DB replay.
   Preferred posture keeps `--no-session-persistence` (its compatibility with persistent
   stream-JSON is a bounded phase-1 verification item — the spike never tested the combination);
   fallback is fresh `--session-id` per launch + purge on every termination path.
2. ACCEPTED — auto-resubmit only when provably pre-acceptance (child died before accepting the
   frame, zero tool activity); delivery-unknown ⇒ neutral turn failure, never silently retried;
   mirrors `chat-session-manager.ts:423-440`.
3. ACCEPTED — fail-closed admission: server-side MCP readiness (session initialized + required
   tools listed) before the first user frame; no readiness ⇒ destroy child, neutral error.
4. ACCEPTED — cancel/termination terminally resolves every pending action request before kill;
   late-Approve-cannot-execute is an acceptance test.
5. ACCEPTED — explicit child state model (`launching → ready → (in-turn | awaiting-approval |
   idle) → reaping`); only `idle` reapable/evictable; atomic state re-check under per-child lock;
   all-busy ⇒ that turn runs on the bounded-fallback engine (no queueing, no evicting busy
   children).
6. ACCEPTED — incognito lifecycle bullet: no resumable provider transcript (or purge on every
   termination path in fallback posture); relaunch replays nothing; purge-guard refusal stays;
   disk-level acceptance check.
7. ACCEPTED — flag-off defined as a lifecycle transition (new launches → fallback immediately;
   in-flight turns drain; warm children reaped, tokens revoked); both flip cases tested.
8. ACCEPTED — pool/LRU ownership assigned to the PID-owning process; both composition roots via
   the single engine-selection seam.
9. ACCEPTED — bounded incremental stream decoder required (max frame + buffer bounds, malformed
   line skipped+logged, bound exceeded ⇒ kill child + neutral failure, EOF-without-terminal ⇒
   neutral failure); `launchStructured`'s accumulate-forever buffer must not be reused as-is.
10. ACCEPTED — gateway/MCP-restart acceptance scenario restored (same-child recovery, tools
    continue, zero lifecycle prose) alongside the child-death test.
11. ACCEPTED — approval-timeout citations corrected to `confirmation-registry.ts:15-30` +
    `gateway.ts:332-335`/`:548-551`.
