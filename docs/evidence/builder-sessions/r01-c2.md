## 5. Counting rules

- C1. Denominator: every eligible owner-requested attempt accepted for execution inside the fixed window. "Accepted for execution" means the owner asked and the system took the request as an attempt (a request id or attempt record exists).
- C2. Failures, timeouts, unresolved and unfinished attempts stay in the denominator. An attempt still open at the end of its window is counted as unresolved. It is never removed.
- C3. Retries count once. A worker retry shares the user attempt id and has its own execution id. A new owner request is a new attempt, even if it repeats an earlier one.
- C4. A later passing attempt supplements an earlier failure. It never replaces it. Both stay in the report.
- C5. Refusals before acceptance (for example, consent not given for the window) are listed separately and are not counted as executed attempts.
- C6. Correct silence is reported separately with its inclusion rule fixed beforehand: it counts as a success only when silence is the declared expected result (S7-a). Silence on a case that expected output is a failure. User-cancelled attempts are also reported separately. Inclusion rule: an owner-cancelled attempt is in the denominator (it was accepted, C1), is not in the verified-outcome numerator, and is shown as its own line in T3. It is also in the S4 and S14 case results because those test the cancel itself. Every ratio is shown twice, with the cancelled and silent attempts in the denominator and with them removed, each with its numerator and denominator spelled out. An owner-cancelled attempt that correctly stays quiet is a cancelled attempt, never S7 correct silence. S4-b has its own count lines: cancelled with no effect, and delivered once with the cancel reported too late. C2's "unresolved at window end" does not apply to a cancelled attempt, which is closed by the cancel and checked for effects through the S4 window.
- C7. Stage reporting: trigger, accepted send, durable in-app result and externally observed receipt are four different stages and each is reported on its own. A durable result is not a receipt. Unread-row absence is not receipt.
- C8. A case is one of pass, fail or not run, per branch, against the exact commit. Unrun is never pass. Zero failures seen in an unrun case is not a pass. Excluded rows are listed with their reason and never counted as pass.
- C9. A case passes only when its declared evidence is on record and no forbidden effect was seen. Absence of output alone is not evidence of no effect.
- C10. A result is valid for one target and one build. No result transfers across a target, a commit or a rules version.
- C11. Zero tolerance for applicable cases: any unauthorized action, cross-owner exposure, consent failure, lost record, duplicate consequential effect or false completion is a fail of that case and triggers the hard stop (section 7).
- C12. No quality or latency threshold is set here. Baselines come first.
- C13. Not run carries a reason from a fixed list: `no device`, `not in claimed scope`, `open choice (a-d)`, `blocked by hard stop`, `environment`, `not reached`, `limitation`. Free text may be added but the code is required.

## 7. Hard stops (shared, unchanged)

The universal stop rule from the roadmap applies to every case. Stop the affected path for unauthorized action, consent failure, data exposed between users or product areas, lost records, duplicate consequential effects or false completion. If the cause is shared or containment is uncertain, dependent work stops. An independent reviewer and the coordinator establish what is safely separate before anything resumes. No lane approves its own exception. A stop is recorded as the case result `fail` for the triggering branch and `not run (blocked by hard stop)` for branches that depend on it. Issue #3078 clean-launch behavior does not stand in for the broader injection agreement.
