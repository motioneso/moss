## Verdict: accept with changes

The source trace is accurate where I checked it, and the proposed agreement is conservative and
does not widen access. It cannot be accepted as a finished map of the current app until the
changes below are made, mainly because main has moved and the report's "identical" claim no
longer holds.

## Claims confirmed against current main

1. Launch taint. `launchChatSession` calls `admitOutsideAgentLaunch` when the engine sets `admitsOutsideContentWithoutPermission`; only the ACP engine sets it. The taint is recorded before recall and replay. Memory seed is admitted as `launch_memory_seed` and blank text returns null. (`chat-session-launch.ts` ~178-196, `acp-chat-engine.ts` 420.)
2. Launch replay refusal. `isInLaunchReplay` is enforced in three places: gateway call preparation, the native permission handler and the ACP built-in permission path. This is the accepted #3078/#3335 narrow behavior and is preserved.
3. Post-launch seed. `seedChatContext` admits (`seed_route` or `evening_seed`) before submit, then adds the idempotency key to an in-memory set only after the drain. So two overlapping calls with the same key can both submit. The report says it is not a durable dedupe; that is correct, and it is the #3339 gap.
4. Background read. `runBackgroundReadForActor` refuses anything except `tasks.get`, requires a read-risk tool with a background-read hook, and refuses per-call executors. `authorizeTaskBackgroundRead` requires exactly one `taskId` and `owner_user_id === actor`, so a shared foreign task fails. The runner rereads owner, state, version and destination before the read, after generation and at commit. A changed title or status produces the "source changed" failure instead of a report.
5. Hostile text in the report model. The report generator's prompt marks the title as untrusted, and the output schema is three fixed fields with a 600-character summary. The generator call carries no tools. This supports "model output is report data".
6. Destination. Reminder destinations resolve only among the actor's own non-private drawer threads and are locked again at delivery.
7. App actions. The resolver refuses blocked routes and consent mismatch before target lookup; the refusal text says approval cannot enable consent. The act-as grant lifetime is 30,000 ms.
8. Open exposure. The spec still says Ben has not ruled on non-YOLO trusted add-on writes reaching declared hosts after hostile content. C1 correctly leaves this as Ben's choice.
9. No `packages/extensions` exists, so "guest isolation is specification only" is still true.
10. All ten listed test files exist on main. None was run by C1 or by me.

## Findings

F1 (must fix) - Stale pin and a false "identical" statement. C1 line 9 says the cited
launch, ACP and gateway files are identical between its pin and main. That was true for the pin
it chose and is not true now. Four cited files differ at `ff07aff5b`:

- `chat-session-launch.ts` now resolves an API-key credential before launch, passes it to the engine, and opens a thread through a new helper.
- `acp-chat-engine.ts` has a new API-key path (credential passed into the spawn, key-rejection handling, masked launch errors).
- `gateway.ts` call preparation now takes identity through `captureToolCallContext`. I read it: it still verifies the token and captures actor, session, thread and turn before any await. The guard is intact.
- `tasks/src/tools.ts` changed only in the Focus tool (adds a today summary); the background-read check is unchanged.

I read all four diffs and found nothing that weakens a cited guard. The report must still be
re-anchored to a current commit, and its "identical" sentence rewritten.

F2 (must fix) - Source-entry routes added since the pin are not mapped. C1 cannot have covered
these. They need a line each in the admission table, even if the answer is "not an agent-visible
source":

- API-key chat launch credential (new input to the spawned agent).
- Outlook browser calendar mirror (`source-context/calendar.ts`). I saw it checks the per-account feature grant and marks mirrored rows read-only and possibly unconfirmed, and the connector tools are declared `content: "outside"`. I did not trace the full path.
- Voice requests, the visual present tool, companion device pairing and session invalidation, and the constrained Codex profile (which may now serve structured calls such as the scheduled-report generator).

F3 (must fix) - The four safety cases are not mapped one by one. The packet checklist asks for
every S8, S9, S10 and S12 branch (definitions in the roadmap file, lines 223-224). C1 lists
negatives in prose but does not tie them to those labels, and two branches are thin.

- S8, consent revoked during read, write or retry: C1 covers the approval wait and dispatch re-check. It does not say what a retried scheduled read does after the Tasks module or its AI consent is switched off. The runner re-checks the reminder, not module consent itself; refusal depends on the gateway's tool listing. That is plausible but no cited test proves it.
- S10, corrected, disconnected, missing and stale evidence: only "stale version" and "descriptor drift" appear. The runner's "source changed" and read-failure outcomes, and the Outlook stale/unconfirmed flags, are the real stale-evidence behavior and are not cited.
- S9 and S12 are adequately covered in prose. Name them explicitly.

F4 (must fix) - "Old data or old permissions restored" is not addressed. The task requires that
outside content never create approval when old data or permissions return. C1 does not say
whether restoring a conversation, a revoked consent, or an old approval card clears the outside
content mark or revives a pending approval. The mark is described as durable and approvals as
single-use with live waiters, which points the right way, but this is unexamined, not shown.
Add it as an explicit negative case (and tie it to S13 restore).

F5 (should fix) - Evidence from outside the sandbox is relied on without a re-check. The
rulings from #3135, #3338, #3419, #3523 and the closed/open status of #3078, #3085, #3339,
#3340, #3335, #3514 come from GitHub, which I was not allowed to contact. I could not confirm
them and I did not find newer local commit titles mentioning them. Treat them as unreconfirmed
until the coordinator rereads them at the new commit.

F6 (minor) - Process notes. C1 says it extracted a ZIP into the checkout and used Tailscale's
pending-file interface, which the original task did not authorize. It records this openly and
says it was on user instruction; the coordinator should confirm that instruction. It also lists
Hindsight and Obsidian reads, which are fine for read-only work. Line anchors in the report are
to the old pin, so they remain valid permalinks but not current-line references.

No bypass of the kind "outside content creates approval" was found in the code I read. That is
a statement about the checked paths only.

## Three separate decisions (replay at startup, preconfigured starting data, provider-scheduled work)

C1 keeps them apart and I agree: launch replay is refused for Moss tools (S12 / #3335); starting
data after launch is admitted and marked but can still provoke a card (#3339, unproved); provider
self-scheduling and callback-free operations are outside the proof (#3340). Nothing in main
merges them. Note that the Claude wakeup case was observed in a past proof only and is not
established for other providers.

## Unresolved choices that remain for Ben

1. Whether non-YOLO trusted add-on writes may reach declared hosts after hostile content (spec still undecided).
2. Only if the controlled case demands it: tighten "no source-influenced action" to an absolute ban, which would override the accepted read-only check and owner-trust rulings.

Everything else listed in C1 is already ruled.
