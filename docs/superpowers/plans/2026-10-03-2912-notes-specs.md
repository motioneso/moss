# #2912 — notes browser tests fail on main

Both failures reproduced on `fix-2912-notes-specs` (base `a968e0a1f`). Neither is a notes defect.
Both are test-environment drift.

## Findings

### notes-path-recheck (line 171) — stale test, fails every run

- The spec plants symlinks with `docker compose exec -T jarv1s sh -c "ln ..."`, which runs as root.
- Since #2424 (`dcc42b672`) the `jarv1s` service runs `cap_drop: [ALL]` plus
  `CHOWN, SETUID, SETGID, FOWNER, KILL`. Root has no `DAC_OVERRIDE` / `DAC_READ_SEARCH`.
- The vault dir `/data/vaults/<user>` belongs to the runtime uid. Root cannot traverse it:
  `ln: failed to access '/data/vaults/<id>/D-<stamp>': Permission denied`.
- Part (a) of the spec (real notes.create/edit/delete through chat) passes, so the product path
  works.

### notes-default-retrieval (line 152) — container OOM, fails 2 of 3 runs

- Run 1 passed; runs 2 and 3 failed. The browser shows "Failed to fetch" on the retrieval turn.
- Server log: `cli-runner exited { code: 137 }` in one run, `api exited { signal: 'SIGKILL' }` in
  the other. Kernel log: `Memory cgroup out of memory: Killed process ...` against the UAT
  container's cgroup.
- Per-process sampling inside the container at the peak (3.83 GiB of the 4 GiB cap):
  - `dist/server.js` 1.85–2.0 GB. Jumps by ~1.2 GB when passive notes retrieval loads the local
    embedding model (`nomic-ai/nomic-embed-text-v1.5`, fp32) for the retrieval turn.
  - `dist/worker.js` 1.26–1.78 GB. Same model, loaded for the notes sync.
  - `npm ci` ~300 MB (CLI tool install at boot), codex ~250 MB, rest small.
- The 4 GiB cap is test-only (`tests/uat/compose.override.yml`, added 2026-09-06 in #2353).
  The production compose sets no memory limit on `jarv1s`.
