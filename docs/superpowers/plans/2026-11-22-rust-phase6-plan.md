**Determinism boundary.** Every permission, warning, acknowledgement, progress stage and result
renders from validated host records, never model prose. Modules do not inject chat turns.
The model has no role in these management flows (neither approval nor copy generation); the
skill's two-job model budget is unused. No model-authored values cross into user data.

**Chosen approach.** Complete the existing Rust host/client and expose management records through
its authenticated server. A new registry stack would simplify naming but duplicate proven trust,
SQL and rollback logic. Reusing the legacy TypeScript publisher could reuse deployment credentials,
but emits the wrong archive/index contract and cannot establish `.mosspkg` trust; keep it serving
legacy installs while a separate Rust artifact pipeline is verified. No marketplace, Workshop,
Food, module redesign, real installer work or production cutover belongs here.

### Verification policy for builders

Each part names a new integration/e2e test above, not a claim that it already exists. Builders
register a focused runner in that part and record its exact unpiped command and exit 0 before
handoff. Backend e2e uses real host/server/CLI with signed fixtures and isolated data; screen e2e
uses a real dev instance and Playwright with no intercepted successful API responses. Every
security claim includes a negative control seen fail when its guard is removed.

Read `.claude/skills/verify-gate/SKILL.md` before DB-touching checks. Existing focused gates for
part 10 (expected final exit 0, each separately; asynchronous `start` also requires inspecting its
completion/result):

```bash
scripts/run-gate.sh start --gate test:rust-finance
scripts/run-gate.sh start --gate test:rust-finance-live
scripts/run-gate.sh start --gate test:rust-meals
```

Set `RUSTUP_HOME` explicitly and isolate `CARGO_TARGET_DIR`; guest and host builds use different
subfolders. No verification command is piped. A launcher exit is not a passing gate. Full
foundation/installed gates belong to later build tasks, **not this docs-only planning task**.

**Kill gate after part 1.** Coordinator observes a real signed package installed through the
new digest-bound contract and refusal of stale review without losing the old module/data.
If the current shell child-process boundary cannot support that, stop detailed downstream design
and resize/rework the service seam with the coordinator. No duplicate installer is quietly built.
Other hard stops: local ownership escape, revocation still callable after refresh/restart, offline
bundle needs network, or unresolved Finance interface/test gate. Ben decides interface exceptions;
the coordinator owns sequencing and evidence, never silently waives the gates.
