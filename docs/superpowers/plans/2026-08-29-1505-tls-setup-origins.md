## Decisions

**D1 — Where the TLS logic lives.** All of it goes in `scripts/setup-prod-origins.ts`. A separate
`scripts/setup-prod-tls.ts` would be outside this lane's file ownership, and the existing file is
already the "pure helpers extracted so tests do not trigger the script's eager secret generation"
module (its header comment, lines 1-5). Rejected alternative, steelmanned: a dedicated TLS module
would read better and keep each file single-purpose — but it costs an ownership violation and a
coordinator round-trip to buy naming, and the combined file lands near 200 lines against a 1000-line
cap. Not worth it.

**D2 — Host validation is an allowlist, not a denylist.** A DNS label allowlist rejects every
forbidden class the spec lists (scheme, userinfo, port, path, query, fragment, wildcard,
whitespace, newline, comma, brackets, Caddyfile placeholders and metacharacters) as a side effect of
only permitting `A-Za-z0-9` and `-`, and it cannot be defeated by a character class somebody forgot.
A denylist of forbidden characters is one omission away from passing `jarvis.lan;evil` into a
Caddyfile. Rejected alternative, steelmanned: a denylist yields a much more actionable error
message ("host must not contain a port"). Resolution: keep the allowlist as the decision-maker, and
when a rejected host contains a character from a known-bad set, name that class in the message.
The allowlist still decides; the denylist only chooses wording.

**D3 — IPv4 is validated after the allowlist, not before.** A dotted-quad matches the DNS allowlist,
so `isIP(host) === 4` is checked afterwards to apply the issuer rule: an IPv4 literal is valid only
with `internal`, and `acme` plus any IPv4 literal is rejected (spec lines 128-129). IPv6 in either
form is rejected by the allowlist itself — bare because of the colons, bracketed because of the
brackets.

**D4 — The issuer union is exact and case-sensitive.** Only the literals `internal` and `acme` are
accepted; an unset or blank issuer defaults to `internal` (spec table, line 133-136). `Internal`
is rejected. The value is written verbatim into the env file and read by the Caddyfile, which does
not case-fold; accepting a variant here would generate config that setup thinks is valid and Caddy
does not.

**D5 — The Caddy proxy IP is the last usable address of the configured subnet.** For the default
`10.251.0.0/24` that is `10.251.0.254`; for `10.42.0.0/24`, `10.42.0.254`; for `172.30.0.0/16`,
`172.30.255.254`. Docker's IPAM hands out dynamic addresses from the low end of the range and
reserves the first address as the gateway, so pinning the top address avoids colliding with a
dynamically assigned container regardless of start order. Rejected alternative, steelmanned:
pinning `.2` is the conventional, more readable choice and is what most compose files do — but it
is exactly the first address Docker's dynamic allocator hands out, so a container that starts
before Caddy can take it and Caddy then fails to attach. A non-deterministic startup failure in a
production TLS path is a worse trade than a less pretty address. Subnets narrower than `/30` and
any non-IPv4 CIDR are rejected rather than guessed at.

**D6 — Emitted key names.** `JARVIS_TLS_HOST` and `JARVIS_TLS_ISSUER` are emitted and read under
their literal `JARVIS_*` names, using plain `process.env` rather than `resolveMossEnv` — the same
treatment `scripts/setup-prod.ts` already gives `JARVIS_WEB_PORT` (line 58) and `JARVIS_IMAGE_TAG`
(line 75). Compose interpolates `${JARVIS_TLS_HOST}` host-side and the Caddyfile reads
`{$JARVIS_TLS_HOST}`; neither can see a `MOSS_*` rename, so emitting `MOSS_TLS_HOST` would produce
an env file that renders an empty Caddy site address. The trust value is emitted as
`MOSS_TRUST_PROXY`, matching how the script already emits `MOSS_AUTH_BASE_URL` and
`MOSS_AUTH_TRUSTED_ORIGINS` (lines 121-122) and matching the shim-aware read at
`apps/api/src/server.ts:193`. This resolves Q2: no `CARVE_OUT` edit is required for correctness,
because the two TLS names never pass through the shim. File a follow-up issue to add them to the
carve-out set and its spec doc for consistency.

**D7 — The `JARVIS_*` prefix in `infra/env.production.example` is left alone.** That file is
uniformly `JARVIS_*` today and the shim accepts both spellings. Renaming its keys is a
whole-file change belonging to the rename work, not to a TLS issue. The new TLS block follows the
file's existing convention.

**D8 — Validation runs immediately after the no-overwrite guard.** The TLS resolve and the origins
derivation move above the `randomBytes` block so invalid input exits before any secret is generated
and long before the single `writeFileSync`. The no-overwrite guard stays the very first check, so
an existing file still wins over every other outcome. New exit code **3** for a TLS/origin config
error (1 and 2 are taken).

**D9 — The override check throws from inside `deriveTrustedOrigins`.** Folding "an explicit
override that omits the requested HTTPS origin is fatal" into the same function keeps one call site
in `setup-prod.ts` and makes the fail-closed path provable by a pure-helper test. It can only throw
when the new optional `httpsOrigin` field is supplied, so `tests/uat/provisioner.ts:213`, which
never supplies it, is unaffected.

**D10 — Override membership is compared after trailing-slash normalisation, but case-sensitively.**
`https://jarvis.lan/` in the override counts as the origin being present. `https://JARVIS.LAN` does
not. Better Auth's origin check is an exact string match, so accepting a case variant would produce
exactly the failure the spec forbids: a deployment that starts cleanly and then returns 403 on
sign-in.

## Contracts

New and changed exports in `scripts/setup-prod-origins.ts`:

```ts
export type TlsIssuer = "internal" | "acme";

/** Thrown for any invalid TLS host, issuer, subnet, or trusted-origin override. */
export class TlsConfigError extends Error {}

export interface TlsSettings {
  /** The validated host, exactly as the operator supplied it (trimmed). */
  readonly host: string;
  readonly issuer: TlsIssuer;
  /** `https://<host>` — no port, no path, no trailing slash. */
  readonly httpsOrigin: string;
  /** The exact static Caddy IPv4 address on the compose network. */
  readonly trustProxyIp: string;
}

export interface ResolveTlsSettingsInput {
  readonly host: string | undefined;
  readonly issuer: string | undefined;
  /** JARVIS_DOCKER_SUBNET, defaulted by the caller. */
  readonly dockerSubnet: string;
}

/**
 * Returns undefined when no TLS host was requested (unset or blank) — the unchanged
 * no-TLS path. Otherwise validates everything and returns the settings, or throws
 * TlsConfigError with an actionable message.
 */
export function resolveTlsSettings(input: ResolveTlsSettingsInput): TlsSettings | undefined;

/** Last usable IPv4 address of an IPv4 CIDR. Throws TlsConfigError on anything else. */
export function deriveCaddyProxyIp(dockerSubnet: string): string;

export interface DeriveTrustedOriginsInput {
  readonly webPort: string;
  readonly publicOrigin?: string;
  readonly override?: string;
  /** NEW, optional. When set, this exact origin must end up in the list or the call throws. */
  readonly httpsOrigin?: string;
}

/** Unchanged signature. Now throws TlsConfigError when httpsOrigin is set and an override omits it. */
export function deriveTrustedOrigins(input: DeriveTrustedOriginsInput): string;
```

Origin list order, no override: `http://localhost:<webPort>`, then the normalised `publicOrigin` if
any, then `httpsOrigin` if any — deduplicated in first-seen order, so a repeat collapses.

Generated env lines, emitted only when TLS is requested:

```
# TLS reverse proxy (opt-in; the `tls` Compose profile). Non-secret values.
JARVIS_TLS_HOST=<host>
JARVIS_TLS_ISSUER=<internal|acme>
# Exact static Caddy address on the jarv1s network — never the bridge CIDR or gateway.
MOSS_TRUST_PROXY=<ip>
```

`MOSS_AUTH_BASE_URL` does not change and is not derived from the TLS host (spec lines 186-187).

## Test cases

Each is stated as behaviour plus what a broken implementation would do.

**Host validation (`resolveTlsSettings`).** A broken implementation passes an attacker- or
typo-supplied string into a Caddyfile site address or an auth origin.

- `jarvis.lan` + `internal` → accepted, `httpsOrigin === "https://jarvis.lan"`. A derivation that
  appends a port or a trailing slash fails here.
- `jarvis.example.com` + `acme` → accepted.
- `192.168.1.50` + `internal` → accepted. An over-eager "hostnames only" rule fails here.
- `192.168.1.50` + `acme` → rejected. Public ACME cannot validate a reserved LAN address; an
  implementation that checks issuer and host independently passes this and fails at issuance.
- `fd00::1` and `[fd00::1]` → rejected, both forms. v1 excludes IPv6 so setup and Caddy cannot
  disagree about site-address parsing.
- `https://jarvis.lan` → rejected (scheme). `jarvis.lan:8443` → rejected (port).
  `user@jarvis.lan` → rejected (userinfo). `jarvis.lan/app` → rejected (path).
  `jarvis.lan?x=1` → rejected (query). `jarvis.lan#f` → rejected (fragment).
  `*.jarvis.lan` → rejected (wildcard).
- `"jarvis.lan b.lan"`, `"jarvis.lan\nb.lan"`, `"jarvis.lan\tb.lan"` → rejected (whitespace and
  newline). A regex without anchors passes the newline case.
- `jarvis.lan,b.lan` and `jarvis.lan;b.lan` → rejected (multiple-host separator).
- `{$FOO}`, `jarvis.{lan}`, `jarvis.lan$X`, `jarvis.lan|x` → rejected (Caddyfile placeholder or
  metacharacter).
- `-jarvis.lan`, `jarvis-.lan`, `jarvis.lan.` (trailing dot), a 64-character label, and a
  254-character total → all rejected. These are the label rules an unanchored "letters, digits,
  dots and dashes" regex lets through.
- Host unset, empty, or whitespace-only → returns `undefined`, throws nothing. This is the no-TLS
  path; an implementation that treats blank as invalid breaks every existing install.
- Every rejection carries a non-empty message. A thrown bare `Error` with no text leaves the
  operator with an exit code and nothing to act on.

**Issuer (`resolveTlsSettings`).**

- `internal` and `acme` accepted; unset or blank defaults to `internal`.
- `Internal`, `ACME`, `letsencrypt`, `internal,acme` → all rejected. A case-folding or
  `includes`-based check passes the first two and generates config Caddy rejects.

**Proxy IP (`deriveCaddyProxyIp`).**

- `10.251.0.0/24` → `10.251.0.254` (the default subnet).
- `10.42.0.0/24` → `10.42.0.254` (the spec's non-default-subnet check). A hardcoded
  `10.251.0.254` fails here.
- `172.30.0.0/16` → `172.30.255.254`. An implementation that only handles `/24` fails here.
- `not-a-cidr`, `10.251.0.0` (no prefix), `fd00::/64`, `10.251.0.0/32` → all rejected. Returning
  a malformed value would set `MOSS_TRUST_PROXY` to something `resolveTrustProxy`
  (`apps/api/src/server.ts:152`) throws on at boot — a container that will not start.

**Origins (`deriveTrustedOrigins`).**

- The ten existing cases still pass, unchanged. This is the "existing origin behavior preserved"
  deliverable.
- `webPort 1533`, `httpsOrigin https://jarvis.lan`, no publicOrigin →
  `http://localhost:1533,https://jarvis.lan`. Localhost must survive so on-box recovery works.
- With a publicOrigin as well → localhost, publicOrigin, then the HTTPS origin, in that order.
- `httpsOrigin` equal to the normalised `publicOrigin` → one entry, not two (deduplication).
- Override that contains the exact HTTPS origin → returned verbatim. Operator control is preserved.
- Override that omits it → throws. Without this the deployment starts and then 403s on sign-in,
  which is the entire point of the "no-lockout" title.
- Override containing `https://jarvis.lan/` → counts as present (trailing slash normalised).
- Override containing `https://JARVIS.LAN` → throws. Better Auth matches origins as exact strings.

**Subprocess cases** — run the real script with
`pnpm exec tsx scripts/setup-prod.ts <tmpdir>` from the repo root, with an explicit env, against a
fresh `mkdtemp` directory per case. A broken implementation passes every pure-helper test and still
writes the wrong file.

- **S1, valid TLS input.** `JARVIS_TLS_HOST=jarvis.lan`, `JARVIS_TLS_ISSUER=internal`, default
  subnet → exit 0, and `env.production.local` contains `JARVIS_TLS_HOST=jarvis.lan`,
  `JARVIS_TLS_ISSUER=internal`, `MOSS_TRUST_PROXY=10.251.0.254`, a
  `MOSS_AUTH_TRUSTED_ORIGINS` line whose comma-split members include exactly `https://jarvis.lan`,
  and `MOSS_AUTH_BASE_URL=http://localhost:3000`. That last assertion is the independent-base-URL
  contract: an implementation that "helpfully" points the base URL at the public HTTPS origin
  fails here.
- **S2, invalid input fails before any file exists.** `JARVIS_TLS_HOST=192.168.1.50` with
  `JARVIS_TLS_ISSUER=acme` → exit code is non-zero **and** `env.production.local` does not exist in
  the temp directory. An implementation that validates after `writeFileSync` leaves a half-valid
  secrets file behind and fails the second half of this assertion.
- **S3, an existing file is never replaced.** Write a sentinel `env.production.local` into the temp
  directory first, run with valid TLS input → exit code non-zero and the file's bytes are
  unchanged. This is the guard at `scripts/setup-prod.ts:25-34`; regenerating the secrets orphans
  every session and all encrypted connector/AI data.
- **S4, no TLS input.** No TLS variables set → exit 0, and the file contains
  `MOSS_AUTH_TRUSTED_ORIGINS=http://localhost:1533`, `MOSS_AUTH_BASE_URL=http://localhost:3000`,
  `JARVIS_DOCKER_SUBNET=10.251.0.0/24`, and **none** of `JARVIS_TLS_HOST`, `JARVIS_TLS_ISSUER` or
  `MOSS_TRUST_PROXY`. This is the prod-safety check: today's operators get today's file.

**Env-example assertion.** Read `infra/env.production.example` and assert that the
`JARVIS_AUTH_BASE_URL=` line's value is the in-container URL `http://localhost:3000` and not an
`https://` public origin, that the comment above it says so, and that the file declares
