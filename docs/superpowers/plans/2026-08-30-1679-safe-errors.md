# Issue 1679 — Per-tool safe handler errors

## Scope

Issue #1679 is the approved security decision: preserve a thrown `HttpError` message only for
tools that explicitly opt in. All other handler failures keep the existing generic response.
This is a security-tier change because the response can reach the model and chat.

## Seams check

- `ModuleAssistantToolManifest` is the shared tool contract at
  `packages/module-sdk/src/index.ts:565-635`; `externalContent` at lines 625-630 is the existing
  opt-in manifest pattern.
- `AssistantToolGateway.runHandler` is the shared handler-failure sink at
  `packages/ai/src/gateway/gateway.ts:603-673`; its catch currently logs the failure and returns a
  generic error at lines 654-671.
- `HttpError` is the existing safe-message type used by module handlers and is exported from the
  module SDK (`packages/module-sdk/src/route-errors.ts:12-20`, re-exported by
  `packages/module-sdk/src/index.ts:1-2`). The REST sink already returns its message only for
  `HttpError` at `packages/module-sdk/src/route-errors.ts:88-90`.
- The notes write tools use fixed, path-free `HttpError` messages, including the linked-source
  guard at `packages/notes/src/write-tools.ts:100-109`; their manifests are at
  `packages/notes/src/manifest.ts:111-164`.
- Gateway integration coverage already exercises handler failures and the real dispatch path in
  `tests/integration/mcp-gateway.test.ts`; notes manifest coverage is in
  `tests/integration/notes-write-tools.test.ts:98-158`.
- The existing live notes path proof is wired by
  `.claude/skills/coordinate/uat-trigger-map.tsv:34` and exercises the generic failure text at
  `tests/uat/specs/notes-path-recheck.uat.spec.ts:237-288`.

## Decisions

1. Add `readonly safeErrors?: true` to `ModuleAssistantToolManifest`. Omitted remains the safe
   default; `false` is not accepted, so an opt-in is visibly intentional.
2. In `runHandler`, after logging, return `error.message` only when both `found.tool.safeErrors`
   is `true` and the thrown value is an `HttpError`. Preserve the existing generic response for
   every non-opt-in tool, every non-`HttpError`, and hostile thrown value. Do not alter
   `runReadToolForActor`, which has its own fail-closed catch.
3. Set `safeErrors: true` only on `notes.create`, `notes.edit`, and `notes.delete`; the existing
   notes guard messages are already fixed and safe for this sink.

## Tests

- In `tests/integration/mcp-gateway.test.ts`, add gateway dispatch cases proving an opted-in tool
  returns its `HttpError` message, an omitted flag returns `Tool <name> failed`, and an opted-in
  tool throwing an ordinary `Error` with secret-looking text still returns the generic response.
  These fail against blanket unwrapping and against the current swallow.
- In `tests/integration/notes-write-tools.test.ts`, assert all three notes write tools opt in and
  the notes read tool does not.
- Update `tests/uat/specs/notes-path-recheck.uat.spec.ts` to assert the safe linked-source guard
  message for the two notes failure scenarios, while retaining its no-filesystem-path assertion.

## Kill gate

Stop after the first implementation and focused tests if the safe message contains any path,
credential, token, or private content, or if a non-opt-in/ordinary-error case is not generic. The
coordinator owns that security call.
