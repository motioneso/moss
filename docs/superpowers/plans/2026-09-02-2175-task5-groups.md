## Design

**Grouping algorithm** — new file `packages/integrations/src/derive-groups.ts`:

```ts
export function deriveGroups(names: readonly string[]): string[];
```

Returns one derived group name per input name, same order, never `""` (falls back to `"Other"`).
Implements the spec's 5 steps: segment split (upper-case boundaries + `_`/`-`/`.`), drop a leading
segment shared by more than half the tools (repeat), group on the next segment, split any group
over 12 by repeating one level deeper, sweep any group under 3 into `Other`.

**Composition point — inside `curation.ts`, not at each call site**, so every consumer (detail API,
summary API, and the model-facing gate in `tool-manifests.ts`) gets the fix automatically without
each caller having to remember to derive:

```ts
// curation.ts
export function withDerivedGroups<T extends Pick<IntegrationToolDescriptor, "name" | "group">>(
  tools: readonly T[]
): T[];
```

No-ops (returns tools unchanged) unless `tools.length > INTEGRATION_LIVE_TOOL_THRESHOLD` AND every
tool's `group` is `""`. Otherwise maps `deriveGroups(tools.map(t => t.name))` onto each tool's
`group` field. Idempotent — safe to call twice.

```ts
export function isGroupOptIn(tools: readonly { length: number }): boolean;
```

Simplified to `tools.length > INTEGRATION_LIVE_TOOL_THRESHOLD` — drops the `.some(group !== "")`
condition. This is the one-line fix that makes the threshold apply uniformly regardless of where
the groups came from, per spec: "over the threshold, nothing is enabled until the user chooses,
whether the groups came from the service or from Moss."

`effectiveEnabledTools` internally calls `withDerivedGroups(tools)` before matching
`state.enabledGroups` — one new line, no signature change. Returns tools with derived `.group`
attached (never renames `.name`).

`discovery.ts:toDetail` calls `withDerivedGroups(tools)` once up front so `groups:` (the group
summary list) and the returned `tools:` array show derived names too, not just the enabled-set
decision.

## Grandfathering — smallest existing seam

**Mechanism: a one-time data-only SQL migration**, the same seam already used for every other
one-time schema/data step in this module (`0207`, `0208`). New file:

`packages/integrations/sql/0209_integration_group_derivation_grandfather.sql`

```sql
UPDATE app.integration_connections
SET enabled_tools = (
  SELECT array_agg(t ->> 'name')
  FROM jsonb_array_elements(discovered_tools) AS t
  WHERE NOT (t ->> 'name' = ANY(muted_tools))
)
WHERE enabled_tools = '{}'
  AND jsonb_array_length(discovered_tools) > 30
  AND NOT EXISTS (
    SELECT 1 FROM jsonb_array_elements(discovered_tools) AS t
    WHERE COALESCE(t ->> 'group', '') <> ''
  );
```

Runs once, at migration time, only against rows matching exactly the spec's grandfathering
condition (over threshold, empty enabled list, no service-supplied groups) — i.e. Ben's one
production connection today. It writes the currently-effective tool names (everything not muted,
since under the old rule an empty `enabled_tools` meant "everything on") into `enabled_tools`
directly, so the moment `isGroupOptIn` starts firing for that connection, its explicit list already
matches what was live a moment before. A later refresh that discovers new tools leaves them off
`enabled_tools` — matching the spec's "leave new tools off, that's what opt-in is for" ruling. No
app-code change needed for grandfathering; the migration runner is the existing mechanism, and
`30` matches `INTEGRATION_LIVE_TOOL_THRESHOLD` (`packages/shared/src/integrations-api.ts:82`).

Also add the `{ version: "0209", name: "..." }` entry to
`tests/integration/foundation-schema-catalog.test.ts`'s expected list (same pattern as 0207/0208).
