# Plan — issue #1752 Task 4: end-to-end proof of a live rescan

Part of #1752.

## Goal

Prove, with a real automated test, that a module dropped onto the modules folder on disk while
both the web server and the background worker are already running becomes visible after a rescan
— with neither process restarted. This is the last piece of #1752; Tasks 1-3 (the holder itself,
wiring it into the worker, and the rescan action end to end) are already done and committed.

## Seams check

Every claim below is checked against the current tree, with the exact file and lines.

1. **A real worker can be started inside a test, not just its internal pieces.**
   `apps/worker/src/worker.ts:107` exports `buildWorker`, which starts a full worker process
   (connects to Postgres, starts pg-boss, registers every queue handler including the module
   control queue) and returns a handle with a `shutdown()` method (`apps/worker/src/worker.ts:86-89`,
   `383-396`). No test currently calls it — `tests/integration/worker-lifecycle.test.ts:16-17` says
   in a comment that "full worker lifecycle is covered by the foundation.test.ts pg-boss
   integration suite", but grepping `tests/integration/foundation.test.ts` for `buildWorker` finds
   no match. That comment is stale; nothing today exercises the real worker process end to end.
   This is the gap Task 4 fills.

2. **`buildWorker` reads the modules folder location from an environment variable, not a
   parameter.** `apps/worker/src/worker.ts:196` calls `resolveExternalWorkerConfig()` with no
   arguments, which reads `process.env` (`apps/worker/src/worker.ts:91-95`). The underlying
   resolver, `packages/module-registry/src/resolve-modules-dir.ts:25-27`, checks the environment
   variable named `JARVIS_MODULES_DIR` first. So the test must set that environment variable to
   the same temporary folder used for the API server before calling `buildWorker`, and restore it
   afterward. `buildWorker` does take an optional `connectionString` override
   (`apps/worker/src/worker.ts:107,109`) — that part does not need the environment variable.

3. **The queue-existence guard will pass in a test.** `buildWorker` refuses to start if any
   expected pg-boss queue is missing (`apps/worker/src/worker.ts:148-164`). The shared test setup
   helper `resetEmptyFoundationDatabase` (`tests/integration/test-database.ts:71-97`) already runs
   `migratePgBoss` with the full queue list before any test body runs, so this guard will not
   block a test that calls `resetEmptyFoundationDatabase` first — same as every other integration
   test already does.

4. **The API server and the worker can be pointed at the same real database from a test**, each
   using its own database role connection string, the same way `external-modules-routes.test.ts`
   already does for the API side alone. `apps/api/src/server.ts:196` defaults its own pg-boss
   client to the "app" role connection string; `buildWorker` defaults to the "worker" role
   connection string. Both roles point at the same physical test database
   (`packages/db/src/urls.ts`), so a job sent by one process's pg-boss client is visible to the
   other's.

5. **The admin rescan route already exists and does both halves of the job**:
   `packages/settings/src/routes-modules.ts:274-292` — it rescans the API process's own in-memory
   discovery list immediately, then (if a pg-boss client was wired in) sends a `{ action: "rescan"
}` message on the module-control queue. The real worker's handler for that queue
   (`apps/worker/src/worker.ts:362-371`) calls the worker's own discovery holder's `rescan()` and
   then `reconciler.reconcileAll()` — this is the exact code path that needs a real worker process
   to prove.

6. **Enabling a newly-discovered module also signals the worker**, separately from rescan:
   `packages/settings/src/routes-modules.ts:246-263` (POST `/api/admin/external-modules/:id`) calls
   `dependencies.reconcileExternalModuleJobs`, which for a single module sends a `{ moduleId,
action: "reconcile" }` message (`apps/api/src/server.ts:601-604`). The worker's reconciler
   (`packages/module-registry/src/external/job-reconciler.ts:78-121`) only creates that module's
   pg-boss queues and registers its worker handler if `isModuleEnabled(moduleId)` returns true,
   which checks the worker's own discovery holder for a matching manifest hash and package hash
   (`apps/worker/src/worker.ts:312-325`) — so the worker's holder must already have discovered the
   module (i.e. the rescan message must already have been processed) before this reconcile message
   can take effect. The two messages land on the same pg-boss queue in the order they were sent,
   but the test still needs to wait for the first one to finish before asserting on the second,
   since pg-boss delivery and processing is asynchronous.

7. **The observable, worker-side proof that a rescan without a restart worked is a new pg-boss
   queue appearing.** Before the module exists on disk, its queue does not exist. After: drop it
   on disk, rescan, enable it, the worker creates that module's queue(s) via
   `reconcileQueue` (`packages/module-registry/src/external/job-reconciler.ts:216-224`,
   using `boss.createQueue`). A real pg-boss client (or a direct read of the `pgboss.queue` table)
   can check for the queue's existence directly — this is a stronger, more direct proof than
   re-reading `/api/modules`, which only proves the API process's own copy of the discovery list,
   not the worker's.

8. **The established pattern to build the test on.**
   `tests/integration/external-modules-routes.test.ts` is the closest existing test: it boots a
   real API server (`createApiServer`) pointed at a temporary modules folder holding a
   hand-written module description file, signs up an admin user through the real sign-up route,
   and drives everything through `server.inject` (in-process, not over the network). Task 4's new
   test copies this setup and adds a second, real worker process via `buildWorker` running
   alongside it.

9. **Not to touch.** `tests/integration/module-distribution.e2e.test.ts` has old comments and a
   restart helper built on the outdated assumption that a rescan needs a process restart. Per the
   Task 3 handoff, it is not owned by this task and stays untouched unless Task 4's changes
   directly conflict with it (they don't — it's a separate file, separate describe block).

## Decision: start a real worker process in the test

The whole point of Task 4 is proving the worker picks up a rescan without a restart. Asserting
only that the right message landed on the queue (the way `external-modules-routes.test.ts` does
for the reconcile-on-enable case) would prove the message was sent, not that a running worker
acted on it — the "no restart needed" claim would rest on inference, not direct observation. This
plan starts a real worker with `buildWorker` in the new test, even though it is heavier than the
existing convention in `worker-lifecycle.test.ts`.

**Flagging to the coordinator explicitly, per the relay's instruction**, since this is a real
design choice: the lighter alternative (assert the queue message only, skip the real worker) is
available and much cheaper to run, but proves a weaker claim.

## New test file

`tests/integration/module-discovery-live-rescan.test.ts`

### Setup (in a `beforeAll`)

- Call `resetEmptyFoundationDatabase()`.
- Create a temporary folder, with one module already present on disk (call it `first-module`) —
  same hand-written `jarvis.module.json` shape as `external-modules-routes.test.ts` uses, with a
  `worker.queues` entry so enabling it is observable as a created pg-boss queue.
- Start a real API server via `createApiServer`, `externalModulesDir` pointed at the temp folder,
  same as the existing pattern.
- Sign up an admin user through the real sign-up route (bootstraps as instance owner, same
  pattern).
- Set `process.env.JARVIS_MODULES_DIR` to the temp folder, call `buildWorker()`, then restore the
  previous environment variable value (or delete it if it was unset).
- Keep the returned worker handle for teardown.

### Teardown (in an `afterAll`)

- Call the worker handle's `shutdown()`.
- Close the API server and destroy its database handle, same as the existing pattern.
- Remove the temporary folder.

### Test case: a module dropped on disk after both processes are already running becomes usable after a rescan, without restarting either process

Behaviour, and why it would fail against a broken (or reverted) implementation:

1. Confirm the baseline: a direct pg-boss read (or a `pgboss.queue` table query) shows no queue
   named for a not-yet-existing second module (call it `second-module`). This guards against a
   false positive from a stale queue left by another test or a previous run.
2. With both the API server and the worker already up and running (not restarted), write
   `second-module`'s `jarvis.module.json` and any files its manifest needs onto disk inside the
   already-configured temp folder. This is the "module dropped in while running" step. Before a
   rescan, `GET /api/admin/external-modules` must not list it — this proves the API process is not
   silently re-scanning on every read (which would make the "no restart" claim meaningless because
   nothing would have needed proving).
3. Call `POST /api/admin/modules/rescan` as the admin user. Assert it returns success.
4. `GET /api/admin/external-modules` now lists `second-module` as discovered — proves the API
   side of the rescan worked (already covered in spirit by Task 3's own tests, kept here as a
   precondition check for the next step, not a new claim).
5. Wait (bounded retry with a timeout, since pg-boss delivery is asynchronous) until the module
   control queue has processed the rescan message. A broken implementation that never processes
   the message, or a worker that isn't listening, must make this step time out and fail the test
   — not hang forever.
6. Call `POST /api/admin/external-modules/second-module` with `{ enabled: true }` as the admin
   user. Assert it returns success.
7. Wait (bounded retry) until `second-module`'s declared queue exists in pg-boss. This is the
   direct, worker-side proof: it can only exist if the real worker process's own discovery holder
   picked up the on-disk module through the rescan message it received while already running, and
   its reconciler then created the queue. A worker that still only knows about modules from its
   own startup snapshot (the bug Task 1-3 fixed) would never create this queue, and the test
   would time out and fail.
8. Assert neither process was restarted at any point in the test — this is implicit in the test
   structure (one `beforeAll`/`afterAll` for each process, no restart helper used anywhere in the
   test body), not a runtime assertion.

### What this test does not need to do

- It does not need to run a job on `second-module`'s queue — queue existence is sufficient proof
  the worker's reconciler ran against fresh discovery data, and running a job would pull in
  runtime/manifest concerns (worker entrypoint, sandboxing) that are out of scope for #1752.
- It does not touch `module-distribution.e2e.test.ts`.

## Kill gate

If a bounded wait in steps 5 or 7 above cannot be made reliable (flaky under normal local-machine
timing, not just under artificial slowdown) after one round of tuning, stop and flag to the
coordinator rather than loosening the timeout indefinitely or adding retries in a loop — that
would be evidence the two-message-ordering assumption in seam 6 above doesn't hold in practice,
which is a design question, not a timing one. Call made by whoever is running Task 4 at that
point, escalated to the coordinator before merging.
