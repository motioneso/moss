## Decision

Add a module-local keyed mutex in `write-tools.ts`:

```ts
const pathLocks = new Map<string, Promise<void>>();

async function withPathLock<T>(key: string, fn: () => Promise<T>): Promise<T>;
```

Semantics: promise-chained FIFO queue per key (resolved absolute file path). On acquire, chains
behind the current tail for that key; on release (`finally`), deletes the key from the map only if
no later waiter has replaced the tail entry (avoids unbounded growth from unique note paths, per
spec).

`notesEditExecute` change: after `resolveExistingFile` resolves `file`, wrap the pre-read guard →
read → count check → pre-write guard → write sequence in `withPathLock(file, async () => { ... })`.
`sync(...)` stays outside the lock (called after `withPathLock` resolves), matching "enqueue sync
after release." Input/output schemas unchanged — no manifest edits.

Add the `ponytail:` comment above `withPathLock` stating the ceiling: single-API-process only,
replace with a cross-process file/advisory lock if multiple API replicas become supported.

## Test cases (`tests/integration/notes-write-tools.test.ts`, new `describe("concurrent edits")` block)

1. **Disjoint overlapping edits on one file both succeed.** Seed a file with two distinct unique
   substrings. Start two `notesEditExecute` calls concurrently (different `oldText`/`newText`
   pairs). Use the existing `readFileFsMock` seam: first call's mocked `readFile` blocks on a
   manually-resolved deferred until the second call has also entered `readFile`, proving both were
   in flight before either wrote. Assert both promises resolve, and the final file content contains
   both replacements (order-independent check via `.toContain`).
   Fails against pre-lock code only in that it doesn't currently prove serialization — pre-lock
   code already happens to pass this specific case since there's no shared mutable read window
   _unless_ both reads race the same content; the real regression this guards is case 2.
2. **Overlapping same-substring edits: exactly one succeeds, other gets existing 409.** Seed a file
   with one occurrence of a substring. Fire two concurrent edits targeting that same `oldText` with
   different `newText`. Without serialization both could read count=1 and both write (last-write-
   wins, lost update). With the lock, the second call re-reads inside the lock after the first
   released, sees the substring is gone (already edited), and its count check yields 0 →
   existing `409 oldText appears 0 times` (not a new error type — reuses existing 409 semantics).
   Assert one promise resolves, one rejects with `HttpError` message matching `/appears 0 times/`,
   and the file contains exactly one complete result (the winner's `newText`, not a merge/corrupt).

Both tests use a deterministic barrier (a manually-controlled promise gate patched into
`readFileFsMock`), not `setTimeout`/timing races, per spec requirement.
