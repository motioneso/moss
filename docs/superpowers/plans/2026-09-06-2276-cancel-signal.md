## The gap, in plain terms

When a structured generation is cancelled or hits its own timeout, two places can still hand back a
result that arrived after the cancel:

1. The shared entry point that calls a provider adapter and then parses its answer. If the adapter
   resolves after the caller already gave up, the shared entry currently parses and can return
   success anyway.
2. The command-line adapter's single-shot path has a rescue step: if the run fails, it re-reads the
   transcript once more in case the answer had just landed. That rescue is meant for a real failure
   that has nothing to do with cancelling — for example, the process crashed for an unrelated
   reason but the last words were still legible. Today the same rescue also fires when the failure
   *was* the cancel or the timeout, so a late answer can be handed back exactly in the case where it
   must not be.

The fix makes both places check "was this cancelled or timed out" before accepting a result, not
after.

## Task 1 — shared entry rejects a late answer before it is parsed

File: `packages/ai/src/structured/generate-structured.ts`.

Decision: immediately after the `await adapter.generateStructured({...})` call at line 196-208
resolves (i.e. it did not throw), and before the `if ("rawText" in generated)` branch at line 209,
add:

```
if (input.signal?.aborted) return { ok: false, error: "aborted" };
```

No signature changes. This is the shared choke point: it covers every adapter (HTTP API adapter and
command-line adapter alike), so a late answer can never reach parsing, schema validation, the
repair-retry loop, or a success return, no matter which adapter produced it.

Test (new case in `packages/ai/src/structured/generate-structured.test.ts`): build a `deps` whose
`createCliStructuredAdapter().generateStructured` returns a *valid* `rawText` result, but only after
the test has already called `controller.abort()` on the `AbortController` whose `signal` was passed
in as `input.signal`. Assert the overall result is `{ ok: false, error: "aborted" }`, not a parsed
success. This is the forced-late-result proof: the adapter's promise resolves with good data, and
the shared entry still throws it away because the signal was already aborted by the time it looked.

## Task 2 — single-shot command-line path stops rescuing a cancelled or timed-out run

File: `packages/chat/src/live/cli-structured-adapter.ts`, `generateOneShotStructured`
(lines 110-201).

Decisions:
- Add one local flag, `cancelled` (boolean, starts `false`), alongside the existing `timedOut`.
- Set `cancelled = true` in the timer callback (line 146-151) at the same point `timedOut` is set,
  and in the external-abort callback (`abort`, lines 152-157) at its start.
- Right after the `Promise.race([generated, stopped])` succeeds (line 162, before returning), if
  `cancelled` is `true`, throw an `Error` named `"AbortError"` (same construction already used at
  lines 154-156 and elsewhere in this file) instead of returning the race result. This closes the
  race where `generated` and the cancel happen to settle in the same tick and `generated` wins.
- In the `catch` block (lines 165-188), only attempt the rescue read
  (`activeEngine.readNew(0)` and the reply search, lines 167-171) when `cancelled` is `false`. When
  `cancelled` is `true`, skip straight to the existing `throw error;` at line 187 — do not read the
  transcript again, do not return a reply.
- The `exit` bookkeeping after the (now skipped) rescue simplifies: since `timedOut` can only be
  `true` when `cancelled` is also `true`, the surviving `exit = timedOut ? "timeout" : "complete"`
  ternary at line 174 becomes unreachable for the `timedOut` branch inside the rescue-success path;
  replace it with `exit = "complete"` there. The existing `exit` assignment below the rescue
  (lines 180-186, used when there is no reply to rescue) is unchanged.
- No signature changes; `cancelled` is function-local.

Tests (new cases in `packages/chat/src/live/cli-structured-adapter.test.ts`):
1. **Forced late result, external cancel is thrown away.** A fake `CliChatEngine` whose `readNew`
   never resolves on its first call (the run loop's own read hangs forever) but resolves with a
   real reply record on the second call (the rescue read). Call `adapter.generateStructured` with an
   `AbortController`'s signal, abort it almost immediately (e.g. via `setTimeout(0)` or a
   microtask). Assert the call rejects (does not resolve with the rescued reply).
2. **Forced late result, internal timeout is thrown away.** Same fake engine shape, no external
   signal; construct the adapter with a very small `timeoutMs` (e.g. `20`) so the internal timer
   fires. Assert the call rejects rather than resolving with the rescued reply.
3. **Regression: non-cancellation rescue still works.** A fake engine whose run loop throws for an
   unrelated reason (e.g. `isAlive()` resolves `false` after one non-complete read, which the
   existing code turns into `CliChatUnavailableError`) with no timeout and no abort — `cancelled`
   stays `false`. Its `readNew(0)` rescue call resolves with a reply. Assert the call **succeeds**
   and returns that reply. This is the "existing non-cancellation recovery remains working" case
   from the issue's acceptance criteria.
4. **Regression: scoped path already discards a late read.** A fake `CliStructuredEngine` (the
   scoped variant, `launchStructured`/`submitStructured`/`readStructured`) whose `readStructured`
   never resolves on the call in flight when the timeout fires. Construct the adapter with a small
   `timeoutMs`, call `generateStructured` with a `scope`, and assert the call rejects. This
   documents current, correct behaviour (task-1's seams check already confirmed no code change is
   needed here) as an explicit regression test rather than leaving it unverified.
