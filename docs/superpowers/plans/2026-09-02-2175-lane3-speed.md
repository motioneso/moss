## Design decision — suppressed/refused outcome (Task 7 step 3)

The gateway cannot get this distinction from `result.ok` (both suppressed-and-served and
refused-by-budget return `ok: true` from `runHandler`'s perspective — they're not exceptions, and
`isModuleReportedError` only fires on the module's own declared error shape, not on a serve/refuse
envelope). Two options:

- **(A) Gateway inspects the envelope's `summary` string** — couples `packages/ai` to
  `packages/integrations`' string constants. Violates module isolation (Hard Invariant).
- **(B) `ToolResult` carries a generic, optional `auditOutcome` field any module's `execute` may
  set**, read by `runHandler` and threaded into the recorded outcome only when present, defaulting
  to today's `success`/`failed` derivation otherwise. Module-sdk stays module-agnostic; integrations
  is the only caller that ever sets it today.

**Decision: (B).** Add to `packages/module-sdk/src/index.ts`:

```ts
export interface ToolResult {
  readonly data: Record<string, unknown>;
  readonly columnOrder?: readonly string[];
  readonly media?: ToolResultMedia;
  /** Overrides the audit outcome runHandler would otherwise derive from ok/error (#2175 Task 7).
   *  Set by a tool's execute when it served a result without reaching the underlying service. */
  readonly auditOutcome?: "suppressed" | "refused";
}
```

In `tool-manifests.ts`'s `execute` closure: the `decision.kind === "serve"` branch
(`tool-manifests.ts:128-136`) returns `{ data: envelope, auditOutcome: "suppressed" }`; the budget
refusal branch (`tool-manifests.ts:139-147`) returns `{ data: envelope, auditOutcome: "refused" }`.
The normal call-through branch (153-194) never sets it, so its outcome is derived exactly as today.

## Task 9 — MCP client reuse within a burst

### Code changes

- `packages/integrations/src/mcp-client.ts`:
  - New exported scope type (structurally identical to `CallMemoryScope`, but declared locally to
    avoid an integrations-internal cross-file type dependency across unrelated modules — both
    files already import from `./limits.js`, not from each other):
    ```ts
    export interface McpClientScope {
      readonly actorUserId: string;
      readonly chatSessionId: string;
    }
    ```
  - Replace `callMcpTool`'s direct `connect()`/`close()` with a lazy-expiry client cache keyed by
    `` `${actorUserId} ${chatSessionId} ${connectionId} ${url}` `` (URL included so a connection
    edit that changes the endpoint never reuses a stale client), window
    `INTEGRATIONS_TOOL_CACHE_WINDOW_MS` (imported from `./limits.js` — Task 9 reuses "the same
    number as Task 3's store" per the plan instruction, which now lives in `limits.ts` from Task 8).
    New signature:
    ```ts
    export async function callMcpTool(
      scope: McpClientScope,
      connectionId: string,
      url: string,
      secret: string | null,
      placement: CredentialPlacement | null,
      toolName: string,
      input: Record<string, unknown>
    ): Promise<{ ok: boolean; data: Record<string, unknown> }>
    ```
    Behavior: look up a live cached client for the key (lazy expiry — if the stored entry's age
    exceeds the window, close it fire-and-forget and treat as a miss); on miss, `connect()` and
    store `{ client, storedAt }`; on every use (hit or miss) refresh `storedAt` so an active burst
    keeps extending the window, matching `CallMemory.record`'s "only a real call extends the
    window" convention. On a call throwing (transport error), evict and close the cached entry
    before rethrowing, so a broken connection is never reused. No `finally { client.close() }` on
    the success path anymore — the client outlives one call on purpose.
  - `discoverMcpTools` (53-68) is unaffected — it already connects/closes once for a one-shot
    discovery, not a burst.
- `packages/integrations/src/tool-manifests.ts:161` — call site updates to pass
  `{ actorUserId: ctx.actorUserId, chatSessionId: ctx.chatSessionId }` and `conn.id` as the new
  leading args.
