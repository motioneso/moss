### ⚠ New finding — not in the spec

**The Food-page AI-consent toggle is itself blocked by #1699.** Writing a module preference means
`kv.set`, and `kv.set` throws `forbidden_kv_mutation` when the calling tool is `risk: "read"`
(`packages/module-registry/src/external/worker-rpc-host.ts:456-457`). The page can only invoke
read tools (`packages/ai/src/routes.ts:667`). So a toggle rendered on the Food page cannot persist
its own value until #1699 lands.

The spec scopes #1699 to "page logging, correction, and deletion" and separately pins consent to
the Food page. Those two statements are jointly unsatisfiable today. **Phase 1 resolves this by
shipping consent as a write-risk assistant tool the user grants through Chat, with the Food page
rendering consent state read-only plus the sentence that grants it.** The toggle becomes
interactive when #1699 lands. This needs a one-line spec amendment; it is not a new blocker.

2. **Does #1694's export declaration land as a manifest key or a separate file?** Owner: #1694 spec

## 2. Design forks, ranked

### Fork A — how Phase 1 estimates

**Chosen: synchronous estimation inside the create tool, with the durable queue as the retry path.**

The create tool already runs on the path that has `ctx.ai`
(`apps/api/src/external-module-tools.ts:31`), so a typed-breakfast log estimates in the request and
the user sees a real estimate immediately. The meal row is persisted _before_ estimation is
attempted, so a provider failure yields `failed` + retry, never a lost meal (spec: "Saving the meal
and estimating it are separate outcomes").

**Steelman of the rejected option (queue-first, always async):** it is the more honest architecture.
Estimation is a variable-latency third-party call, and putting it in the request means the create
tool's p99 is the provider's p99; a slow provider turns "log my lunch" into a spinner. The queue
path is verified available to modules (`apps/worker/src/external-module-ai-bridge.ts:46`), so this
is a real option, not a strawman. It also makes `pending` the normal state rather than an error
state, which is a simpler mental model.

**Why synchronous still wins for Phase 1:** the async path cannot report anything back to the
browser. The manual-run endpoint is fire-and-forget with a 5-second per-actor singleton
(`apps/api/src/external-module-jobs.ts:10,81-82`), and per the
`pgboss-singleton-buckets-on-a-fixed-epoch-grid` memory that window is a fixed epoch grid, not a
sliding one — two meals logged 6 seconds apart can still collide inside one bucket. Phase 1 would
be measuring the estimator against a delivery mechanism that has its own known defect. Synchronous
first gives a clean signal at the kill gate; the queue is already wired for retry and can become
the default in Phase 2 if latency proves bad.

### Fork B — page writes in Phase 1

**Chosen: no page writes in Phase 1.** The Food page is read-only (date selector, meal rows, daily
totals, consent state). All writing happens through Chat tools.

**Steelman of the rejected option (Finance-style manual-run writes):** Finance ships page writes
today through exactly this route — `external-modules/finance/src/web/api.ts:8` says so outright,
and `runQueue` at `:81` is the working precedent. Copying it would give Food a fully interactive
page now, with no dependency on #1699. Precedent in-repo beats waiting on an unstarted issue.

**Why read-only still wins:** Finance's writes are connector operations where "queued" is an honest
answer — a bank sync genuinely is async. Food's writes are direct data entry where the user expects
the row to appear. With no result channel the page cannot show a validation error, cannot show the
new row, and cannot distinguish "saved" from "singleton-deduped into nothing". Building that UI and
then rebuilding it on #1699 is the more expensive path. **This ranking flips if #1699 slips past
the Phase 1 kill gate** — at which point Finance-style writes become the right fallback, and this
plan should be revised rather than the phase stalled.

_Fork B is a milestone-level fork. Per the skill, an adversarial second opinion is valuable but not
a gate; `/grill-me-codex` was unavailable (usage limit until 2026-08-19) and this is recorded as
taken without one._

## 3. Determinism boundary

Binding for every phase.

- **All Food UI feedback renders from the meal record**, never from model output. The saved
  description shown to the user is the user's own text. Estimate status is the persisted enum
  (`pending` / `needs_details` / `estimated` / `failed`), never inferred from prose.
- **Food never injects a turn into the host chat.** Chat logging returns a tool result; the host
  renders it.
- **The model gets exactly two jobs:**
  1. Convert a bounded meal description into a structured nutrition estimate, or say it needs details.
  2. Produce the bounded clarification question when it needs details.

  Everything else — dates, totals, ordering, day boundaries, incomplete-totals disclosure — is
  computed from records in TypeScript.

- **Guidance budget: `assistantOnboarding.guidance` ≤ 150 words.** If Food needs more to behave, the
  design is wrong. (The validator's own ceiling is 8 KiB —
  `packages/module-registry/src/external/validate.ts:43` — which is far too loose to protect us; 150
  words is this plan's rule.)
- **Model-authored values crossing into user data** (every nutrient number) carry all four guards:
  schema field descriptions in the output schema; a prompt contract with one worked example; a
  boundary validator rejecting out-of-range and non-numeric values before persistence; and per-item
  before/after diff acceptance on correction, so a re-estimate never silently overwrites a user's
  own corrected value.

Nullability is part of the boundary: unknown, pending, and failed nutrients are `NULL`, never `0`.
Daily totals sum only non-null estimates and always carry an `incomplete` flag when any meal in the
day lacks a completed estimate.

  owner_user_id uuid NOT NULL REFERENCES app.users(id) ON DELETE CASCADE,

  fat_g numeric(8,2),
  fiber_g numeric(8,2),

### Task 7 — tests

Behaviours, each stated with how a broken implementation fails it:

1. **Meal persists before estimation.** Provider throws; meal row still exists with
   `estimate_state = 'failed'`. _Fails if_ estimation is inside the same try-block as the insert —
   the user loses the meal on any provider blip.
2. **Idempotent create.** Same `idempotencyKey` twice → one row. _Fails if_ the unique constraint is
   missing — a timed-out retry silently duplicates lunch.
3. **Nutrients never zero-filled.** `needs_details` outcome → every nutrient column `NULL`. _Fails
   if_ the mapper coerces `undefined → 0` — the user reads a real "0 g protein" that was never
   estimated.
4. **Totals exclude incomplete.** One estimated + one pending meal → totals sum only the estimated
   one and set `incomplete: true`. _Fails if_ totals `COALESCE(...,0)` — a half-estimated day reads
   as a low-calorie day.
5. **Local-date pinning.** Meal at 23:30 in `America/Los_Angeles`, then the user's timezone changes
   → meal stays on its original `local_date`. _Fails if_ the day is derived from `consumed_at` at
   read time — history silently reshuffles across days.
6. **DST boundary.** Meal during a spring-forward transition lands on the correct local date.
   _Fails if_ offset arithmetic assumes fixed offsets.
7. **Stale revision rejected.** `correctMeal` with `expectedRevision` behind current → rejected, no
   write. _Fails if_ unguarded — an async estimate overwrites the user's own correction.
8. **Consent gate.** Consent ungranted → no provider call, meal saves `pending`. _Fails if_ the
   check is after the call — health-adjacent text reaches a provider without consent.
9. **Two-actor privacy.** Actor B cannot read, list, summarize, or correct actor A's meals; an
   admin context cannot either. _Fails if_ any query trusts a caller-supplied owner id.
10. **Module isolation.** Food cannot read `app.wellness_*`; Wellness cannot read `app.food_*`.
11. **No content in logs or payloads.** Assert descriptions, nutrient values, and transcripts appear
    in neither log output nor the queue payload. _Fails if_ a debug log interpolates the meal.
12. **Lifecycle.** Food absent before install; nav entry and tools appear after install+enable;
    disable hides surfaces and tools while rows are retained. Through the platform contract, not a
    test-only shortcut.

13. **Torn estimate write degrades safely.** Simulate the `INSERT food_estimates` failing after the
    CAS `UPDATE food_meals` succeeded (R12 — modules have no transactions). The meal reads back as
    having no estimate, never as a partial or zeroed one, and re-running the estimate queue
    completes it. _Fails if_ the mapper assumes an estimate row exists for the current revision —
    the meal then throws or renders zeros on every page load.
14. **Empty day names its date.** `computeDailyTotals(localDate, [])` returns that `localDate` with
    all-null nutrients and `incomplete: true`. _Fails if_ the date is read from `meals[0]` — opening
    a day with nothing logged renders a blank or wrongly-dated header.

**Wiring assertion (per `wired-not-just-defined`):** grep that a production caller passes
`idempotencyKey` into `logMeal`, and that the page's rendered rows come from `food.meals.list`
rather than a fixture. A tool that unit-tests green while no caller reaches it is the failure mode
this exists to catch.

## 5. Verification

Run in order. Never pipe — a pipeline reports the last command's status, so a piped gate exits 0 on
a real failure.

**`external-modules/*` is not a pnpm workspace package** (`pnpm-workspace.yaml` globs only
`apps/*`, `packages/*`, `spikes/*`). There is no `@moss/food-module` to filter on, and a `--filter`
that matches nothing **exits 0** — it would have read as green forever. Food's tests therefore live
in the repo-root suites as `tests/unit/external-module-food-*.test.ts`, matching how Finance is
tested (`tests/unit/external-module-finance-categorize.test.ts` and five siblings).

Two root `package.json` edits are required for Food to be typechecked and built at all:

- `check:external-modules` (line 20) gains `&& tsc -p external-modules/food --noEmit`
- a new `build:external:food` script mirroring `build:external:finance` (line 21)

These are the narrow registration exception the spec's Planning Constraint allows. They are also
exactly the smell that Constraint names — a genuine third-party author cannot edit root
`package.json`, so generic discovery here is worth a follow-up issue.
