### Phase 2: module credential family loads lazily, worker-safe across rotation

- Add `createModuleCredentialCipherFromKeyring(keyring)` beside
  `createModuleCredentialSecretCipher` in `module-credential-crypto.ts`.
- Cross-process staleness finding: the in-memory cache is per process and the
  refresh hook runs in the interface process only, so the worker would keep a
  pre-rotation key after Rotate. Fix, as the coordinator recommends: entries
  expire after 60 seconds so the worker picks up a rotation on its own, and
  every decrypt reloads once and retries on failure instead of erroring out.
  The expiry lives in the generic store so slice 1's latent hole heals too.
- Change the cipher threading from built-once objects to per-use resolvers:
  `routes-module-credentials.ts` (via `routes.ts:890`),
  `external-module-tools.ts:49`, and the worker chain (`worker.ts:361`
  through the job handler and invoker into `worker-rpc-host.ts:387`) resolve
  env-wins, else store, else a setup-guidance error naming the Settings
  screen, at each use. Nothing in any boot path throws for a missing key.
- Tests: decrypt with a store-loaded keyring works; env set means the store
  is never read; neither means the named guidance error and boot still
  succeeds; rotate then decrypt through a second independently built cipher
  that never saw the refresh call (the worker simulation); expired entries
  reload. Each fails against boot-time construction or an ageless cache.
- Slice 1 hole answer: same cache, so latently yes, but live no, because no
  worker code path touches the integrations cipher. Report this at phase end.
- Verification: same unpiped vitest form as phase 1 (expect exit 0).
