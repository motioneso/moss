**Goal:** Let an instance admin describe a module in chat, have Moss agree a plan and build it, and
see the finished draft running immediately for themselves alone — with nothing stored beyond what
already exists and nothing added to chat (that is stage 2/3). Ships when the admin presses ship.

**Architecture:** Five build issues, in the dependency order #1752 confirmed and the other four
issue bodies re-confirmed while writing this plan (no reordering needed — see "Order check" below).
A module folder that appears while the server is running must be found (#1752) before a draft can
be visible to its one author (#1753) before a build agent can produce and install one (#1754). The
front end (#1755, #1756) is written against the approved mockups and wired to real data as the
backend lands; it does not block on the backend to start.

The build agent itself is not a new kind of AI loop. Grounding found that chat's "live" mode already
runs a real coding agent in a tmux session per conversation, gated by an approval hook
(`packages/chat/src/live/cli-launch-commands.ts`, `packages/chat/src/live/claude-permission-hook.ts`).
A module build is a background job that launches that same mechanism against a scratch directory,
outliving the chat turn that started it. This matches the spec's own framing: "the assistant already
writes files and runs shell commands in chat, gated by approval cards... What is missing is the path
from a scratch directory to an installed, approved, running module."

**Tech Stack:** Fastify (API), pg-boss (jobs/queues), Kysely/Postgres (data), Fastify route + Kysely
migrations for schema, React front end using the `jds-*` design-system primitives.

**Spec:** `docs/superpowers/specs/2026-08-19-moss-builds-modules-on-moss.md` (read in full — this
plan does not repeat its Problem Statement, User Stories or Testing Decisions, only implements them).
Pointer doc with decisions and two grounded findings: `docs/coordination/state-1739-moss-builds-modules.md`.
Mockups: `docs/superpowers/specs/assets/2026-08-19-moss-workshop/` (`workshop.html`, `chat.html`,
`plan.html`, `draft.html`; `approval.html` is superseded — never build it).

## Global Constraints

Copied from the spec and this project's `CLAUDE.md` — every task below implicitly includes these.

- Module isolation: modules collaborate only through declared public APIs and events, never by
  importing another module's internals or querying its tables.
- No admin private-data bypass; RLS applies to every actor including admins; no `BYPASSRLS` on
  runtime roles.
- Private by default; a draft is visible to its author alone until shipped.
- Secrets never escape: connector/AI credentials, tokens, password hashes never reach frontend
  responses, logs, pg-boss payloads, or AI prompts. pg-boss payloads are metadata-only (actor/resource
  IDs, job kind, idempotency key, small params) — never content or secrets.
- Provider-agnostic AI: never hardcode a provider or model name.
- Never edit an applied migration — add a new file. Module SQL lives in the owning module's `sql/`,
  never in `infra/postgres/migrations/`.
- All seven self-operation exclusion categories in `packages/ai/src/gateway/self-operation.ts`
  (`self_authority`, `prompt_shaping`, `secrets`, `identity_auth_registration`, `data_scope_consent`,
  `assistant_brain`, `external_effect`) stand unchanged. Moss never ships its own work, never handles
  a module's credential, never turns the "stop asking me" (YOLO) setting on for itself.
- A built module must satisfy the existing module validator (`validateExternalModuleManifest`,
  `packages/module-registry/src/external/validate.ts`) unchanged. A generated module that fails it is
  a build failure, not a reason to relax the validator.
- Stage 1 boundary: the built module may have a page and background work. It stores no new data
  (no new tables) and adds nothing to chat (no new tools). Those are stage 2 and stage 3.
- Design system: `jds-*` primitives only, no invented classes. Run the invented-class audit (the
  `design-system` skill) across both `apps/web/src/styles/` and `packages/ui/src/styles/` before
  any UI task is considered done.
- Plain English in every status update, commit message body beyond the technical summary line, and
  handoff: name things by what they do, only use an exact identifier when the reader must act on it.

// apps/api/src/external-module-discovery-holder.ts
import { discoverExternalModules, type ExternalModuleDiscovery, type ExternalModuleRejection } from "@jarvis/module-registry";

export interface ExternalModuleDiscoveryHolder {
  getDiscoveries(): readonly ExternalModuleDiscovery[];
  getRejected(): readonly ExternalModuleRejection[];
  rescan(): Promise<{ discoveries: readonly ExternalModuleDiscovery[]; rejected: readonly ExternalModuleRejection[] }>;
}

export function createExternalModuleDiscoveryHolder(options: {
  modulesDir: string;
  coreVersion?: string;
  reservedQueueNames?: readonly string[];
}): ExternalModuleDiscoveryHolder {
  let discoveries: readonly ExternalModuleDiscovery[] = [];
  let rejected: readonly ExternalModuleRejection[] = [];

  const run = () => discoverExternalModules(options);

  const snapshot = run();
  discoveries = snapshot.discoveries;
  rejected = snapshot.rejected;

  return {
    getDiscoveries: () => discoveries,
    getRejected: () => rejected,
    rescan: async () => {
      const next = run();
      discoveries = next.discoveries;
      rejected = next.rejected;
      return next;
    },
  };
}
```

// packages/jobs/src/module-jobs.ts (replace lines 16-34)
export type ModuleControlPayload =
  | { readonly moduleId: string; readonly action: "reconcile" }
  | { readonly moduleId?: undefined; readonly action: "rescan" };

const MODULE_ID_PATTERN = /^[a-z0-9](?:[a-z0-9-]*[a-z0-9])?$/;

export function assertModuleControlPayload(value: unknown): asserts value is ModuleControlPayload {
  if (typeof value !== "object" || value === null) {
    throw new Error("module control payload must be an object");
  }
  const record = value as Record<string, unknown>;
  const keys = Object.keys(record);

  if (record.action === "rescan") {
    if (keys.length !== 1 || keys[0] !== "action") {
      throw new Error("rescan payload must carry only { action: \"rescan\" }");
    }
    return;
  }

  if (record.action === "reconcile") {
    if (keys.length !== 2 || !("moduleId" in record)) {
      throw new Error("reconcile payload must carry exactly { moduleId, action }");
    }
    if (typeof record.moduleId !== "string" || !MODULE_ID_PATTERN.test(record.moduleId)) {
      throw new Error("moduleId must be a valid module id");
    }
    return;
  }

  throw new Error(`unknown module control action: ${String(record.action)}`);
}
```

import { join } from "node:path";
import { resolveModulesDir } from "../resolve-modules-dir";

const BUILD_ID_PATTERN = /^[a-z0-9](?:[a-z0-9-]*[a-z0-9])?$/;

export function resolveModuleBuildsDir(env: NodeJS.ProcessEnv): string {
  if (env.JARVIS_MODULE_BUILDS_DIR) return env.JARVIS_MODULE_BUILDS_DIR;
  const modulesDir = resolveModulesDir(env); // .../data/modules
  return join(modulesDir, "..", "module-builds");
}

export function resolveBuildSourceDir(buildsDir: string, buildId: string): string {
  if (!BUILD_ID_PATTERN.test(buildId)) {
    throw new Error(`invalid build id: ${buildId}`);
  }
  return join(buildsDir, buildId);
}

export const MODULE_BUILD_QUEUE = "module-build";

export interface ModuleBuildPayload {
  readonly actorUserId: string;
  readonly buildId: string;
  readonly step?: string;
}

export interface ModuleBuildStepResult {
  readonly deferred: boolean;
  readonly continuation?: { readonly buildId: string; readonly step: string };
}

export function createModuleBuildWorker(deps: {
  sendJob: typeof sendJob; // from packages/jobs/src/pg-boss.ts
  boss: PgBoss;
  runStep: (payload: ModuleBuildPayload) => Promise<ModuleBuildStepResult>;
}) {
  return async ([job]: [{ data: ModuleBuildPayload }]) => {
    const result = await deps.runStep(job.data);
    if (result.deferred && result.continuation) {
      await deps.sendJob(
        deps.boss,
        MODULE_BUILD_QUEUE,
        { ...job.data, ...result.continuation },
        { singletonKey: `build:${result.continuation.buildId}` },
      );
    }
  };
}
