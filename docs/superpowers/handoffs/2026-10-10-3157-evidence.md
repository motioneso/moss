# Issue #3157 evidence: automatic session handoff for long chats

Branch `scheduled/3157-automatic-rollover`, base `integration/scheduled-proactive`, PR #3328.

## Scope

- The app counts what one provider session was sent and returned, by estimate. Reported output
  usage can raise the count but never lower it.
- Before a turn would pass `JARVIS_CHAT_SESSION_BUDGET_TOKENS`, the next admitted turn relaunches
  the exact owned session (owner, conversation, provider) from the accepted summary (#3156) plus
  every uncovered turn.
- With no accepted summary, or a replay that would not fit, the healthy session keeps serving and
  a summary run is requested.
- Private chats never hand off.
- Out of scope: vendor context-full signals, new adapters, interrupted-turn recovery.

## Disclosures

- The first attempt used "Please remember". The model reached for a memory tool, which waited for
  approval and timed out. That left rows 1 to 3 in the thread. All later messages forbid tools.
- The drawer offered no visible "New chat" button, so the run continued in the same thread.
- The sign-in poll returns 500 "no such login" after the code is accepted. The sign-in itself
  worked. This is a separate small fault.
- A fresh install refuses to start module reconcile until
  `MOSS_RECONCILE_CONFIRM_OWNER_EMAIL` names the first account. The demo install set it.
- The meter is an estimate. It does not read the vendor's own context count.
