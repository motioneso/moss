# Issue #3131 evidence: owner chooses between differing saved quiet hours

Branch `scheduled/3131-resolve-quiet-hours-conflict`, base `integration/scheduled-proactive`.

## Scope

- An owner whose Profile quiet hours and older email-alert schedule differ picks one in
  Settings > Alerts & quiet hours, inside the existing quiet-hours editor (#3130).
- Each consumer keeps its own schedule until the choice saves. A failed or stale choice writes
  nothing.
- The saved choice becomes the one canonical Profile schedule. Notifications, focus and alert
  cards follow it through the #3165 classification.
- Chat cannot make the choice. No urgency path changes.

## Change

| Area | Before | After |
| --- | --- | --- |
| API | No way to settle a conflict | `POST /api/me/quiet-hours/resolution` with the chosen side, its schedule and the version read |
| Server rule | n/a | Locked read; only a live conflict at the read version with the chosen side unchanged is settled; a repeat of the settled schedule is a 200 no-op; anything else is 409 and writes nothing |
| Alert record | n/a | Never written by the choice |
| Editor | Conflict note naming both schedules, form still shown | Form hidden; note plus one button per differing schedule; failure keeps the offer with Try again; a stale choice reloads the latest |
| App map | Conflict described as unresolved | Choice flow, success lines, failure and stale errors, recovery path |

## Red, green and negative controls

Each enforcement was removed on its own and the scoped database suite rerun through the gate.

| Enforcement removed | Test that failed |
| --- | --- |
| Version check | Older version whose schedules changed back (200, expected 409); another user replaying the owner's choice |
| Conflict-only check | Owner whose schedules already agree (200, expected 409) |
| Repeat-is-harmless branch | Same choice sent again (409, expected 200) |
| Owner lock and Profile revision guard together | Two choices from the same read held at the lock (both 200, expected one 409) |
| Owner lock only, or revision guard only | None. Each alone still holds the race |
| Code-level owner filter on the read | None. Database row rules alone keep other owners' rows out |

Unit tests for the choice rules and the editor were written red first.

## Installed demonstration

`pnpm test:uat:3131` on an isolated install, dev port 5184, image built from merge commit
`0e99f12ff`: 1 passed (12.1 min). Real browser, real server, real worker. No response was
intercepted or rewritten.

The two differing records are seeded straight into the database: Profile quiet hours off, and an
older email-alert schedule on for a window that covers the current time. No current writer can
create a disagreement, by design, so the seeded rows stand in for an upgraded install. Every later
change goes through the app.

| Step | Result |
| --- | --- |
| Reload Settings > Alerts & quiet hours | Form hidden; "Keep quiet hours off" and "Use 18:36 to 18:35" offered |
| Look | Desktop and phone, light and dark; buttons 8px apart, nothing spills over |
| Choose while the browser is offline | Refused; both saved records byte-for-byte unchanged |
| Notification inside the window, before a choice | Arrived at once, so the old Profile behaviour still governs |
| Try again online | The alert window saved as the one schedule; reload agrees |
| Send the same choice again | 200, version unchanged, nothing written |
| Notification inside the window, after the choice | Held, then released once at the window's end |

Only the on-versus-off case and the "use the alert schedule" button run live. Two different
windows and "Keep quiet hours off" are covered by the database tests above.
