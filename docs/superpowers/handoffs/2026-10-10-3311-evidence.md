## Rebase onto #3331

#3331 (list and cancel, migration `0308`) and #3334 (browser test fake) merged first. The branch
was rebuilt on that base as two commits: the turn-runner split, then the feature.

- `0309` now extends `0308` instead of `0307`:
  - context check is `pending`, `dismissed`, `acknowledged`;
  - the trigger keeps `0308`'s dismiss branch and also allows delivered pending to acknowledged;
  - this PR's own column grant is gone, because `0308` already grants `(state, context_state)`.
- The acknowledge policy stays separate. Its WITH CHECK repeats the Main-thread check, because
  Postgres ORs permissive UPDATE policies and `0308`'s cancel policy admits any of the owner's
  reminders.
- Test expectations that changed with the combined rules:
  - an app-role acknowledgement of the owner's side-chat, queued, or already acknowledged
    reminder now throws (row-level security or trigger) instead of updating no rows, because the
    cancel policy's USING admits those rows; another user's attempt still updates no rows;
  - a queued context change reports `0308`'s "identity cannot be changed";
  - acknowledged to dismissed, and dismissed to acknowledged, are both rejected;
  - the column test now changes the reminder text along with the context state and expects a
    permission error.
- `settle()` in `0308`'s cancel path dismisses a delivered reminder only while its context is
  pending, so an acknowledged reminder reports already delivered and is left alone.

## Live proof

Real UI on a private test copy (own database, own model runner, own sign-in from the project's
encrypted test token). Model: Claude Haiku 5.5 through the Claude CLI sign-in. Driven by
Playwright through the chat drawer. No screenshots, no rewritten responses. Reminder states read
from the test copy's own database after each run.

| Case | Steps | Reply | Reminder state after |
|---|---|---|---|
| Warm | Set "lock the door"; one ordinary exchange starts the model session; the reminder is delivered; ask in the same open window | "Since your last message, I haven't sent any reminders. The most recent one, "Reminder: lock the door," went out before that." | acknowledged |
| Side | Set "check the oven" in Main; it is delivered; ask in a new side chat | "I haven't sent you any reminders recently, and you have no notifications at all right now." | pending |
| Cold | Restart the model runner; ask in Main | "I haven't sent any reminders you haven't already seen; the most recent was "Reminder: check the oven."" | acknowledged |

Warm session check: exactly one model session was created after the reminder was set (by the
ordinary exchange, before delivery), and none at the follow-up. Cold check: the follow-up after
the runner restart relaunched with replay and created a new session.

### What the live runs showed beyond the acceptance

- Setting a reminder drops the warm model session on purpose (`pre-model-turn.ts`), so the first
  model turn after a request is always a relaunch. A warm reply needs one ordinary exchange
  between the request and the delivery.
- Opening the chat drawer posts a resume that relaunches the session, so every fresh page load is
  a cold start.
- The open drawer does not repaint when a reminder is delivered; the message appears on reload.
  Outside this issue.
- A cold launch shows a recent reminder twice: once in the replayed history and once in the
  admitted block. The block stays because replay is bounded, so it is what guarantees an older
  pending reminder is seen. The model answered correctly in every cold run.
