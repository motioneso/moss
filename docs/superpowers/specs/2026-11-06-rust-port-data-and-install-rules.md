# Rust port: data migration and install rules

## Status

- **Proposed build contract, not a shipped capability.** JS-32; source reviewed at `1cb86c8b2`.
- Ben chose a **full rewrite of the server and UI in Rust**, for Windows, macOS and Linux.
- Companion: `docs/superpowers/specs/2026-11-06-rust-port-plan.md` (JS-31). This document owns the detailed data, privacy, install and recovery rules; the main plan owns sequencing and the wider rewrite.
- “Must” below is an acceptance requirement for that rewrite. It does not certify today's code. No production data was inspected or changed for this plan.
- The recommendation is bundled PostgreSQL with pgvector on every install on all three systems, an owner-started move to a separate destination, and a retained original installation. A failed move must leave the old app recoverable.
- Approval of this document does not authorize a production cutover. The owner approves a concrete rehearsal report and the final write freeze separately.

## Database

| Candidate                             | Consequence                                                                                                  | Rule                                                                                                                                 |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------ |
| Bundled PostgreSQL + pgvector         | Preserves SQL functions, roles, RLS, vector types and logical dump semantics; packaging is substantial work. | **Use on every install, on Windows, macOS and Linux.** Ship pinned, compatible server/extension binaries and backup tools.           |
| Embedded PostgreSQL-compatible engine | Syntax compatibility does not establish role, FORCE RLS, extension, trigger or transaction equivalence.      | Not accepted without a new complete equivalence proof and revised plan.                                                              |
| SQLite plus application isolation     | Requires replacing every security policy, privileged function, migration and vector path.                    | Not part of this rewrite plan. No silent fallback when PostgreSQL fails.                                                             |
| External PostgreSQL                   | Fits existing server operation; adds operator-managed version and backup responsibilities.                   | Explicit owner choice at setup only, with the same capability and upgrade gates. Every install must run without an external service. |

- Initial compatibility target is the repo's PostgreSQL 17 family. Pin the exact minor and pgvector versions in each release manifest after qualification; inspect the actual source install before import. Do not assume its mutable image tag proves its version.
- One private cluster per installation, accessible only locally with generated credentials; no trust authentication or public database listener. Host API sharing never exposes the database port.
- The supervisor owns lifecycle, crash recovery, single-instance locking and port conflict handling. It must not attach to an unrelated local Postgres or kill it.
- Bundle backup/restore tooling. Never reuse a raw PostgreSQL data directory across OSes, CPU architectures or unsupported major versions: use a qualified logical export/import.
- Runtime pools use only app, worker, auth or scoped module roles. A separate, short-lived installer/backup process holds bootstrap authority while app/worker access is fenced. It is not an admin web endpoint with unrestricted SQL.
- Preserve role ownership, ACLs, function owners, `SECURITY DEFINER` search paths, triggers, extensions, sequences and collation-dependent behavior. Recreating tables alone is not equivalence.
- Migration owner/bootstrap operations can read private data for recovery. The threat model excludes a hostile machine administrator or unlocked-account malware. Several accounts sharing one OS user is a different, stated risk; see [Several accounts on one install](#several-accounts-on-one-install); “no admin bypass” refers to Moss actors, including Moss admins.

### Privacy tests

Run each test through real Rust HTTP and worker paths and directly through the runtime role. Include owners A/B, an unrelated administrator C, anonymous/missing actor, and every supported sharing level.

| Guarantee                      | Required proof                                                                                                                                                                                                                                                                                                                                                                                          |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Private by default             | Create every private resource with no share. B and C cannot SELECT, change, delete, export, search, fetch attachments or resolve it through AI tools. Forged owner IDs on INSERT/UPDATE are rejected. Inventory must cover every private table, not just a probe table.                                                                                                                                 |
| No admin bypass                | Repeat as C with admin settings powers. Inspect role flags, memberships and definer functions; `SET ROLE` cannot reach owner/bootstrap. Startup rejects runtime superuser, `BYPASSRLS`, missing FORCE RLS or unexpected privileged membership.                                                                                                                                                          |
| Explicit sharing only          | A grants the declared minimum level to B; only the corresponding operations succeed. Revoke and repeat through caches, search, jobs and downloads. A grant for another resource or user provides no access. Owner-only tables never inherit generic sharing.                                                                                                                                            |
| Actor scope survives pooling   | Interleave A/B/C transactions; force cancellation, SQL error, timeout and connection reuse. No stale actor survives; absent/malformed actor fails closed. Caller-supplied identity never overrides authenticated identity.                                                                                                                                                                              |
| Background authority is narrow | Worker reloads current actor/resource/consent state before acting. Removed share, disabled account or revoked approval prevents execution. Maintenance functions have specific capabilities, not arbitrary owner reads.                                                                                                                                                                                 |
| Vault isolation                | B/C cannot traverse, link, junction, hardlink or race an ancestor swap into A's vault. Test Windows drive/UNC/device paths and POSIX symlinks. Use descriptor-relative operations and OS ACLs; do not mistake POSIX mode bits for Windows protection.                                                                                                                                                   |
| Agent containment              | In one-OS-user mode on each OS, B's agent tries to read A's vault root and agent home, the database files, the key store, and the Moss process's environment and memory. Record per OS which attempts are blocked, each with a negative control run with confinement removed. The shared-install notice lists only blocked results. In per-account OS user mode, the same attempts must all be blocked. |

Each security test must fail when its protection is deliberately removed in a disposable fixture. Record the negative-control result; passing with the guard removed is a failed gate.

## Schema and migrations

### Ownership

- Retain `infra/postgres/migrations/` for platform schema, and each owning module's `sql/` directory. Rust crates may move code; moving or replacing applied SQL bytes is not required.
- Inventory all registry-declared first-party directories from `getBuiltInSqlMigrationDirectories` in `packages/module-registry/src/index.ts`, not just core migrations. The registry is authoritative; `packages/proactive-monitoring/src/sql/` is a real exception to the usual `packages/<module>/sql/` layout. Include installed modules absent from the source checkout, disabled modules and archived data.
- Current first-party SQL folders span AI, backtrack, briefings, calendar, chat, commitments, connectors, email, goals, integrations, meetings, memory, news, notes, notifications, people, proactive-monitoring, scratchpad, settings, sports, structured-state, tasks, usefulness-feedback, wellness, workflows and workshop under `packages/`. External SQL is present under `external-modules/finance/`, `meals/` and `job-search/`.
- A module owns its declared tables and migrations. Other modules use its public API/events; no table joins across module internals. The host generates security policies for external modules, as `module-rls-emitter.ts` does today.

### Ledger contract

1. Never edit, renumber, normalize newlines/BOMs, delete or replace an applied migration. Fixes are new migrations with new IDs. Keep the original ledger and application timestamps.
2. At startup, before any DDL, validate the entire applied ledger against a signed release inventory: identity, filename, original bytes and checksum. Check missing files, unknown applied versions, duplicate IDs, wrong module ownership and unexpected SQL/backfill pairs. Fail closed; never rewrite hashes to make a mismatch pass.
3. Legacy built-in SQL-only hash is SHA-256 of exact file bytes. Backfill hash is SHA-256 over `moss:sql-migration+backfill:v1\0`, decimal SQL byte length plus `:`, SQL bytes, decimal backfill byte length plus `:`, backfill bytes. Preserve this exact encoding, not a JSON approximation.
4. Preserve the historical built-in directory order from `scripts/migrate.ts`, file order within each directory and global built-in ID uniqueness. Future releases declare explicit dependency order; they must not reorder old migrations globally by number.
5. Preserve `app.schema_migrations` and `app.module_schema_migrations`. Module ID plus version identifies external entries. Their legacy hash is SHA-256 of the bytes obtained by Node-compatible UTF-8 decoding with replacement, then UTF-8 re-encoding, as `packages/db/src/migrations/module-sql-runner.ts` does. This equals the raw-byte hash only for valid UTF-8. Preserve that historical calculation for comparison; invalid-UTF-8 legacy module files then block import with originals retained, never normalize or replace the ledger. New module files require fatal UTF-8 validation. Rust adds checksum comparison for applied module files; today's version-only skip is not sufficient.
6. Keep historical backfill sources as inert compatibility artifacts. An exact legacy pair maps to a frozen Rust transformation whose own version/hash is in the release manifest. Compare JS and Rust outcomes on synthetic edge fixtures and authorized isolated copies: rows, Unicode behavior, limits, NULLs, JSON, errors and rollback. Never execute an unknown pair or omit the backfill. No Node runtime ships to run these migrations.
7. Hash-bound RLS shims from `legacy-upgrade-shims.ts` remain explicit compatibility adapters. Any temporary RLS relaxation is restricted to the migration transaction, with all consumers fenced, and must be restored on success and rollback. Unmatched checksum gets no shim.
8. New SQL/backfills have immutable IDs, explicit input/output schema versions and frozen implementation hashes. Add catalog expectations and upgrade/rollback-failure fixtures in the same PR. Built-in IDs cannot collide across modules; external IDs are namespaced by module.
9. One migration lock owner at a time; losing the lock connection aborts DDL. Core DDL/backfill/ledger commit atomically. Module DDL, generated policies and ledger proof must also commit atomically through a narrowly scoped host operation, without granting the module ledger-edit authority. Do not reproduce today's separate DDL/ledger commit crash window.
10. Bootstrap and grants are intentionally rerunnable today. Rust pins and verifies their release hashes, runs them idempotently under the correct lock/authority, then verifies the resulting role/policy catalog. Do not claim the old runner hash-checks these files.
11. Invalid, drifted or partially installed external modules remain disabled with data intact. Unknown schema is a blocked import, not a reason to mark the database current. New runtime grants are never inferred from untrusted module SQL.

## Moving an existing Docker install

The following is the required behavior of an owner-facing migration assistant, not commands to run on production now. Source inspection and copying require the installation operator's explicit authority; Moss account exports cannot bypass RLS to gather other users' data.

### Package inventory

| Item                 | Preserve and verify                                                                                                                                                                                                                                                                               |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Database             | All schemas including module data and pg-boss history, users, auth password hashes, shares, sessions/device records, constraints, roles/ACL definitions and both migration ledgers. Enumerate tables and extension versions from the source catalog.                                              |
| Files                | All private vault bytes, binaries/attachments, recordings/artifacts, module-owned persistent files and independently configured mounts. Hash file bytes and record paths, sizes, ownership intent and external-root mappings. Do not follow links blindly.                                        |
| Credentials          | Both connector/AI keyrings, current and retired keys, key IDs/order for no-ID envelopes, nested family-key stores, OAuth credentials/client configuration, push keys/subscriptions and relevant signing/session configuration. Transfer through an encrypted recovery channel, not a user export. |
| Jobs                 | Queue definitions, schedules/timezones, pending/in-flight/failed/completed history and domain-level operation receipts, retries, approval state and idempotency keys. Record source IDs and import mapping.                                                                                       |
| Search               | All embeddings, dimensions, model/version provenance, content hashes, chunks and ingestion checkpoints. Indexes may be rebuilt; vector values and original sources must survive.                                                                                                                  |
| Runtime dependencies | Installed module versions/hashes, CLI login material and configured tool identity; preserve private originals. OS-bound sessions may need sign-in again. Do not copy executable caches as trusted cross-OS binaries.                                                                              |

Every discovered item receives one disposition: transferred and verified, safely reconstructed from preserved input, or preserved but inactive with a stated reason. No “ignored” bucket. An unclassified persistent mount/table stops cutover.

### Sequence

1. **Preflight.** Display source installation identity and target empty installation identity, versions, capacity and backup location. Privately enumerate mounts, all tables/ledgers and key IDs without revealing values. Reject a nonempty or wrong destination; source and destination must not share DB, writable vault or queue storage. Import every source account into any destination; never drop accounts. If the destination's agents share one OS user (see [Several accounts on one install](#several-accounts-on-one-install)), show the shared-install notice before the owner approves the move, and to every imported account at its first sign-in. Reject unsupported source versions and insufficient capacity for original, backup, destination and temporary/index space.
2. **Rehearse.** After owner authorization, take a protected copy and exercise the whole conversion/restore with outbound effects disabled. This preliminary copy does not authorize final cutover. Confirm every source credential envelope authenticates, including nested family keys. A missing key is a blocker, never a cue to generate a replacement.
3. **Resolve incompatibilities.** Produce a private report of filename collisions, unavailable modules, unportable credentials, unknown job kinds and external folders. Fix or explicitly preserve-and-disable each item before moving. Required product functionality that cannot be migrated blocks GA; “inactive” is not feature parity.
4. **Fence producers.** Put source API, webhooks, schedules, connectors, agents and file writers into durable maintenance mode. Pause retention/purge jobs and external-vault writers. Drain only enumerated safe jobs with already authorized effects; do not create new user actions merely to empty the queue.
5. **Stop consumers.** Stop and verify every worker/agent after the drain. Record unfinished operations as uncertain. Prevent service/container auto-restart. Keep only the source DB alive for its consistent dump, deny runtime-role connections and fence all non-backup clients; the backup session is read-only. Verify no remaining write transactions. “Untouched” means logical user data, not PostgreSQL housekeeping bytes. After the dump, stop the source DB too. No old or new application writers run.
6. **Freeze and export.** Record cutover watermark and manifest; dump the database retaining owners/ACLs and capture all files while writes remain stopped. Export keys separately wrapped for recovery. Encrypt the entire archive, including manifests containing private filenames. Verify it and retain an independent copy. The source volumes, keys and old image remain untouched.
7. **Restore elsewhere.** Create roles and extensions in a fresh destination cluster with new runtime database passwords; restore schema/data/ACLs in controlled order. Copy vaults into the destination's private roots; map linked roots only after explicit folder selection. Verify hashes before migration. Never import by overwriting the Docker volume, even on the same Linux host.
8. **Convert offline.** Validate historical hashes first, then apply new Rust migrations and job mappings. Keep the original snapshot immutable. Failures leave the destination quarantined and source recoverable. Record each conversion's counts/digests and preserve pre-conversion values where representations change.
9. **Verify.** Compare table key sets and canonical row digests per owner, counts, constraints, sequence next-values, file manifest hashes, migration ledgers, grants and policy/function catalogs. Compare intentionally transformed tables against the approved mapping, not just counts. Verify decryptability without logging plaintext. Run the privacy matrix and owner-visible reads/search, sign-in, attachment download and linked-folder checks. Rehearse outbound effects with isolated test accounts; do not send real mail as a migration test.
10. **Switch authority.** Owner sees the reconciliation and inactive-item report and approves the switch. Issue a new installation generation/worker lease; remove source routing, then activate target routing and exactly one worker set. Verify the old host remains fenced across reboot. Restore only approved schedules/consents, never enable previously disabled modules or watchers.
11. **Observe and retain.** Check first real jobs/connector refreshes, phone/companion access and backups. Keep original Docker volumes, encrypted snapshot, recovery keys and compatible old binaries until the retention rule below permits deletion. Do not automatically prune them on successful first launch.

### Jobs and side effects

- The Rust queue is a new Moss-owned PostgreSQL queue. Archive the pg-boss schema as protected history; Rust does not start a pg-boss consumer against it.
- Pending jobs get exactly one import record keyed by source installation and source job ID. Preserve schedule timezone, retries/limits and idempotency identity. Re-running import cannot enqueue a duplicate.
- In-flight or uncertain non-idempotent work becomes **needs reconciliation**, never automatically retried. A source completion receipt suppresses execution even if its queue row looks pending. Require provider reconciliation or owner decision for unknown mail sends, payments, deletes or external writes.
- Startup fencing includes old services and inbound routes, not merely a destination advisory lock: different databases do not share a lock. A stale source auto-restart must be shown unable to consume or accept writes.
- Metadata-only payloads use per-kind semantic schemas, with actor/resource IDs and bounded approved parameters. A short string is not automatically safe; reject content and credentials even if they fit the size limit.

### Data that cannot move

- Case-folding/Unicode collisions, reserved names, junctions and invalid paths are reported before extraction. Preserve original bytes and a mapping; require deliberate rename/placement rather than merging or silently dropping files. Reject archive path traversal, absolute paths, link escapes and decompression bombs.
- Preserve incompatible module data and original package hashes in a protected archive; keep the module disabled until its new package is qualified. Never run old Node code inside the Rust app as an undocumented fallback.
- Expired OAuth attempts, OS-bound CLI credentials, sessions or companion credentials may need reauthorization. Report what needs signing in and why; keep historical records and ciphertext. Do not claim successful decryption proves provider acceptance.
- Embedding-model differences do not authorize truncation or automatic network re-embedding. Keep the original vectors/model pair; qualify retrieval and normalization parity. A new index/model uses a separate generation and explicit rebuild approval; do not mix vector spaces.
- Unknown jobs remain visible in protected history and cannot execute. If original source content or a key is unavailable, label recovery impossible for those items and block a “complete” migration. Any owner-approved partial move must retain the originals and list the omissions.

## Fresh install

No terminal, Docker, separately installed database, runtime package manager or edited configuration file is permitted on the supported desktop path. These are release gates, not things already built.

| System        | One download and launch                                                                                                                                                                                  | Private local data                                                              | Key protection                                                         |
| ------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| Windows       | Signed per-user installer with bundled Postgres/pgvector; graphical prerequisite handling. No administrator needed for ordinary local operation.                                                         | `%LOCALAPPDATA%\Moss\` (not roaming AppData); user-only ACLs.                   | User-scoped DPAPI-wrapped store; restrict file ACLs and broker access. |
| macOS         | Signed/notarized app in a disk image; drag/install and open. All bundled executable code/extensions pass signing checks.                                                                                 | `~/Library/Application Support/Moss/`; owner-only permissions.                  | Keychain entry bound to the intended signed app/service.               |
| Linux desktop | Signed graphical package for each qualified distribution, with dependencies resolved by the graphical installer. An AppImage is acceptable only if launch needs no chmod, FUSE setup or terminal repair. | `$XDG_DATA_HOME/moss/`, default `~/.local/share/moss/`; owner-only permissions. | Secret Service in the user's session; no plaintext fallback.           |

- Phase 1 must publish a tested OS-version, CPU-architecture and Linux-distribution matrix. “Linux” does not mean every distribution. A missing signing prerequisite, key store or runtime must produce graphical repair or a clear refusal before data is created, not a shell command.
- Layout below each root: instance identity/version, private DB, vaults per actor, module data, logs with safe codes, staged updates and recovery metadata. Executables are versioned separately from data. Never put credentials or private data in the install directory or cloud-synced roaming folders.
- First-run choices: **New installation**, **Move an existing installation**, **Restore a backup**, or **Connect to another Moss install**. Connecting to another install is optional; local operation must remain complete.
- New install creates keys and cluster once, performs readiness/privacy checks, creates the owner through normal authentication, explains backup recovery and opens the app. Setup is resumable after power loss; it must not create a second identity/keyring on retry.
- Default API is local only; sign-in and trusted-origin checks still apply locally. Phone access is an explicit GUI choice with TLS, paired/authenticated access and managed firewall permission. Never expose an unauthenticated onboarding server to the LAN.
- Start-at-login is an explicit choice. Explain whether closing the window leaves background work running and that logout/sleep can stop it. No missed-job burst on resume; use each job's expiry/idempotency rules.
- No automatic antivirus exclusion. Handle file locks with bounded retry and a safe error; changes to OS protection require a separate, explained owner choice and cannot be the normal installation prerequisite.
- Every install supports several accounts. [Several accounts on one install](#several-accounts-on-one-install) sets the restrictions, the honest limit and the notice.

## Several accounts on one install

Ben ruled on 2026-11-06 that every install supports several accounts and that desktop and server are one product: "I would want the Rust version to support multi-user in the desktop version as well. And I kind of want the desktop and server version to be the same, right? It just depends on where you host it. And I know that there's the privacy risk, but we're going to do all the restrictions we can, but part of it is also just trusting your shared users." This overturns the earlier single-account desktop rule.

### One build, three reach settings

Every install is the same program and the same build. Two settings differ by host; neither makes a second product.

| Setting         | Choices                                                                                                                                                                                          | Notes                                                                                                                                                                                              |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Reach           | **This computer only** (default, loopback); **Home network** (explicit choice, TLS, paired access, managed firewall prompt); **Internet** (explicit choice, TLS on an origin the owner controls) | Sign-in and trusted-origin checks apply at every level. Loopback is reachable by every program and OS user on the same machine, so "this computer only" is not an access control between accounts. |
| Separation mode | **Per-account OS users** where the host grants Moss the right to switch users (a Linux service set up for it, as production is today); **One OS user** everywhere else                           | Setup detects the mode and shows it in Settings. A normal desktop install is one OS user, because creating OS accounts needs administrator rights and the installer must not ask for them.         |

The separation mode, not the word "desktop" or "server", decides how strong the privacy guarantee is. A Linux server that cannot switch users is in one-OS-user mode and gets the same rules and notice as a laptop.

### Restrictions every one-OS-user install must apply

1. **Privacy rules on every query.** Every request, job and agent tool call runs under the `NOBYPASSRLS` runtime roles with the actor set per transaction, exactly as on every other install. Nothing about one-OS-user mode relaxes RLS.
2. **A separate working folder per account.** Each account gets its own vault root and agent home folder, created with the tightest permissions the OS allows: owner-only modes on macOS and Linux (today's `0700` folders and `0600` files in `packages/vault/src/vault-ops.ts`), user-only ACLs on Windows. All Moss access still goes through `VaultContext`.
3. **Secrets kept out of agent reach.** Agent processes receive no database URL or password, no auth secret, no connector or AI key and no recovery key, in their environment, arguments or files. Credentials are used through the broker. G6 traces this to the last consumer, including the agent launch path.
4. **One agent process per account.** Each account's agent runs in its own process with its own home folder. Where the OS offers confinement that needs no administrator rights (Landlock or bubblewrap on Linux, a sandbox profile on macOS, AppContainer or a restricted token on Windows), Moss confines that process to its own account's folders and denies the Moss data folder, the database files and the key store. Which of these actually holds on each OS is unproven. Phase 3 measures it per OS, with a negative control, and records the result.
5. **The notice.** When a second account is added, Moss tells the people sharing it what is and is not protected (below).

### What holds and what does not on one OS user

What protects each property was traced to today's code or is a requirement of this plan. "Does not" lists what still gets through after every restriction above. On an install with per-account OS users, the OS also separates each account's agent, folders and agent sign-ins from the others.

| Property                                                               | What protects it                                                                                      | What does not                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| ---------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Account A's data through Moss screens, API, search and agent tools     | RLS under the runtime roles, actor set per transaction; agent tools act as their own account          | This holds only while nobody reads the files or the Moss process. A session token or database password taken from either lets someone act as A through the API or query the database directly. G2 must prove the in-app guarantee.                                                                                                                                                                                                                                                                 |
| Secrets held by the running Moss process and stored database passwords | The OS key store; nothing passed into agent environments, arguments or files                          | On every OS, a program running as the same OS user can read another process's environment and can ask the key store for what Moss stored there; on Linux and Windows it can also read process memory. A copied auth secret or database password lets that program forge sessions or connect to the database directly. So the Moss process keeps no secrets in its environment. macOS's hardened runtime is meant to block memory reads; unproven. Phase 3 measures what confinement blocks per OS. |
| Database files on disk                                                 | Owner-only permissions on the Postgres data folder, which stop other OS users                         | Anyone signed in to that OS account, and any unconfined program running as it, can copy the raw files and read every account's rows. RLS guards queries, not files. This includes password hashes and session tokens.                                                                                                                                                                                                                                                                              |
| Vault files and attachments                                            | Separate root per account; owner-only modes or user-only ACLs; `VaultContext` path checks inside Moss | The permissions name the OS user, and every account is that one user, so they do not separate Moss accounts. A person at the OS login, or an unconfined agent, can open any account's folder.                                                                                                                                                                                                                                                                                                      |
| Connection passwords and AI keys                                       | AES-256-GCM in the database; the key in the OS key store; no key in any agent's environment           | Windows DPAPI and Linux Secret Service release a user's secrets to any program running as that user. An unconfined agent could ask for the key and decrypt every account's credentials. macOS can tie a keychain item to the signed app; Phase 1 must prove it does.                                                                                                                                                                                                                               |
| One account's agent reading another account's files                    | Separate process and home folder; OS confinement where Phase 3 proves it on that OS                   | Without proven confinement, nothing. The agent runs as the same OS user. An agent's own sandbox (for example Codex's) is the vendor's feature, not a Moss guarantee.                                                                                                                                                                                                                                                                                                                               |
| Agent sign-ins (CLI login material)                                    | Kept in each account's own agent home                                                                 | Same limit as vault files.                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| Admins seeing private data                                             | `NOBYPASSRLS` roles; admin power is configuration only (below)                                        | The OS account owner is not limited by Moss at all. Whoever holds the OS login and the recovery key can restore a full backup elsewhere and read every account. The same is true of a server's operator.                                                                                                                                                                                                                                                                                           |

Beyond these restrictions, privacy between accounts on one OS user rests on trust among the people sharing the install. The plan says so plainly and the product says so on screen. The notice is a disclosure, not a consent that switches any restriction off.

### The notice

- **When it appears.** In one-OS-user mode, an administrator adding a second account (invite, approval or opening sign-up) sees it before confirming. Each new person sees it at first sign-in, and so does every imported account at its first sign-in after a move into a one-OS-user install. It appears again if the separation mode or a proven confinement result changes.
- **What it says.** Plain words, close to: "Everyone on this Moss runs under the same user on this computer. Moss keeps each person's notes, chats and connections private inside the app. But someone who can sign in to this computer, or an AI agent running on it, may be able to open other people's files. Only share this Moss with people you trust." It then lists, per item, what Moss confines on this OS, using only results G2 proved.
- **In the import flow.** Moving a multi-account source into a one-OS-user install shows the same notice to the owner in preflight, and to every imported account at first sign-in.
- **App map.** The notice, the separation-mode display and the account screens are app-map entries in the PR that builds them.

### Accounts: creating, removing and administering

- **First account.** The person who completes setup becomes the bootstrap owner and first administrator, as today (`is_bootstrap_owner`). On a desktop this is usually the person who installed Moss.
- **Creating accounts.** The same flow on every install: an administrator turns on sign-up, with or without approval, from Settings, People (today's registration and approval controls). Inviting a person and creating an account for them are new requirements. With reach set to this computer only, the new person signs in on the same computer; otherwise they use the chosen reach. Each new account gets its own vault root, agent home and agent process, and sees the notice.
- **Removing accounts.** An administrator can deactivate an account, which revokes its sessions and stops its agent and schedules, or delete it, which removes its rows and vault root through today's deletion path and also removes its agent home (new). Stopping the agent and schedules on deactivation is also a requirement of this plan. An account holder can also delete their own account after confirming their email address, a typed phrase and, if the account has one, their password, as today (`packages/settings/src/me-account-routes.ts`). Today's guards stay: an administrator cannot delete their own account through the administrator path, the bootstrap owner cannot be deleted, deactivated or demoted by anyone including themselves, and the last administrator cannot be removed (`packages/settings/src/routes.ts`, `packages/settings/src/repository.ts`, `packages/settings/src/me-account-routes.ts`). Deleting asks for confirmation and offers the account holder an export first. Existing backups still hold the account until they age out; the confirmation says so.
- **Who is an administrator.** Any account with the administrator flag. Administrators promote and demote each other within the same guards. A Moss administrator is not the OS account owner. The OS account owner controls the machine, the files and the recovery key, which Moss cannot limit.
- **What an administrator can see and do.** The account list (names, sign-in addresses, status, roles), registration policy, reach, AI providers, modules, install-wide settings, and backup status.
- **What an administrator cannot see or do.** Read another account's notes, chats, mail, calendar, meetings, connections or files through Moss; sign in as another account; set a password and then use it to enter; see another account's credentials. RLS applies to administrators like everyone else, and G2 tests it with administrator C. Full-instance recovery archives remain operator disaster recovery, not an administrator data browser.

## Running on a server

A server is the same program and build, on a machine the owner leaves running, often with no screen, that people reach over the home network or the internet. This section covers what differs on such a host; it is a hosting choice, not a second product. It is the target for Ben's Docker installation; actual account count is discovered in preflight. It uses the same Rust program and rewritten browser UI, not a retained TypeScript service.

## Keys and private data

### Storage and transfer

- Preserve version-1 AES-256-GCM decryption: algorithm, IV/tag/ciphertext encodings, key IDs, exact legacy SHA-256 derivation and legacy candidate ordering. Transfer either the original key material into a derivation-aware sealed store or the already-derived keys with an explicit format marker; **never hash an already-derived key again**.
- Preflight resolves `JARVIS_CONNECTOR_SECRET_KEY`, `JARVIS_CONNECTOR_SECRET_KEY_ID`, `JARVIS_CONNECTOR_SECRET_KEYS`, `JARVIS_AI_SECRET_KEY`, `JARVIS_AI_SECRET_KEY_ID` and `JARVIS_AI_SECRET_KEYS`, including their `MOSS_` aliases through `packages/db/src/env.ts`. Inspect names/presence and effective derivation in the protected process; never show values.
- Keep current and retired connector/AI keys until every dependent envelope, nested family key and retained backup is accounted for. Rewrap into new keys only as a separate verified transaction/recovery procedure after migration. Never retire a key solely because current top-level rows decrypt.
- Every install uses the OS stores above, except the headless key file below. Locked, missing, refused or corrupt stores stop credential use; never fall back to a default key or plaintext file. Keychain enrollment and restore to a new OS account are GUI flows tested on each OS.
- **Headless key file exception:** only an owner who explicitly chooses it at setup, on a Linux machine with no keychain session, may use a service-account-only `0600` key file outside data/export roots. Its host volume must be protected for an at-rest claim. Never choose it because keychain initialization failed. Preserve the Docker source's old configuration for rollback.
- Recovery uses a **random 256-bit recovery key**, encoded with a transcription checksum for the owner to save. Passphrases are not supported in this version; never apply the legacy SHA-256 derivation to a human password. Keep a sealed copy in the installation's OS key store (or the headless key file) for unattended backups, and an independent owner-held copy. Never put the unwrapped recovery key in an archive.
- Each backup archive and separate credential-key bundle gets its own fresh random 256-bit data key. Encrypt each object with AES-256-GCM using a fresh 96-bit nonce and 128-bit authentication tag; wrap each data key with the recovery key using the same authenticated cipher and a distinct fresh nonce. Versioned authenticated headers bind object kind, installation ID, snapshot ID, key ID and encoding version. No key/nonce pair may repeat. Bound archive encryption into authenticated chunks within the cipher's message-size limits, with unique per-chunk nonces and a final authenticated manifest binding order, total bytes and completeness. The exact streaming format and test vectors require cryptographic review before implementation; restore authenticates all chunks and completeness before extraction or activation.
- Scheduled backup unlocks the locally sealed recovery key and creates the envelopes without asking the owner to type it again. A locked store yields a visible failed backup, never plaintext output. On another machine, the archive, matching wrapped credential bundle and owner-held recovery key suffice; no original keychain or headless key file is required.
- Recovery-key rotation first creates and verifies a fresh backup under the new key. Existing archives either retain their old recovery-key requirement (clearly listed) or get data-key envelopes rewrapped and restore-tested as new authenticated artifacts. Never delete old recovery keys or overwrite the only artifact before every retained backup has a demonstrated recovery path. Losing both the local store and the independent recovery key makes encrypted recovery impossible; say this during setup.
- Full-instance recovery archives are **operator disaster recovery**, not user exports or an app-admin data browser. A privileged local maintenance process creates them while fenced. Ordinary account exports stay owner-scoped and exclude credentials. A password hash/session table in a protected DB backup is not permission to return it from an API.

### At-rest claims

- Current Moss encrypts credential envelopes; its ordinary DB content and vault files are not app-encrypted. The Rust plan must not describe those existing files as ciphertext.
- Require verified encrypted volumes for bulk DB/vault/temporary data before claiming protection from a stolen disk: BitLocker/device encryption, FileVault, or a qualified Linux encrypted filesystem. Cover backup destinations and swap/crash dumps, not just the main directory. Backups themselves are always application-encrypted.
- Installer shows whether volume encryption is verified, unavailable or unknown. Linux detection may remain unknown on some setups; show that state plainly and make no protection claim. Unknown status alone does not prevent installing or using Moss; the gate requires honest reporting and a qualified graphical route to protection on the supported matrix, not universal detection. No “encrypted” badge on unknown. Phase 1 must prove a practical graphical path on the supported OS matrix; if it cannot, a separately specified/tested encrypted-storage implementation is a GA gate. Do not silently shrink the supported product to technical users.
- Encryption at rest does not isolate an unlocked account, a machine administrator or a malicious process running as the service account. Those are separate OS/process boundaries.

### Secret use and module isolation

- Plaintext secret values exist only at the credential broker and authorized adapter boundary for the necessary operation. Secret types omit logging/serialization; log events use reviewed codes and safe IDs. Error messages, traces, panic reports, subprocess arguments/environment, diagnostics, telemetry, jobs and prompts must be tested for leaks through the final consumer, including vendor adapters.
- Third-party code runs as capability-limited WebAssembly components, with no ambient filesystem, network, process, environment, database pool or keychain imports. Pin runtime/import ABI and resource/fuel limits; kill/revoke outstanding capabilities at timeout, cancellation or uninstall.
- Host binds actor/module identity. Typed database operations or a parsed restrictive SQL subset must reject role/GUC changes, `set_config`, indirect privileged functions, arbitrary extension calls, cross-module tables and multi-statement escapes. A token blacklist is insufficient. Per-module RLS/grants remain defense in depth.
- Prefer brokered credential-bearing network requests to exporting secret values into a guest. Existing `ctx.auth.getCredential` compatibility must not imply unrestricted plaintext access; rebuilding modules is already required by the full rewrite. Per-destination consent and redirect/DNS/egress validation apply to brokered calls.
- Module UI is isolated from the host origin/session storage and receives narrowly typed messages. Modules collaborate through declared APIs/events only. Preserve disable/revoke state and do not grant new capabilities on import without approval.

Clearly distinguish same-disk backup from an independent recovery copy.                                                                                |
| Consistency           | Fence writes or use a proven DB/file snapshot protocol with a shared watermark. DB dump plus a concurrent filesystem copy is not automatically consistent. | Verify backup         | Authenticate archive/manifest and run a restore drill into an isolated destination, with network/worker effects blocked. ## Compatibility and cutover

- Keep the final TypeScript release available, without forced migration, for **at least two supported Rust releases and 90 days after Rust GA, whichever is later**. This is a proposed support floor for Ben's decision, not a staffing promise. If security fixes cannot be maintained, announce a revised plan before GA rather than silently withdrawing support.
- Retain each installation's frozen rollback snapshot and old binaries for at least that window **and until the owner confirms a verified independent recovery copy and approves disposal**. No automatic source-volume deletion at expiry.
- Old and new applications may coexist on separate copies for rehearsal; only one accepts production writes and external side effects. Never share a live writable DB/vault to simplify the cutover.
- Keep existing HTTP contracts while rewriting both UI and server: routes, status codes, JSON/stream events, authentication, CSRF/trusted origins, pagination, timestamps, pairing, upload limits and errors. Sources include `packages/shared/src/*-api.ts`, `packages/auth/src/`, `apps/trail-marker/` and `apps/vocci-delivery/`. Inventory actual connected clients before cutover.
- Keep the existing external origin where possible. Test phone browsers, installed PWA/service workers, Trail Marker and Android clients against Rust; verify reconnect, active sessions, push signing identity and upload resume. Mixed old/new web assets must be version-detected and refreshed safely without losing unsent drafts. A cached old client is a supported compatibility case, not grounds to bypass authentication.
- Existing supported password hashes must verify. An unreadable or unsupported hash blocks cutover for that account unless a pre-approved account-recovery flow proves the rightful user can reset it without impersonation or admin access to private data. Keep the original hash privately in the frozen snapshot, disclose the required reset before approval, and never activate a migration that strands an account. If session compatibility cannot be proved, offer an explicit fresh sign-in and revoke old sessions consistently. Device re-pairing and OAuth redirect changes must be listed before approval. Never silently reset passwords or lose account identity.
- **Rollback before target writes:** stop/fence Rust, verify no accepted writes/effects, restore routing to the retained original Docker DB/vault/image, then start exactly its consumer set. Additive SQL is not the proof; the original was never mutated.
- **Rollback after target writes:** freeze Rust, preserve its full DB/files/keys and side-effect receipts as a separate branch, and show the watermark and affected records. Default restore returns to the old snapshot, so later writes are absent from the resumed app but retained for recovery. Owner must explicitly approve that consequence.
- “Keep newer writes” requires a tested reverse converter for data, vault formats, credentials, queues and operation receipts. Additive schema alone proves none of those. Without one, do not promise lossless downgrade or replay uncertain external actions. Reconcile provider state before old workers restart; OAuth refresh-token rotation can make old credentials stale even when the old DB is intact.

## Decisions and unknowns

- Bundled database and clone-first cutover are the joint recommendation, conditional on the platform gates. No evidence yet proves signed PostgreSQL/pgvector packaging, desktop keychain recovery or installers on all target OSes.
- The exact source installation versions, live module inventory, mounts, data volume, key availability and connected-client versions are intentionally unknown until authorized private preflight. Do not put them in this public document.
- Proposed support floor: two releases/90 days plus owner-controlled snapshot disposal. Ben must approve the maintenance commitment before announcing GA; JS-31 carries the decision.
- Several accounts on one install is decided (Ben, 2026-11-06). What each OS actually confines in one-OS-user mode is measured in Phase 3 and G2; the notice claims only what passed. Encrypted-volume UX and the final restrictive module query/credential ABI remain explicit qualification gates. The main plan must not call any of these solved by separate folders, bounded strings or generic process isolation.
- First-party/module code is rewritten; retained SQL/backfill bytes and old snapshots are compatibility evidence, not a hidden TypeScript runtime.
- This plan makes no claim that every current secret consumer, vendor adapter, module SQL file or policy is already secure. Complete catalog/consumer inventory and the tests above are required before user data moves.
