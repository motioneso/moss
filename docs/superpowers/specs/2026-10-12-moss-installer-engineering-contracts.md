## 3 Host preparation contract

### 3.1 Trust and process boundary

A trusted, version-pinned release provides a narrow local helper. A shared deterministic core owns plan validation and reconciliation; platform adapters own Docker discovery, native folder selection, official prerequisite flow and default-browser launch. The implementation may choose packaging technology during the authorized feasibility work, but it must not depend on a resident privileged daemon or a general-purpose web command API.

Use structured arguments and fixed operation names. Never interpolate shell commands from a browser, vault path, registry row or fetched page. Only a reviewed host plan can cause Compose execution. Sanitized environment and explicit process arguments select the Docker endpoint, project, file set and env file; ambient `DOCKER_HOST`, `DOCKER_CONTEXT`, `COMPOSE_FILE`, project names and shell variables must not silently redirect work.

Privilege is separate from the normal helper. Each necessary privileged change is identified and approved by the user through the platform's standard flow. The unprivileged helper does not retain passwords or elevate the entire application. Docker membership/service changes and vendor terms are visible prerequisites, not implicit consequences of Continue.

### 3.2 Host installation record

Proposed protected host record, schema version 1:

| Field                        | Contract                                                                                                                         |
| ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| `installationId`             | Immutable random identifier generated once for this deployment; persisted in backend and host state                              |
| `planRevision`, `planDigest` | Versioned, validated non-secret plan; every material host/path/config change creates a new revision                              |
| `route`                      | `local`, `server`, or `manual`; records presentation intent, not permission                                                      |
| `hostBinding`                | Actual Docker endpoint and daemon identity, context label, OS/architecture and runtime account; label alone is insufficient      |
| `deploymentBinding`          | Exact Compose project, ordered file set, profiles, env-file location, pinned image reference/digest and named-volume identities  |
| `notesIntent`                | `external`, `managed`, or `later`; external realpath and directory identity are private host data; no preauth root listing       |
| `connectionPlan`             | Exact intended origin, local bind address/port, explicit access profile and allowed continuation mode; no claim/code or password |
| `phase`                      | Last durably acknowledged phase plus current non-secret operation/result; a click is not a completed phase                       |
| `operationId`                | Stable ID for an in-flight fixed operation, with expected plan digest and bounded result                                         |
| `secretReferences`           | Locations/identifiers of protected secret storage only; never raw secrets or key fingerprints intended as authentication         |

Host records and env files use user-private permissions (0600 on Unix, equivalent owner ACL on Windows) and atomic write/replace with durability checks. A per-deployment OS lock serializes concurrent helpers. The lock owner/expiry record is not evidence that the operation finished; a crash requires actual-state reconciliation.

Before every apply/resume, compare the target endpoint/daemon, installation identity, exact project/file set and plan digest. A mismatch pauses for a new reviewed deployment decision. No automatic adoption, migration or cleanup of another deployment is permitted.

### 3.3 Lifecycle and fixed operations

Proposed phases:

`chosen → prerequisites_checked → notes_planned → reviewed → config_committed → images_ready → services_started → runtime_ready → browser_handoff → owner_bound`

A phase may also be `needs_action`, `failed` or `unknown`, retaining its last acknowledged predecessor. Failure is not a reset to `chosen`. Secret generation is a one-time protected sub-operation of configuration creation; an existing complete secret set is reused, a partial/missing set needs explicit recovery, and an existing deployment's secrets are never regenerated automatically.

Fixed operations are: inspect prerequisites; validate Notes intent; render/review plan; prepare/resume that plan; inspect runtime readiness; issue/revoke bootstrap code; open/print continuation; separately review/apply a later Notes mapping; and review/apply/inspect an explicitly requested post-bootstrap access plan. There is no arbitrary exec operation and no browser-triggered Docker operation.

Every mutating operation receives the expected installation ID, plan revision/digest and operation ID. It reports acknowledged phase, bounded error code, changed resources and next allowed action. Repeat requests reconcile the same operation. A reused ID with a different payload is rejected. Cancellation stops new phases where possible and reports already-created services/files; it does not claim rollback.

### 3.4 Configuration and startup

The renderer forwards every reviewed value, including runtime UID/GID, bind port, trusted origin, image pin and Notes mapping. Validate the **effective merged Compose configuration**, not merely the generated fragment:

- For a fresh installer-managed deployment, publishing is loopback-only before owner claim. No wildcard IPv4/IPv6, duplicate inherited public port or alternate first-owner route remains. An existing deployment retains its recorded binding/origin profile; upgrading or resuming is not permission to replace it with loopback. Post-bootstrap publishing follows the explicit access transition in section 3.8.
- Database/runner service exposure and management endpoints remain private as required by their existing topology.
- External Notes uses a long-form bind with `create_host_path: false`, precise read/write scope and no mount over private managed vault storage.
- No Docker socket, host root, whole home, credential/system tree or broad deployment directory is exposed to Moss.
- Original stable keys, env file, project and named volumes are retained across restart/recreation. No `down -v`, prune or automatic image change.
- File paths are serialized as data with control-character rejection and platform-aware handling. A path that no longer identifies the reviewed directory fails before apply.

Required readiness is a structured conjunction: intended installation identity; database reachable; migrations successful and supported schema; API operational; required runner healthy. Selected Notes host scope is additionally checked as mounted/accessible, with owner-specific activation still pending. AI login, email, News and Sports are optional and cannot block runtime readiness.

Poll with backoff, show the last verified phase and allow manual Check again. After bounded waits, report the specific unresolved readiness component; do not mark ready or retry destructive operations simply because a timeout elapsed.

### 3.5 Browser handoff

The local wrapper opens the OS default browser only after readiness. It opens a clean Account route and displays the one-use code in the helper for manual copy/paste. No code is appended to the URL, passed to the browser process as an argument, copied automatically to a shared clipboard, or stored in a general log.

A headless helper prints a clean address and separate short-lived code. If remote access uses an SSH forward, the user establishes it with their existing SSH setup on the browser computer. Select and verify the browser-side port and exact hostname before committing its trusted origin or issuing the code, as specified in section 3.7; the helper does not collect SSH secrets.

The helper may remain as a simple local status window or exit after handoff. Browser setup must not depend on it remaining open. Reissuing a code is a host operation, not a public reset endpoint. Existing owners get ordinary sign-in and server-saved resume instead of a new code.

### 3.6 Self-managed claim command

Ship a fixed `moss-setup` executable inside the version-pinned Moss image. This is a **new proposed contract**, not a command available on the inspected baseline. Supported operations are `claim issue`, `claim status` and `claim revoke`; they use the sanctioned host-admin/auth-database boundary and cannot create an owner or reset an existing one themselves.

The manual template and helper both produce the deployment-resolved form:

`docker compose [saved project, ordered -f files, profiles and --env-file flags] exec -T jarv1s moss-setup claim issue --expect-installation <installation-id> --origin <exact-browser-origin>`

`claim status` and `claim revoke` use the same saved deployment flags and expected installation ID. The released instructions must expand those placeholders from the reviewed record; this contract notation is not a universal copy-paste command. No desktop helper is needed. The command refuses wrong installation, unsupported origin, populated/no-owner ambiguity or an existing owner; issue/revoke serialize with claim consumption. A raw code is generated inside the trusted operation and returned once to the deliberate manual invocation or the helper’s protected in-memory capture, never supplied through argv, env, URL or normal container/application logs. `exec -T` makes the container output a pipe even when the host operator has a terminal, so do not impose a contradictory in-container isatty-only check. The supported manual instructions require the operator’s private interactive terminal and prohibit tee/redirection into logs or unattended CI; the helper path consumes a narrowly typed secret result without persisting/logging it. Test both exact invocation forms and redaction rather than claiming the process can infer all host capture behavior. Status returns bounded generation/expiry/locked/claimed information without echoing a code.

The image-internal command does **not** apply host Compose, env, firewall or port changes. It receives no Docker socket or broad host/deployment mount. Host access changes use the host-side helper's fixed `moss-host-setup access plan|apply|status` interface, or the manual template's exact reviewed edit/Compose-recreation instructions. These host commands are also proposed shipped interfaces, not existing baseline binaries. DIY owners may use the latter without installing either desktop wrapper.

### 3.7 Exact SSH continuation order

Static exact-origin allowlisting is required. The missing issue in the earlier draft was selection order, not the allowlist itself.

1. Before generating the effective config or claim, choose the laptop/browser local port and exact browser host string, such as `127.0.0.1` or `localhost`. They are different origins; the current generator defaults to localhost and does not automatically authorize an arbitrary alternate hostname/port.
2. Start the user-managed SSH local forward on the browser computer with `ExitOnForwardFailure=yes` and an explicit loopback bind. Its destination is the chosen host's loopback service port. A successful forward proves the local port was bound, not that the intended Moss installation answered.
3. Place the exact chosen browser origin in the reviewed `JARVIS_AUTH_TRUSTED_ORIGINS`/base-origin configuration as applicable, prepare/recreate through the saved deployment contract, and verify the expected public installation identity through the tunnel.
4. Only then issue the installation/generation/origin-bound code and open or print the clean Account URL using exactly that host and port.

If the laptop port is occupied, choose another before issuing the code. If it changes after issue, revoke the old generation, review the exact added/replaced origin on the host, apply the configuration through Compose recreation where required, recheck identity and issue a fresh code. Do not wildcard loopback ports/hosts, disable origin checks, or suggest an arbitrary alternate local port while the server still trusts only the old one. A closed tunnel leaves a resumable waiting state; it does not expose a LAN claim endpoint. All SSH credentials remain in the user's existing SSH setup.

### 3.8 Explicit post-bootstrap access transition

**Approved revision placement:** Ready's Access row displays the actual current mode and offers “Use Moss from other devices,” also available later in Settings. This opens one focused browser subpanel; it is not a seventh numbered step and Keep local completes onboarding. Choices are Keep local; Home network (HTTP, unencrypted); or verified HTTPS using an existing proxy, supported private HTTPS setup or an optional Tailscale path. No domain purchase, certificate setup or Tailscale signup is required to finish.

For HTTP, show this warning before review: “Other people or software on this network may be able to read or change your passwords and content. Some device features need HTTPS.” HTTPS is recommended. Do not claim that a private IP is confidential. Existing Trail Marker companion parsing requires remote HTTPS, so label LAN browser readiness separately from companion readiness; do not relax the companion's existing policy.

The approved access plan contains installation ID, canonical-owner confirmation, current plan digest, exact target interface/address/port, precise trusted origins, proxy/cookie mode, affected Compose/env files and proposed service recreation. Show the requested exposure and any platform firewall consent separately. It must not widen to all interfaces by convenience when a bounded interface was chosen, enable router port forwarding, open the internet, enable public Funnel or grant automatic certificate trust.

Lifecycle: `draft → reviewed → checkpoint_saved → host_apply_pending → checking_new_route → verified`, with `needs_action`, `failed` or `restored_previous` retaining the last acknowledged record. Preconditions for a fresh installation's widening are an exactly-one canonical flagged owner, no active claim/bootstrap session and first-owner routes permanently closed for that established instance. Revoke unused/bound generations and sessions, while retaining consumed claim receipts as consumed for audit and idempotency; do not rewrite terminal history merely to widen access. Get started never runs this transition.

The browser saves owner-scoped intent/checkpoint and explains the fixed host step. While present, the host helper can review and perform only that explicit plan. If it has closed, the same host-side interface resumes it. In DIY, instructions edit the actual saved configuration and use the original Compose project/file set/env/profile flags to recreate the affected service. An ordinary restart does not apply new ports/env. No image-internal CLI or browser gets a generic host-control channel.

Preserve host-side recovery, stable keys/volumes and a validated previous configuration. Select one coherent active cookie/proxy mode and canonical session origin for the resulting profile. Current cookie behavior is global and proxy-sensitive, so an HTTP-to-HTTPS change may require sign-in again; do not promise simultaneous authenticated HTTP and HTTPS merely because both ports answer. A retained loopback binding can serve bounded diagnostics/host recovery without proving a usable non-Secure browser session. Verify the new route from the intended second device, including real sign-in/cookies, before marking that client path ready. HTTPS additionally needs actual certificate trust and correct proxy peer/Secure cookies; companion pairing is its own check. A server health check or click from the original browser cannot prove a phone or companion can connect. The user can keep local-only access throughout and return later.

If apply or verification fails, keep the host recovery path and show exact retry/return options. Restoring a local HTTP browser session may require the explicitly reviewed prior cookie/proxy configuration; do not silently downgrade HTTPS or advertise a working HTTP session before that restoration is verified. Any restoration uses only the recorded prior configuration and the same deployment identities, not an image/database downgrade or volume deletion. Prefer prepare/verify before removing any old remote route; a removal is an explicit reviewed step. Origin changes may require a new login, while progress restores after identity checks.

Existing deployments enter `legacy_preserved`: record actual current bindings/origins/cookie behavior and resume without access migration. A read failure is not permission to infer local-only and rewrite configuration. Existing HTTP login, Settings, provider connection and onboarding resume tests must remain green. A later owner-requested change follows this same explicit plan; the security language must not introduce a hidden migration by blocking “new” requests on their existing origin.

## 4 Protected bootstrap and owner authentication

### 4.1 Transport profiles and origin enforcement

New endpoints explicitly join the existing exact-origin, Host, CSRF and credential-rate-limit mechanisms. Transport is evaluated against the installation's explicit profile, not a new global HTTPS rule. A client-supplied forwarded header, private IP, `isSecureContext` or checkbox does not prove protected bootstrap or HTTPS.

| Profile               | Allowed behavior                                                                                                                                      | Change authority                                                                                                                              |
| --------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `fresh_bootstrap`     | Loopback on the host, verified SSH-forwarded browser loopback, or verified HTTPS; claim exchange and first-owner creation fail closed on raw LAN HTTP | Initial reviewed host plan; never weakened by browser bypass or later LAN selection                                                           |
| `local_authenticated` | Owner exists; local browser continues account setup and normal application access on its exact configured local origin                                | Default retained fresh-install mode after claim, with no automatic LAN widening                                                               |
| `lan_compatibility`   | Authenticated browser access over deliberately configured LAN HTTP; existing Settings/provider/resume flows remain supported                          | Explicit post-bootstrap owner-reviewed host transition, or preserved prior configuration; visible plaintext-risk and feature-limit disclosure |
| `verified_https`      | Authenticated access through a trusted HTTPS origin, exact trusted proxy peer and correct secure cookies                                              | Explicit host/proxy/certificate plan, with actual device trust and session checks                                                             |
| `legacy_preserved`    | Established binding, origins, cookie mode and supported HTTP/HTTPS flows remain unchanged by upgrade or resume                                        | Any later change is a separately reviewed migration; no indirect new transport gate                                                           |

First-owner claim/session endpoints reject unsafe or unknown bootstrap transport in every profile. Ownership is never claimable again merely because LAN access was enabled. Normal established-account requests retain their installed access policy; do not block legacy HTTP Settings, provider setup, private content or resumed onboarding under the phrase “new sensitive operation.” Preserve exact-origin/CSRF checks and configured proxy trust everywhere. HTTP remains unencrypted and is not described as confidential.

Test actual cookies separately for local HTTP, forwarded loopback, preserved LAN HTTP, newly selected LAN compatibility and verified HTTPS. Validate Host/origin and DNS-rebinding defenses without trusting client-forwarded headers. HTTPS needs the correct Secure cookie behavior; compatibility HTTP retains a deliberate tested non-TLS cookie configuration, not a falsely secure label. Switching scheme/hostname may require sign-in again while server progress survives. The existing companion rejects remote HTTP and must continue to do so; a successful LAN phone browser is not proof of companion reachability.

Profile classification is server-derived from migration/installation state and the canonical owner flag, never a client-selected profile, URL parameter or helper-presence test. Every genuinely fresh empty instance, including DIY and missing-metadata installs, requires a claim; missing metadata never re-enables old open signup. A uniquely flagged established owner preserves the actual legacy configuration; a populated/no-owner or multiple-owner instance enters guarded repair. Initialization must durably establish installation metadata before claim issuance.

Preauth metadata exposes only bounded readiness and public installation identity, never owner identity, vault paths, preferences or detailed host diagnostics. A non-sensitive help page may explain protected bootstrap. Existing exposed instances are not quietly reclassified as new installs or made unreachable.

### 4.2 Code, session and owner state

Proposed human-code contract: twelve CSPRNG-generated Crockford-base32 characters, grouped as three groups of four for typing/copying, provide 60 bits of entropy. Store only a domain-separated keyed verifier under the protected stable auth/host secret, not a plain fast hash that enables cheap offline guessing from a leaked claim table. The code expires ten minutes after issue, is bound to one installation, generation and exact continuation origin, and is displayed once through the private host terminal/helper. Reissue serializes with claim/owner creation, revokes all prior unused generations and bootstrap sessions, and refuses if an owner already exists.

State is `issued → browser_bound → consumed`, or `expired/revoked`. Exchange binds at most one bootstrap session. The browser session is short-lived, HttpOnly and SameSite, transport-appropriate, origin-bound and restricted to bootstrap status/owner creation. It has no general user/session privilege. It cannot outlive the code's absolute expiry or extend it through polling.

Permit at most ten failed exchanges per claim generation across all sources, counted atomically and persisted through restarts. Exhaustion locks that generation until host-only reissue; per-source throttling is additional, not the primary guessing bound. Keep uniform errors, secret-free audit and denial-of-service recovery. With ten guesses against 60 random bits, the online guessing bound is at most 10/2^60 (about 8.7×10^-18) per generation. This does not prevent interception, malicious local processes, a stolen browser session or compromise of the verifier key, so protected transport, one-use binding and host authority remain essential. Negative tests must prove distributed requests cannot reset or exceed the shared budget. Claim locking permits denial of service; recovery is explicit host-only reissue, never remote unlock or weakened limits.

If the exchange response is lost, first check for the scoped bootstrap cookie. If absent, the host can reissue; replay must not mint additional browser sessions. No user-entered code is stored as a resume draft.

### 4.3 Proposed HTTP contracts

These routes are proposed. Wire formats should live in the shared public contract package and be validated at both boundaries; owning modules control their implementation.

| Operation                        | Input                                                                     | Output and authority                                                                                  |
| -------------------------------- | ------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| `GET /api/setup/readiness`       | No secret; expected public installation ID may be compared                | Minimal readiness/version/protected-route status; no owner/host-private data; errors remain unknown   |
| `POST /api/setup/claim/exchange` | Code, expected installation ID and stable request ID over verified origin | Restricted bootstrap cookie and expiry; uniform failed exchange; no raw code in response              |
| `GET /api/setup/claim/status`    | Bootstrap cookie                                                          | Bound/expired/revoked/owner-created state; no established owner identity to an unauthenticated caller |
| `POST /api/setup/owner`          | Name, password and operation ID; valid bootstrap session                  | Owner identity transaction result and normal session if issued; no email required                     |
| `POST /api/auth/sign-in/owner`   | Password, correct installation origin; server resolves the one owner UUID | Existing normal session and normal account-status checks; generic rejected-credential response        |
| Host `issue/revoke code`         | Fixed trusted host operation; expected installation and generation        | One-use code shown locally or acknowledgment; no web issue/reset endpoint                             |

All credential endpoints use no-store responses and secret/body redaction. CSRF, origin and input checks precede state changes. Type definitions must prohibit credential fields in general setup draft types. All old email/social/OIDC paths that could create the first owner must require the same verified first-owner authority before identity creation, or be unavailable while the installer-managed instance is unclaimed. A secure new endpoint alongside open legacy bootstrap is a release failure.

### 4.4 Transaction and failure behavior

Under one database serialization boundary, recheck installation and code generation, absence of any bootstrap owner, current bootstrap-session authority and the intended operation. Atomically persist the UUID-keyed user, password credential, canonical `app.users.is_bootstrap_owner` designation, claim consumption, the installation-intent-to-owner association, initial setup record and successful bootstrap audit. The existing `app.users.is_bootstrap_owner` flag is the sole ownership authority. Add a partial uniqueness constraint for flagged owners only after a migration preflight rejects existing duplicates; do not invent a second authoritative owner pointer or registry. Installation/claim/progress records may retain receipt/reference IDs, but authorization always resolves the unique flagged owner. Shared readers reject zero/multiple owners where an established owner is required instead of choosing the first row. A populated database with no bootstrap owner is a recovery condition, never a fresh-claim candidate. Current legacy tests deliberately allow signup-based recovery in that state; replacing it requires a reviewed host-guarded repair/migration path and compatibility tests, not deleting those tests or silently reopening initial signup.

This must be a real shared transaction using the established privileged auth boundary, not a second transaction inside the current Better Auth after-hook. Respect module-owned public audit functions and database-role restrictions; do not grant the ordinary Settings runtime access to password tables to achieve it.

After commit, issue the normal session through the established session machinery. If that step or the response fails, retain the committed owner and consumed claim. The same browser reconciles its session; otherwise it signs in as owner with the chosen password. Do not delete a valid owner because cookie delivery failed, replay account creation or reopen initial signup. Store no password for retries. If identity commit fails, no owner credential or privileged session may survive.

No-email is a required product outcome; the candidate Better Auth boundary is conditional, not a supported drop-in configuration. Better Auth 1.6.14 documents email as required, its core user type requires `email: string`, and its default schema marks email required/unique. The implementation cannot satisfy this by asserting that a plugin, nullable database column or reshaped session output makes the whole vendor contract nullable.

Before selecting the adapter, complete the separately authorized disposable integration proof against the exact locked Better Auth/core/Kysely adapter and Moss PostgreSQL mappings. Candidate: Moss-owned owner creation/sign-in endpoints, real NULL email, an existing password credential keyed by immutable user UUID, established hash/verify utilities and documented endpoint/session primitives. Pass only if real vendor session creation/get-session/refresh/logout/revocation and Moss identity/status/access paths work with NULL through restart; DTOs/types honestly model absence; legacy email/password/social accounts still behave correctly; and email-free reset/verification cannot invoke a sender. No synthetic or empty-string email, dependency patch/fork, app-wide casting away of email requirements or mocked vendor/session result counts as proof. Record each unavoidable vendor type assumption inside one explicitly reviewed boundary rather than scattering casts.

Official custom endpoint and session-creation primitives exist, and inspected lower-level session storage keys by user ID, so a full authentication replacement is not yet proven necessary. Those seams still do not establish that absent-email creation/types and every consumer are supported. If the proof requires undocumented internal widening, global casts or weakened security, stop and review a scoped auth-boundary change before product planning. No automatic required-email fallback is selected. First-owner transaction/race/crash proof remains a separate mandatory gate even if nullable-email sessions work.

### 4.5 Schema and migration boundary

Proposed logical changes, with exact DDL reserved for the authorized implementation plan:

- Immutable installation identity plus schema/journey compatibility versions. Ownership remains solely `app.users.is_bootstrap_owner`, with migration-preflight duplicate rejection and a database uniqueness constraint. Any installation receipt references a user non-authoritatively; no second owner field can diverge from the flag.
- Nullable/absent owner email through user storage, DB types, public DTOs, session serialization, profile/admin/export rendering and every vendor consumer. Present-email uniqueness and existing account links are preserved.
- Explicit local-owner credential mode resolving the existing credential/hash authority by immutable user UUID. No second user identity or parallel password store is introduced.
- Hashed bootstrap claim, generation, expiry, bound-session identity and terminal operation metadata under auth ownership.
- Dedicated revisioned setup progress under Settings ownership, and explicit Notes source ownership/grants.
- Guarded self-delete accepts a no-email owner's explicit immutable-target confirmation and current credential/re-authentication requirement; legacy `confirmEmail` remains supported for legacy accounts. Removing the email field must not remove destructive-action confirmation.

Use additive migrations and verified pre-migration backup/restore procedures. Preserve user IDs, grants, source links, stable encryption/auth keys, sessions where compatible and existing email/social accounts. Never rewrite applied migration history. A failed migration leaves the application closed to unsafe bootstrap and reports recovery, not a new empty-owner state. Publish a minimum compatible binary/schema fence; an automatic image downgrade is not a safe database rollback.

### 4.6 Guarded recovery and administrative targets

Unify target checking across reconcile, password reset, delete-user-data, restore and key rewrap. Independent expected installation ID and owner UUID must match the actual exactly-one owner under the operation's transaction/lock. A UUID is target confirmation, not operator authentication; the sanctioned host/admin execution boundary remains required. Zero, multiple, missing or mismatched targets fail closed except a narrowly defined, genuinely empty fresh installation before any ownership exists.

For legacy installs, retain existing email confirmation until an explicit authenticated/host-authorized migration records the owner UUID and installation identity. Do not substitute a value queried in the same operation as its own independent confirmation. Fix the existing reconcile `LIMIT 1` ambiguity gap rather than copying it.

Password reset changes only the intended existing credential, requires exactly one affected credential row, uses hidden terminal input or protected IPC, and prohibits plaintext argv. It atomically updates the credential, records the audit and revokes all supported existing authentication access: browser sessions, legacy bearer sessions/bindings and paired/companion credentials as applicable. Recheck identity inside the lock, then verify a new sign-in and rejection of old access. The current echoing prompt/argv path and lack of full reset revocation are new work to replace, not safe behavior to inherit.

Email-free accounts never enter fallback email verification/reset/notification sends. Test this at the last sender boundary. A later optional recovery-email feature requires separate explicit enrollment, verification and delivery support; connecting an inbox does none of those.

## 5 Durable setup and navigation contract

### 5.1 Owner record

Use a dedicated Settings-owned record rather than expanding the existing global `onboarding.state` value into a multiuser draft:

| Field                        | Proposed meaning                                                                                           |
| ---------------------------- | ---------------------------------------------------------------------------------------------------------- |
| Key                          | Composite installation ID and immutable owner UUID, with one journey record                                |
| `journeyVersion`, `revision` | Compatible schema/journey version and monotonic compare-and-swap revision                                  |
| `status`                     | `pending`, `completed` or legacy-compatible `skipped`; terminal state is not overwritten by stale requests |
| `lastSavedScreen`            | Stable meaningful screen/subscreen identity, not an array index inferred from current readiness            |
| `steps`                      | Visited and deliberate saved/skipped decisions, separate from live capability status                       |
| `drafts`                     | Strictly allowlisted non-secret incomplete user input; no arbitrary JSON payload passthrough               |
| `resourceRefs`               | Canonical provider/connection/source and pending host-change references, not duplicated settings           |
| `pendingOperations`          | Bounded resource/action/request references and last acknowledged results, never secret payloads            |
| `completedAt`                | Set only by a committed completion transition                                                              |

RLS/authorization must prevent another account reading the row or inferring private drafts/references. Installation mismatch is a distinct rejection. An existing member never inherits the owner's journey.

Proposed API: authenticated owner `GET /api/onboarding/progress`, `PATCH /api/onboarding/progress` with `expectedRevision` and stable `operationId`, and an extended completion operation taking the expected journey revision. Retain `GET /api/onboarding/status` and existing complete/skip callers through explicit compatibility adapters; do not let global legacy writes overwrite another owner's record.

A stale revision returns a typed conflict with safe current saved state. Same operation ID and payload return the acknowledged result; a different payload under that ID is rejected. Where a canonical module's own mutation has an uncertain outcome, reconcile that module's state first, then advance the checkpoint. Do not claim an atomic transaction across external OAuth, filesystem operations and the progress database.

### 5.2 Resume, settings and concurrency

After authentication, load the owner's acknowledged checkpoint before deriving navigation, then refresh canonical resources. Failed reads retain last-known content visibly unverified and disable dependent edits. The wizard does not create default provider/source/preferences to fill a missing response.

Keep browser-local secrets in current credential-screen memory only; clear them on success, exit, origin change, sign-out or account change. Optional non-secret in-memory drafts may survive a transient request failure, but only acknowledged server data is promised after browser kill. Do not silently replay credentials on reconnect.

Each pending action is bound to installation, actor, resource, operation and initiating navigation generation. Late results can reconcile the same owner's resource after navigation but cannot change the current route without authority. Account changes invalidate private caches and callbacks. Completion and global finish share one same-account pending authority, preserving the shipped recovery behavior.

Settings and onboarding operate on the same underlying values. Canonical resource revisions prevent a stale wizard save from undoing a newer Settings change. Where an existing API has no version contract, extend that owned API or explicitly reconcile/review before committing; client timestamps alone are not CAS.

### 5.3 Completion

Ready reads canonical saved state and presents the expanded recap. Unresolved optional capabilities may remain skipped/failed/unknown with truthful consequences; unresolved required identity, transport, runtime readiness or an explicitly pending host recreation blocks completion.

Completion serializes the journey revision and terminal transition. A duplicate request returns the terminal acknowledgment without a second action. Unknown outcome triggers readback. If committed, show Open Today or navigate only when the original owner and navigation generation still apply. Never run host preparation, reconnect services, generate content or silently clear unsaved choices as a side effect.

## 6 Notes ownership and read/write readiness

### 6.1 Scope and binding

The host's pre-account external path or managed-folder intent is private installation data. Bind its opaque intent reference to the verified installation/owner inside the owner-creation transaction. Actual canonical source creation, filesystem preparation and probing happen afterward as idempotent owner-authorized operations. Only then permit account-private enumeration or ingestion under the granted scope. A source grant must be checked on directory listing, direct requests, preference reads, Notes tools, background indexing/jobs, status and exports. The host-global allowlist remains necessary but is not the permission model.

The managed source is one idempotent private owner directory. Onboarding must never expose, select or grant the entire multiuser vault root as a Notes source. Preserve the existing backend’s legitimate canonical private-vault storage mount and its account isolation; this requirement does not remove that storage. Failure retains intent and an existing working source; retry uses the same owner/intent rather than creating more directories. For legacy global roots, migrate only independently established exact account-source scopes and explicitly legitimate shared grants. Ambiguous/unowned roots require authenticated host/operator review; a saved path is not permission to grant its parent/global root to every account. Include cross-account migration, export and indexing negative tests.

The external mount contract continues to recognize `JARVIS_NOTES_VAULT_HOST_PATH` to `/data/external-notes`, but new generated binds use long syntax and strict existence checks. Grant only the reviewed directory. Reject host root, whole home, system/credential roots, unexpected aliases and path injection. Revalidate realpath/directory identity at selection, apply and probe to address symlink/mount time-of-check/time-of-use changes. Do not recursively change existing vault permissions.

### 6.2 Probe and activation

A proposed authenticated `POST /api/onboarding/notes/verify` takes an owner-visible candidate source ID, expected source/intent revision and operation ID, never an arbitrary host path. Server code uses the real runtime UID/GID and the authorized source resolver.

After disclosure, check read/list access and create a uniquely named temporary file exclusively in an authorized location, write/read a bounded sentinel, then remove that exact file safely. Never overwrite or test by editing an existing note. Bind cleanup to the created file identity, not an unchecked later path. A cleanup failure is `cleanup_required`, includes a private owner-visible location/recovery action and is not a successful readiness result.

Typed states: `not_configured`, `unavailable`, `missing`, `disallowed`, `read_denied`, `read_only`, `verification_unknown`, `cleanup_required`, `ready_rw`. Only `ready_rw` allows activating the replacement. Indexing has separate `not_started/running/failed/complete` status and does not hold up Continue after readiness.

A later mount edit has a saved owner checkpoint, approved host plan revision and explicit Compose recreation using the original project/file set/keys/volumes. The helper validates the owner target guard before recreation. On return, reauthenticate if necessary, verify the intended installation and new mount/source and then activate it. Existing selected subfolders within an already authorized mount need no host recreation. Existing Restart cannot be repurposed to claim new mount application.

### Ownership boundaries

Assign a single owner per shared boundary and keep parallel lanes on feature-specific surfaces:

- **Host-core owner:** shared plan/renderer/record contract and production/Notes Compose templates. Mac and Windows owners consume it through fixed typed operations; neither edits core files opportunistically.
- **Identity owner:** auth bootstrap/session compatibility, claim/rate-limit wiring and shared target guard. Guarded CLI call-site changes coordinate through this owner; unrelated lanes cannot add alternate signup behavior.
- **Progress and UI integrator:** setup repository/routes, the common wizard/navigation shell, application route/app-map integration and completion authority. Feature lanes add isolated screen/adapters against agreed props/public contracts, not concurrent edits to the wizard root.
- **Notes owner:** source grants, access resolver, probe/activation and canonical source UI. It requests host-plan changes through the host-core owner and identity binding through the identity owner.
- **Feature owners:** personalization, AI, email, News/Sports own their canonical adapters and isolated screens/tests. Shared catalog/DTO barrel changes go through their designated single owner.
- **Migration/release integrator:** reserves migration identifiers, reviews role/RLS grants and assembles cross-lane schema changes. Applied migrations are immutable; no two lanes assign the same number or edit one migration in parallel.
- **Independent review:** separate Standards and Spec review against a pinned diff plus security/installed-path proof review. The coordinator owns final QA/merge/tracker transitions under the repository process.

These are responsibilities, not additional horizontal “build all database, then all UI” tickets. Each candidate still delivers a narrow end-to-end user behavior. If a refactor is necessary, scope it to the smallest contract extraction and prove existing behavior first; do not import the executing setup generator merely to reuse its functions.

### Pinned Better Auth evidence and proof boundary

Better Auth tag 1.6.14 resolves to commit `5038d41ca2c2a7350efb499c4506ac812afd6ddf`. The required-email contract and candidate lower-level seams were checked against that source and the already-installed 1.6.14 distribution; that source review did not establish a supported nullable-email API.

- [Email concept](https://github.com/better-auth/better-auth/blob/5038d41ca2c2a7350efb499c4506ac812afd6ddf/docs/content/docs/concepts/email.mdx#L6), [core user type/schema 9–29](https://github.com/better-auth/better-auth/blob/5038d41ca2c2a7350efb499c4506ac812afd6ddf/packages/core/src/db/schema/user.ts#L9-L29), and [required/unique email plus extension merge 153–199](https://github.com/better-auth/better-auth/blob/5038d41ca2c2a7350efb499c4506ac812afd6ddf/packages/core/src/db/get-tables.ts#L153-L199): stock public contracts require email. Intersecting plugin fields cannot honestly widen the core `email: string` type.
- [Documented custom endpoint/session primitives 116–143](https://github.com/better-auth/better-auth/blob/5038d41ca2c2a7350efb499c4506ac812afd6ddf/docs/content/docs/concepts/plugins.mdx#L116-L143), [user-ID keyed session internals 317–505](https://github.com/better-auth/better-auth/blob/5038d41ca2c2a7350efb499c4506ac812afd6ddf/packages/better-auth/src/db/internal-adapter.ts#L317-L505), and [session route 367–507](https://github.com/better-auth/better-auth/blob/5038d41ca2c2a7350efb499c4506ac812afd6ddf/packages/better-auth/src/api/routes/session.ts#L367-L507): a Moss-owned compatibility boundary is plausible, but these seams do not make absent-email creation/types a supported drop-in option.
- G0a therefore precedes the full bootstrap tracer proof. It must record real database NULL and actual session consumers, honest nullable Moss types, restart/revocation/status checks and legacy compatibility. A mocked wrapper, bypassed validator, empty string or cast is not a pass. A full auth replacement is not selected merely because stock signup requires email.

### Isolated vendor-path experiment result

**Partial feasibility evidence, not G0a acceptance.** The authorized disposable experiment used the installed Better Auth/core/Kysely adapter 1.6.14 and a real file-backed Node SQLite database. The custom owner endpoint/sign-in path persisted genuine SQL NULL for email and exercised actual vendor signed-cookie/session code. The final recorded run on 12 October 2026 at 03:21:47–03:21:50 UTC passed 17 runtime assertion groups, including get-session, two fresh Node-process restarts, refresh, stock change-password after sign-in, logout, user-session revocation, expiry and a UUID-targeted password-update primitive. Environment: Node 24.19.0, Better Auth/core/Kysely adapter 1.6.14, Kysely 0.29.2 and TypeScript 6.0.3; no dependencies were installed or changed. Requests and Cookie/Set-Cookie headers were exercised directly in process, without a network listener, browser, external account or real credential.

The experiment also confirmed that the core User Zod parser and TypeScript user contract reject null/missing email, and stock signup/reset still require email. The strict typecheck with six expected-error assertions exited 0; removing those annotations yielded the six real email-contract errors and exit 2, including cookie/create-user inputs. Runtime exploration was explicitly JavaScript and did not claim a type-safe product integration or hide the mismatch behind casts. Thus it demonstrates a possible runtime seam, not a documented nullable-email API or a completed honest type boundary. It does not justify a configuration-only fix, a fake/empty email, scattered casts or a forced-email fallback.

The environment had no PostgreSQL/Docker executable. A built-in SQLite dialect attempt hit a missing Kysely export; the successful experiment used supported Kysely-instance configuration with an explicit test-only SQL execution driver bridge. The bridge exercised a real SQLite file and did not mock vendor session outputs, but its presence and different database backend limit the conclusion. No vendor dependency was patched.

Not tested: actual PostgreSQL/Moss schema, migration and RLS integration; Moss API and account-status consumers; schema migration and legacy email/social regressions; atomic owner/claim transaction and crash races; real browser UI/transport profiles; complete host recovery or all session/device revocations; mail-send suppression. The UUID update primitive is not proof of the guarded reset workflow. These remain mandatory G0a/G0b and release assertions, so no installer/auth implementation is certified by this experiment. No protection-removal security negative-control suite was run; the type counterexamples do not substitute for it. Disposable database/session tokens were deleted after the recorded run.

The completed reproducible report, sanitized result/log receipts, scripts and exact dependency fingerprints are retained with the engineering handoff; they are not shipped as product code.
