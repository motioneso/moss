# Extension classification: feature modules (part 3)

Read-only survey of the checkout. Tests skipped. Paths are relative to each section's folder.

## packages/news

News has two paths that decide which stories reach a person and in what order. The main path runs in
the background and saves a ranked snapshot per person. The fallback path builds a page live from
feeds when no fresh snapshot exists.

**Recommended open extension point for "which stories reach this person, and in what order":**
`rankCandidates` in `src/compilation/rank.ts`. It takes the candidate stories (already de-duplicated,
already stripped of excluded publishers and of stories the person dismissed) plus the person's topic
guidance, and returns the kept stories with a relevance score, sorted. Its sort step is the pure
function `orderRanked` in the same file. The built-in asks the AI model to score and drop
candidates; an extension could call that, then reorder, drop or promote stories. Two cautions. The
function takes a database handle as its first input, which the twin must keep out of the
extension's reach (close over it, pass only candidates and topics). And the "more like this" boost
and the dismissal filter run around it in `compilePersonalizedNews` (`src/compilation/compile.ts`),
so an extension here cannot undo a dismissal, which is the right behaviour. For the live fallback
path the matching point is `rankStories` in `src/ranking.ts`.

## Surprises

- `packages/news/src/compilation/compile.ts` holds the person's dismissal filter and the "more like
  this" boost in the same function as fetching and publishing. The open ranking point sits inside
  it. If anyone wants to extend the whole selection step rather than just the ranking, the
  dismissal filter must be split out first so an extension cannot bring dismissed stories back.
- `packages/news/src/compilation/rank.ts` takes a database handle as its first input. The twin must
  hide that handle from the extension.
- `packages/news/src/news-service.ts` mixes the open live-page grouping with the read-time recheck
  of exclusions and dismissals, which should stay built-in.
- `packages/news/src/compilation/candidates.ts` decides which sources to pull (open) but also
  routes keyed sources to the keyed reader. Keys never pass through it, but the routing should
  stay out of an extension's reach.
- `packages/news/src/source/catalog.ts` is a plain source list, but the list of hosts Moss may fetch
  from is derived from it. Extending the list would widen outbound traffic.
- `packages/meetings/src/export-render.ts` mixes layout (open) with escaping of untrusted text
  (must stay).
- `packages/wellness/src/recall-context.ts` computes an energy trend (open in spirit) and writes it
  into Moss's memory (privacy). Marked locked until split.
- `packages/notes/src/write-tools.ts` repeats the folder-confinement check from `path-guard.ts`.
  Marked locked until that check lives only in the guard.
- `packages/tasks/src/drift.ts` decides "at risk" and "in focus" inside database queries. It needs
  a pure function before it can be an extension point.
- `external-modules/finance/src/worker/handlers/sync.ts` mixes bank token reads with sync logic.
- Meeting summaries are written by a generator passed in from outside `packages/meetings`, and
  email triage is outside `packages/email`. Those extension points belong to whoever owns those
  callers.
- `packages/news/src/discovery/policy-validation.ts` was hard to place. It is a quality check (is
  this a real news site) that also acts as a gate on outbound traffic. Marked locked.
- `packages/sports/src/source/__fixtures__/*.json` are test data and are not counted.
