## Surprises

Files that mix locked and open logic. Each would need splitting before an extension point is possible.

- `packages/module-registry/src/route-catalog.ts` holds the filter that hides routes Moss may never call. It also holds `searchScore` and `search`, which rank which app actions Moss finds for a request. The ranking is a good extension point once it moves out.
- `packages/settings/src/app-action-tools.ts` runs both the "find an app action" tool and the "call an app action" tool. The call goes into the approval checkpoint. The find tool only passes the catalog search through.
- `packages/connectors/src/email-extract.ts` builds the email summary prompt and parses the answer, which is a prime customization. The same file caps the stored summary so a model cannot echo a whole email, and it applies the sign-in code hiding rule. The cap and the hiding rule must stay outside any extension.
- `packages/module-registry/src/index.ts` (4,010 lines) is the composition root. It decides whether a module may act on Moss itself and lists the tables a data deletion clears. It also builds `buildNewsDiscoveryPorts`, `buildSportsDiscoveryPorts`, `buildNewsBriefingSource` and `buildSportsBriefingSource`, which choose news and sports sources for briefings. Those four are open once split out.
- `packages/module-registry/src/meeting-output-runtime.ts` wires the meeting summary model call. It also enforces that meeting notes never go to a substitute model. The privacy rule must stay locked. How the summary is asked for could be opened elsewhere.
- `packages/cli-runner/src/model-list-adapters.ts` uses provider tokens. It also decides which models appear in the model list (`filterAnthropicModelIds` and siblings), which a person might want changed.
- `packages/settings/src/web-search-engine-resolver.ts` is marked open, but its order depends on whether a search key is saved. An extension should get the key's presence as a yes or no and never the key itself.
- `packages/shared/src/email-otp-rule.ts` is locked because loosening it could let sign-in codes reach summaries and briefings. A person might still want to fix a wrongly hidden email. That needs a different mechanism from an extension.
- Several manifests (`manifest.ts` in connectors, settings, workshop, backtrack, structured-state) declare tool risk and approval rules alongside plain metadata such as queue names and migration folders. I marked them locked. The integrations manifest has no risk declarations, so I marked it plain.

Classification notes:

- The integrations tool classifier (`classifier-*.ts`) is model-driven grouping, but its groups map straight onto risk and "run without asking". So I locked all of it under the action checkpoint. Only the display name and display grouping are open.
- I classified `packages/settings/src/runtime-config-*.ts` as locked because one of its keys is a search API key. If secret keys move fully into the credential store, the resolver and routes would be plain.
- `packages/integrations/src/call-memory.ts` contains non-text bytes, so grep treats it as a binary file. I read its header, and it is a per-person store that blocks the same tool call twice in quick succession (plain).
