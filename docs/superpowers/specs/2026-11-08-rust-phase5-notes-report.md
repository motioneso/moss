## Adapter contract and limits

The trusted host maps a `(module, resource)` pair to an account's folder preference and supplies
that account's allowed roots. Module parameters never select an account or an absolute root.
Relative legacy preferences can resolve against a configured base preference. The generic
adapter has no People-specific settings or behavior.

The pending-verification operations on the `vault` port are `notes.read`, `notes.list`, `notes.compare-write` and
`notes.remove`. File paths are relative Markdown names in parameters. Reads return the legacy canonical-path `destinationId`. Mutations require that ID and the
exact expected text, or null for a new file; a folder relink invalidates the old destination. Folder locks remain held until invocation finish.
Failed invocations compensate only if the current bytes still equal the adapter's last write;
an external edit is retained and reported as a rollback conflict.

This is compensation, not an atomic database/filesystem transaction. It does not recover a
process killed after publication. Arbitrary editors do not participate in folder locking.
The existing VaultContext component-check/open race remains, as does a final comparison versus
an arbitrary editor's rename. Empty parent folders created before a failed write may remain.
These limits must not be presented as stronger guarantees in later module work.
