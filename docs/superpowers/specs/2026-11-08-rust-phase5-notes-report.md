## Adapter contract and limits

The trusted host maps a `(module, resource)` pair to an account's folder preference and supplies
that account's allowed roots. Module parameters never select an account or an absolute root.
Relative legacy preferences can resolve against a configured base preference. The generic
adapter has no People-specific settings or behavior.

The operations on the `vault` port are `notes.read`, `notes.list`, `notes.compare-write`
and `notes.remove`. File paths are relative Markdown names in parameters. Reads return the legacy
canonical-path `destinationId`. Mutations require that ID and the exact expected
text, or null for a new file; a folder relink invalidates the old destination.
Folder locks remain held until invocation finish.
Failed invocations compensate only if the current bytes still equal the adapter's last write;
an external edit is retained and reported as a rollback conflict.

This is compensation, not an atomic database/filesystem transaction. It does not recover a
process killed after publication. Arbitrary editors do not participate in folder locking.
The existing VaultContext component-check/open race remains, as does a final comparison versus
an arbitrary editor's rename. Empty parent folders created before a failed write may remain.
These limits must not be presented as stronger guarantees in later module work.

## Review follow-up

The first independent Claude review found one major issue: preference lookups could
wait beyond the call deadline, including forever on an exhausted pool. The regression
test failed first with the only pool connection held. Folder providers now receive
the remaining budget; the built-in provider bounds acquisition, query and commit,
using discard-on-cancellation data contexts. The same full-pool test uses a 100 ms
budget and permits two seconds for scheduling while the connection remains held.
The corrected database gate passed both this regression and the existing privacy test;
the guest suite also passed all nine tests again and host strict Clippy passed.

The review also identified three minor limitations, retained explicitly for part two:

- A global state mutex spans file I/O. Slow filesystems can stall other accounts;
  per-call locking is deferred rather than claiming filesystem I/O deadlines.
- The preliminary text-edit helper is literal, whereas the legacy JavaScript editor
  expands dollar replacement tokens. The 118-vector block/identity corpus does not
  cover that helper; complete edit-tool parity remains continuation work.
- Reads/listings create `.moss-notes.lock` in the chosen folder. That requires a
  writable folder and the hidden file may be synced by outside software. Read-only
  folder parity and a revised lock strategy remain continuation work.
