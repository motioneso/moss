What changed. Each connection is one ruled row, read left to right: who it is, whether it works, how many tools are on, and whether the classifier can use it. The whole row opens the connection, so the separate Configure button is gone. The tool-server and web-API badges are gone too, because they describe plumbing, not anything you act on.

3. Classifier states

The flow from issue 2984. There is no Prepare button and no risk to pick for each tool. Turning the switch on shows what is sent and what it costs, once. After that Moss prepares every tool by itself. Every tool you have on stays on, the risky ones still ask you before they run, and you only ever switch tools off. A tool that changes is prepared again without asking.

What is left to show. Seven states remain, drawn here at the real width of the rail. The phone row underneath is the same block at phone width, where it sits above the tool list.

4. A very big connection

What changed. Radarr has 237 tools in 71 sections, and only the five movie tools are on. Today that is a 47,000-pixel page. Here the sections with everything off fold into a compact three-column index, the sections with something on stay open, and the summary says "5 of 237 on, in 1 of 71 sections" before you scroll at all.

Why. On a big connection you are hunting for the few tools you want. Search and the folded index get you there; a wall of switches does not. Radarr's own descriptions are web addresses, so they show as code.

5. Readable tool names

Proposal. Show a readable name in bold and the raw name underneath in small, faint type. The raw name stays searchable and copyable, but nobody has to parse it to find a tool. It stays in the normal typeface, because it is a label here, not code.

Where the readable name comes from. A simple rule makes a decent name for free, with no model call. When the classifier prepares the tools, the model can also write a better name in the same pass, at no extra call. The middle column is the free rule, the right column is the model's name.

  1. Drop known prefixes: intent_script__, Hass, api_v3.
  2. Split joined words at capitals and underscores, then lower-case all but the first word.
  3. For web services, turn the method into a verb: get becomes "Look up" or "List", post "Add", put "Update", delete "Delete".
  4. When the description only repeats the name ("Execute Home Assistant AddTaskWork intent"), hide it and say there is no description, instead of showing filler.

Questions for you

  1. One switch per tool, or two? The mockups keep one switch: off means Moss never uses the tool, in chat or in the classifier. The tool's menu has "Keep out of the classifier" for the rare case where chat should use it but quick answers should not. Is that menu item worth having, or should it go?
  2. Grouping before the classifier runs. Grouping by what a tool does needs Moss to know each tool's risk. Home Assistant sends no hints, so without the classifier the list falls back to Home Assistant's own groups, A to Z. Should Moss run a cheap naming and sorting pass even when the classifier is off, or is A to Z fine until you turn it on?
  3. Full-width screen for one connection. The connection's screen hides the settings index and shows a "Settings / Connections" trail instead, to get the width back. Is that all right, or should the index stay?
  4. Model-written names. The free rule gives "Add task work"; the model gives "Add a work task". Is the better name worth having the model write it during preparation?
  5. The word "classifier". The switch reads "Let the classifier use this connection". Would a plainer name read better, for example "Quick answers"?
